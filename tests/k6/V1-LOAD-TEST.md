# v1 사용자 흐름 부하 테스트

기준: [v1 인프라 설계](https://github.com/100-hours-a-week/KTB4-5th-wiki/wiki/Cloud-1단계-초기-배포-설계). 대상은 개발 서버 `https://dev.dameokja.com`이다.

| 구간 | 서로 다른 계정 | 로그인 흐름 횟수 | 기간 | 업무 API 평균 RPS |
| --- | ---: | ---: | --- | ---: |
| 아침 | 140 | 140 | 5분 | 1.4 |
| 여유 목표 | 200 | 700 | 5분 | 7 |
| 평일 저녁 | 100 | 100 | 1시간 | 0.0833 |
| 주말 점심 | 150 | 150 | 1시간 | 0.125 |
| 주말 저녁 | 150 | 150 | 1시간 | 0.125 |

각 흐름은 로그인 → 최신 등록순 재고 조회 → 유통기한순 조회다. 각 계정은 별도 VU와 쿠키 저장소를 사용한다. 세션 시작을 전체 기간에 균등 분산한다. MAU 200명을 200명 동시 활동으로 해석하지 않는다. 최신 등록순 첫 조회는 정렬 변경을 표현하기 위한 모델링 선택이다.

CSRF 발급을 흐름마다 별도로 수행한다. 업무 요청 3개 외에 HTTP 요청 1개가 추가되므로 여유 목표 구간의 전체 요청률은 약 9.33RPS다. 실제 전송 타이밍에 따라 순간 요청률은 다르다. 사용자 생각 시간, 브라우저 정적 자원, SSE는 포함하지 않는다.

## 실행

WSL에서 이 디렉터리로 이동한 다음 실행한다. 기존 private/accounts.json의 계정 200개가 필요하다.

```bash
k6 run -e MODE=smoke v1-flow.js
python3 run_v1_suite.py
```

전체 실행은 약 3시간 10분이다. 중복 실행하지 않는다. 단일 구간은 MODE를 morning, peak, weeknight, weekend_lunch, weekend_dinner 중 하나로 지정한다. 실행 프로세스에서 Ctrl+C로 중지할 수 있다.

## 결과 및 해석

private/v1-suite-status.json에 진행 상태, private/v1-구간.json에 지표, 같은 이름의 .log에 실행 로그를 기록한다. private 디렉터리는 Git에서 제외한다. 결과 파일은 재실행하면 덮어쓴다.

설계의 200ms 목표를 본 스크립트에서는 업무 API p95<200ms로 해석했다. 설계 자체에 백분위는 명시되어 있지 않다. 상한은 max<1000ms로 확인한다. 단발성 HTTP·응답 형식 오류는 해당 흐름만 실패 처리하고 재시도 없이 다음 예정 흐름을 진행한다. 전체 요청(CSRF 포함) 연속 5회 실패, 또는 최근 최대 100건 중 최소 20건 관측 후 실패 5건 이상이며 실패율 5% 이상이면 전체 실행을 중단한다. 이 중단 기준은 run_v1_suite.py 실행 시 적용된다. 오류율·응답시간 목표 미달은 결과에 그대로 남기되 중단 기준에 도달하지 않으면 다음 구간을 진행한다.

기존 계정의 재고를 그대로 조회하며 데이터를 추가하거나 삭제하지 않는다. 빈 목록 응답은 empty_inventory_responses에 기록한다. 빈 냉장고 중심의 결과는 실제 데이터가 쌓인 DB 조회 성능을 대표하지 않는다. 사전 점검에서는 두 계정의 목록이 모두 비어 있었다.

월간 가용성 99%, 서버 CPU·메모리·DB 연결·파일 디스크립터 한계는 이 클라이언트 테스트만으로 입증할 수 없다. 지연 원인 판단에는 같은 시간대 서버 지표가 추가로 필요하다.

실행 방식 참고: [k6 per-vu-iterations 공식 문서](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/per-vu-iterations/).
