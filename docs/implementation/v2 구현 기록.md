## 구현 의사결정

### I1. IaC 도구

- 날짜: 2026-10-07 (M14 네트워크 진입점 구축)

**결정 요약**: v2는 **CloudFormation**, v3(k8s)는 **Terraform**으로 전환을 검토합니다.

**이유**
- v1에서 이미 CloudFormation을 쓰고 있음(`infra/monitoring`, `infra/discord-alerts`)
- state 파일을 직접 관리할 필요가 없음(AWS가 스택으로 상태 관리)
- 10/16까지 일정이 빠듯해 새 도구를 익힐 여유가 적음
- v3는 k8s로 구조가 크게 바뀌고, Terraform은 AWS 리소스와 Kubernetes·Helm을 한 코드로 묶을 수 있어 전환 시점으로 적절함

| | CloudFormation | Terraform |
| --- | --- | --- |
| 문법 | YAML/JSON | HCL |
| 미리보기 / 적용 | change set / `deploy` | `terraform plan` / `apply` |
| 상태 관리 | AWS가 스택으로 관리 | state 파일 직접 관리(S3 + 잠금) |
| 범위 | AWS 전용 | AWS, GitHub, Kubernetes 등 |

**트레이드오프**
- v3에서 도구를 바꾸면 v2 템플릿은 재사용하지 못함
- 하나의 리소스는 한 도구만 관리해야 함. v2 리소스를 v3에서도 쓰면 `terraform import`로 가져온 뒤 CloudFormation 스택에서는 `DeletionPolicy: Retain`을 걸고 제거하는 순서로 옮김. v3를 새로 만들고 v2 스택을 삭제하면 DB처럼 데이터가 있는 리소스만 import 대상

### I2. 콘솔 사용 범위

- 날짜: 2026-10-07

**결정 요약**: 템플릿은 파일(`infra/v2/`)로 관리하고, 일반적인 인프라 배포는 I3의 GitHub Actions를 통해 수행합니다. 콘솔은 **최초 부트스트랩 배포와 change set·Events 확인**, **각 서비스 리소스 조회**에 사용합니다. 스택이 만든 리소스를 콘솔에서 직접 수정하지 않습니다.

**이유**
- CloudFormation 콘솔에서 템플릿 업로드, change set 확인, Events 확인을 해도 CLI `deploy`와 결과가 같아 IaC가 유지됨
- 콘솔에서 리소스를 직접 바꾸면 템플릿과 실제가 달라지고(drift), 다음 스택 업데이트 때 덮어써지거나 업데이트가 실패함

**예외**: 급하게 콘솔에서 고쳤다면 같은 내용을 바로 템플릿에도 반영하고, drift detection으로 차이가 없는지 확인

### I3. 인프라 배포 파이프라인

- 날짜: 2026-10-07

**결정 요약**: 최초 부트스트랩을 제외한 CloudFormation 템플릿 적용은 **GitHub Actions에서 CD 검증 과정을 거쳐 수행**합니다. PR에서는 템플릿 검증과 change set 검토를 수행하고(적용 안 함), main에 머지되면 배포 전 검증 통과 후 스택을 적용하고 배포 후 동작을 확인합니다. AWS 접근은 Access Key 없이 GitHub OIDC 역할로 합니다. 아래 검증 흐름은 구현 방향이며, 이 문서 변경 자체가 워크플로 구현 완료를 의미하지는 않습니다.

**이유**
- Git의 템플릿과 적용 이력을 배포 기준으로 통일함. 다만 Actions 사용만으로 drift가 자동 방지·복구되지는 않으므로 별도 확인이 필요함
- 머지 전에 무엇이 생기고 지워지는지(특히 교체되는 리소스)를 PR에서 확인할 수 있음
- 앱 CI/CD(v1 CI·CD 위키, v2 23번 ECS Native Blue/Green 호출)가 모두 GitHub Actions라 인프라 배포도 같은 도구·같은 OIDC 방식으로 맞춤 (2026-10-07 사용자 결정, Git sync와 비교 후 선택)
- 기존 Discord 알림 워크플로가 그대로 결과를 알려 주고, 조직 저장소에 별도 GitHub App 설치 승인이 필요 없음
- **저장소가 public이므로 표준 GitHub-hosted runner의 실행 분수는 무료이며, private 저장소처럼 월별 무료 실행 시간 한도를 소진하지 않음.** 실행 시간 과금 부담 없이 CD 검증과 배포 완료 대기를 구성할 수 있다는 점을 선택 근거로 삼음. 여기서 “무제한”은 무료 실행 분수 기준이며, 작업별 최대 실행 시간·동시 실행 수 제한은 존재함. Larger runner는 public 저장소에서도 유료이고, AWS 리소스 비용 등은 별도임(2026-10-07 공식 문서 확인).

**조사 과정과 판단 기준**

1. 처음에는 Actions가 JSON을 S3에 저장하고 Lambda가 받아 인프라를 적용하는 방식을 검토함. IaC 목적에서는 CloudFormation이 JSON/YAML 템플릿을 직접 해석해 리소스를 관리하므로 중간 전달용 Lambda가 필수는 아님. S3는 필요할 때 템플릿·배포 산출물 저장에 사용하고, Lambda Custom Resource는 기본 리소스로 표현할 수 없는 작업에 한정해 검토함.
2. CloudFormation Git sync는 추적하는 저장소·브랜치의 템플릿과 스택 배포 파일 변경을 감지해 스택을 갱신하므로 별도 배포 workflow를 작성하지 않아도 됨. PR에 change set 정보를 제공할 수 있고, 브랜치 보호와 PR 승인으로 머지 전 검토도 가능함.
3. Git sync의 제약은 인프라 내용을 상세하게 선언할 수 없다는 것이 아니라, 배포 전후 임의 작업과 조건부 진행을 하나의 파이프라인으로 제어하는 범위가 제한적이라는 점임. 템플릿 문법·정책 검증은 Git sync를 유지하면서 Actions CI로 추가할 수도 있음.
4. Actions 역시 잘못 작성한 코드를 자동으로 안전하게 만들지는 않음. 실제 안전성은 검증 항목·실패 시 중단 조건·복구 절차에 달려 있음. 따라서 “실수를 할 수 있어서 Actions를 선택”하기보다 **배포 중간 결과를 확인하고 다음 단계 진행 여부를 제어하기 위해 선택**함.
5. CloudFormation 업데이트 성공과 서비스 정상 동작은 다름. 예를 들어 보안 그룹 변경 자체는 성공해도 필요한 통신을 막으면 서비스는 실패할 수 있음. 스택 완료 후 필요한 통신·헬스 체크를 수행하고, 실패를 배포 성공으로 처리하지 않는 흐름을 구축함.

**후보 비교**

| 후보 | 장점 | 단점 |
| --- | --- | --- |
| **GitHub Actions (검증 → change set → 적용 → 동작 확인)** ✅ | PR 변경 미리보기, 배포 전후 검사·중단 조건·승인·독립 스택 간 순서 제어, public 표준 runner 실행 분수 무료 | 워크플로·역할·테스트·실패 대응을 직접 작성하고 유지해야 함 |
| CloudFormation Git sync | 배포 workflow 없이 변경 자동 반영, PR change set 댓글과 머지 전 승인 가능 | GitHub 연결 및 스택별 동기화 설정 필요. 임의 스크립트·적용 후 통합 테스트·환경 승격은 별도 자동화 필요 |
| Actions CI + Git sync 적용 | 머지 전 코드 검증과 간단한 자동 반영을 함께 구성 | 적용 이후 검증 결과에 따라 다음 환경의 배포를 진행하는 흐름은 추가 구성 필요 |

**선택한 검증 흐름**

```text
PR 생성
  → 템플릿 문법·정책 검사
  → change set 생성 및 생성·삭제·교체 대상 검토
  → PR 승인 후 main 머지
  → 배포 대상 커밋·파라미터 기준으로 재검증 및 변경 계획 확인
  → CloudFormation 적용 및 스택 완료 대기
  → 변경 대상에 맞는 통신·헬스 체크
  → 결과 기록·알림, 실패 시 후속 단계 중단
```

- 템플릿 검증 도구로 `cfn-lint`, 정책 검사 도구로 CloudFormation Guard 등을 검토함. 구체적인 검사 규칙과 서비스별 헬스 체크는 구현 시 확정함.
- PR에서 확인한 change set과 main에서 `deploy`가 생성하는 change set은 동일한 실행 대상이 아닐 수 있음. 머지 이후 상태·파라미터가 달라질 수 있으므로 적용 대상 변경 계획을 다시 확인해야 함.
- dev 적용 → 통합 테스트 → prod 승인·적용, 백업 완료 확인, 배포 시간 분리는 Actions에서 추가할 수 있는 확장 사례임. 모두 현재 구현 완료되었거나 필수 단계로 확정된 것은 아님.
- CloudFormation 자체의 실패 롤백과 배포 후 헬스 체크 실패의 복구는 별개임. 후자는 이전 템플릿 재적용 가능 여부와 데이터 영향을 고려한 복구 절차를 따로 정의해야 함.

**구성**
- 역할 3개: PR용 plan 역할(change set만), main 브랜치 전용 deploy 역할, CloudFormation 실행 역할
- 역할은 부트스트랩 스택(`infra/v2/bootstrap/github-oidc.yaml`)으로 한 번만 손으로 배포

**트레이드오프**
- 실행 역할이 AdministratorAccess라 main에 머지할 수 있는 사람이 사실상 계정 관리자 권한을 가짐 → main 브랜치 보호(리뷰 필수)로 보완
- v2 구현 계획의 GitHub OIDC 역할(10/12, M16)을 인프라용으로 앞당겨 만듦. M16에서는 앱 배포용 역할만 추가
- public 저장소의 외부 PR 코드에 AWS 배포 권한을 주지 않음. 비권한 검증과 AWS 접근이 필요한 change set 작업을 분리하고, 신뢰된 실행 경로에만 OIDC 역할을 허용함.

### I4. v2 진입 도메인과 전환 방식

- 날짜: 2026-10-07

**결정 요약**: v2 ALB는 먼저 **서브도메인(예: `v2.dameokja.com`)**으로 띄워 검증하고, 검증이 끝나면 기존 도메인을 v1에서 v2로 **Blue/Green 방식으로 전환**합니다. 전환 전까지 `dev.dameokja.com`은 v1 dev EC2를 그대로 가리킵니다.

**이유**
- v1 dev를 멈추지 않고 v2를 나란히 띄워 비교·검증할 수 있음
- 문제가 생기면 Route 53 레코드만 v1으로 되돌리면 되어 롤백이 간단함

**구현 메모**
- network 스택은 `DomainName` 파라미터로 서브도메인을 받아 ACM 인증서를 발급. 전환 시 기존 도메인을 인증서에 추가(SAN)하거나 와일드카드로 교체
- 전환은 Route 53 레코드 교체(또는 가중치 레코드로 단계 전환). 레코드 TTL을 전환 전에 낮춰 둠
- 이 전환은 인프라(v1 → v2) 전환이고, 앱 배포의 Blue/Green(ECS 타겟 그룹 2개, M16)과는 별개

### I5. 사용 AZ

- 날짜: 2026-10-08

**결정 요약**: v2는 **ap-northeast-2b, ap-northeast-2c** 두 AZ를 씁니다. 템플릿 파라미터 `AzA`=2b, `AzB`=2c이고, 이름의 A/B는 "첫째/둘째 AZ"라는 뜻입니다.

**이유**
- 기존 환경을 2b에 두고 있고, 다른 AZ는 이전에 2c로 설정해 왔음 (사용자 결정)

**구현 메모**
- NAT 1개는 `AzA`(2b) public 서브넷에 둠. 2b 장애 시 2c private 서브넷의 외부 통신도 끊기는 것은 감수
- 인스턴스 타입(t4g 등)이 2c에 있는지는 배포 전 `describe-instance-type-offerings`로 확인

### I6. dev와 prod의 구성 차이

- 날짜: 2026-10-08

**결정 요약**: v2 dev는 prod와 같은 구조로 만들지 않고 **ECS 인스턴스 1대**에 nginx, FE, BE, Redis를 올립니다. DB는 지금처럼 분리된 기존 dev DB 서버를 그대로 씁니다. v2 prod는 v1 prod와 **따로 새로** 만들고, 완성되면 Route 53에서 전환합니다(I4와 같은 방식).

**이유**
- dev를 prod와 같게(ALB, 2AZ ASG, DB Primary·Standby·Replica·Orchestrator) 두는 것은 dev 용도에 비해 과함 (사용자 판단)
- Docker Compose 대신 ECS 1대로 두면 Task Definition, SSM 설정 주입, GitHub Actions ECS 배포를 dev에서 미리 검증할 수 있음
- BE 코드는 환경별로 바꾸지 않고 접속 주소(DB `db-write`/`db-read`, Redis 엔드포인트)만 설정값으로 바꿈. dev는 `db-write`와 `db-read`가 같은 DB를 가리킴

**영향**
- ALB, 2AZ ECS·ASG, ECS Blue/Green, DB 이중화·failover는 **v2 prod에서 처음** 동작함. 전환 전 prod 서브도메인에서 충분히 테스트(사실상 스테이징)
- DB Standby·Replica 추가와 failover 테스트는 v1 prod가 쓰는 prod DB에서 처음 하게 됨 → 사용자가 적은 시간에 하거나, prod DB 스냅샷으로 만든 임시 DB에서 먼저 연습
- dev에는 Replica가 없어 복제 지연 문제가 dev에서 드러나지 않음 → BE에 "쓰기 직후 읽기는 `db-write`로" 원칙 공유
- 구현 계획(`docs/design/v2 구현 계획.md`)의 날짜별 작업과 network 스택 가이드는 이 결정에 맞춰 다시 정리 필요
- 인스턴스 계열: v1은 가격 우선으로 t4g(ARM)였지만, v2는 범용성 우선으로 **x86(t3)**. dev는 `t3.medium` (2026-10-08)
- OS: **Amazon Linux 2023 (ECS 최적화 AMI)**. Ubuntu도 고려했지만 AWS가 Ubuntu용 ECS 최적화 AMI를 제공하지 않아 Docker·ECS 에이전트 설치와 업데이트를 직접 관리해야 함. 컨테이너 안의 FE·BE 이미지는 호스트 OS와 무관하므로 AL2023 사용 (2026-10-08)

### 미결정

| 항목 | 후보 | 현재 추천 |
| --- | --- | --- |
| Redis 구성 | ElastiCache cache.t4g.micro / EC2 자체구축(t4g.micro, AOF 영속화) | EC2 자체구축 검토 중(v2 22번의 자체구축 방향과 일치) |

### 임시 기본값 (v2 설계에 없어 구현 중 정한 값)

| 항목 | 값 | 근거 / 바꾸는 조건 |
| --- | --- | --- |
| ALB idle timeout | 300초 | SSE 연결 유지(v2 21번). BE heartbeat 주기를 이보다 짧게. nginx `proxy_read_timeout`도 함께 조정 |
| S3 프로필 사진 조회 | 비공개 버킷 + Presigned URL | v2 17번은 "클라이언트 직접 접근"만 정함. 공개 읽기로 바꾸면 버킷 정책만 수정 |

## dev 구축 순서 (ECS 인스턴스 1대)

위 I6 결정에 따른 dev 구축 순서입니다.

### 구조

```
인터넷 ──80/443──▶ EC2 1대 (ECS 최적화 AMI, t3.medium, 자동 퍼블릭 IP)
                   └ ECS Task 1개 (host 네트워크)
                       nginx :80/:443 (TLS, certbot)
                       FE    :3000
                       BE    :8080 ──3306──▶ 기존 dev DB 서버 (그대로)
                       Redis :6379 (AOF는 호스트 폴더)
```

- v1 dev(`v1/dev/compose.yaml`)와 같은 구성을 Docker Compose 대신 ECS가 관리하고, Redis가 추가된 형태입니다.
- 기존 172.31 VPC의 **2b public 서브넷**을 그대로 씁니다. 새 서브넷, NAT, ALB는 만들지 않습니다.
- `host` 네트워크라 컨테이너끼리 `127.0.0.1:포트`로 통신합니다. v1 nginx 설정의 `frontend:3000`, `backend:8080`은 `127.0.0.1:3000`, `127.0.0.1:8080`으로 바뀝니다.
- 인스턴스는 ASG 없이 1대입니다. 인스턴스가 교체되면 호스트 폴더(인증서, Redis AOF, 로그)가 사라지기 때문입니다.
- 고정 IP(EIP)는 쓰지 않습니다(2026-10-08 결정). 퍼블릭 IPv4는 EIP든 자동 IP든 요금이 같고, 인스턴스를 끄지 않고 계속 켜 두는 운영이라 IP가 바뀔 일이 없기 때문입니다. **인스턴스를 중지했다 켜거나, `InstanceType`을 바꾸거나(중지·시작됨), 인스턴스가 교체되면 IP가 바뀌므로** 그때는 Route 53 레코드를 새 IP로 고쳐야 합니다.

### 0단계: 배포 파이프라인 (PR → 미리보기, main 머지 → 적용)

> 대상 저장소 `100-hours-a-week/KTB4-5th-CLOUD` · 리전 ap-northeast-2 · 결정 근거는 위 I3
> 파일: [`.github/workflows/infra-v2-cfn.yml`](../../.github/workflows/infra-v2-cfn.yml), [`infra/v2/bootstrap/github-oidc.yaml`](../../infra/v2/bootstrap/github-oidc.yaml). `cfn-lint`, `actionlint` 검사 통과

#### 동작

배포는 직접 스크립트를 짜지 않고 AWS 공식 Action [`aws-actions/aws-cloudformation-github-deploy@v2.0.0`](https://github.com/aws-actions/aws-cloudformation-github-deploy)을 씁니다. `mode: create-only`로 change set만 만들고 변경 내용을 Markdown(`changes-markdown`)으로 돌려줘서 PR 댓글에 그대로 붙입니다. 직접 쓰는 명령은 cfn-lint 실행과 PR 댓글 달기뿐입니다.

워크플로는 일부러 최소한으로 두었습니다. 쓰다가 불편한 점이 생기면 그때 추가합니다(아래 "나중에 추가할 수 있는 것").

```
브랜치에서 infra/v2/*.yaml 수정 → PR
  └ plan: cfn-lint → change set 생성 → 변경 목록을 PR 댓글로 (적용 안 함)
리뷰 후 main 머지
  └ deploy: change set 생성 후 바로 실행 (실제 적용)
```

- GitHub에 AWS Access Key를 저장하지 않고 **OIDC**로 그때그때 임시 자격 증명을 받습니다.
- 역할은 3개로 나눕니다.

| 역할 | 누가 씀 | 할 수 있는 것 |
| --- | --- | --- |
| `dameokja-github-cfn-plan` | PR 워크플로 | 읽기 + change set 만들기·삭제 (적용 불가) |
| `dameokja-github-cfn-deploy` | main 브랜치 워크플로만 | `dameokja-*` 스택에 change set 만들고 실행 |
| `dameokja-cfn-execution` | CloudFormation 서비스 | 실제 리소스 생성 (위 두 역할은 이 역할을 넘겨주기만 함) |

- 기존 `discord-cicd.yml`이 모든 워크플로 결과(`workflows: ["*"]`)를 Discord로 보내므로, 이 워크플로 결과도 따로 설정 없이 알림이 옵니다.


#### 순서

#### 1. GitHub OIDC 공급자 (확인 완료)

IAM 콘솔 → 자격 증명 공급자에 `token.actions.githubusercontent.com`이 이미 있습니다(2026-10-08 확인, 약 2개월 전 수동 등록). 계정당 하나만 만들 수 있어서 부트스트랩 템플릿은 공급자를 만들지 않고 이 공급자를 가리키는 역할만 만듭니다.

#### 2. 부트스트랩 스택을 손으로 한 번 배포

파이프라인이 쓸 역할을 파이프라인으로 만들 수는 없어서(닭과 달걀), 이 스택만 직접 배포합니다.

- 파일: `infra/v2/bootstrap/github-oidc.yaml`
- 콘솔: CloudFormation → 스택 생성 → 템플릿 파일 업로드 → 스택 이름 `dameokja-github-oidc` → 마지막 화면에서 **"IAM 리소스를 생성할 수 있음"** 체크
- 또는 CLI:
  ```powershell
  aws cloudformation deploy --region ap-northeast-2 `
    --stack-name dameokja-github-oidc `
    --template-file infra/v2/bootstrap/github-oidc.yaml `
    --capabilities CAPABILITY_NAMED_IAM
  ```
- 완료 후 **출력** 탭의 역할 ARN 3개를 복사

이 스택은 이후에도 바뀔 일이 거의 없고, 바꿀 때도 손으로 배포합니다.

#### 3. GitHub 저장소 변수 등록

저장소 → Settings → Secrets and variables → Actions → **Variables** 탭 → New repository variable

| 이름 | 값 |
| --- | --- |
| `AWS_CFN_PLAN_ROLE_ARN` | `GitHubPlanRoleArn` 출력값 |
| `AWS_CFN_DEPLOY_ROLE_ARN` | `GitHubDeployRoleArn` 출력값 |
| `AWS_CFN_EXEC_ROLE_ARN` | `CfnExecutionRoleArn` 출력값 |

역할 ARN은 비밀번호가 아니라서 Secrets가 아닌 Variables에 둡니다. 저장소 설정 권한(admin)이 필요하니 없으면 조직 관리자에게 요청하세요.

#### 4. 파라미터 파일 채우기

`infra/v2/params/dev.json`에 VPC ID와 2b public 서브넷 ID를 `ParameterKey`/`ParameterValue` 형식으로 채웁니다. 워크플로가 이 파일을 그대로 스택 파라미터로 넘깁니다.

- 저장소가 Public이라 VPC ID, 호스티드 존 ID가 공개됩니다. 자격 증명이 아니라 이것만으로 접근할 수는 없지만, 꺼려지면 이 값들도 GitHub Variables로 옮길 수 있습니다.

#### 5. 워크플로 추가

`.github/workflows/infra-v2-cfn.yml`을 저장소에 넣습니다. 처음 PR에는 아래 1단계(`infra/v2/dev.yaml`: ECS 클러스터 + 인스턴스 1대)를 함께 넣어 파이프라인과 dev 인스턴스를 같이 확인합니다.

#### 6. 첫 PR로 확인

- [ ] PR에 plan 체크가 뜨고 통과
- [ ] PR 댓글에 리소스 5개(클러스터, SG, 역할, 인스턴스 프로파일, 인스턴스)가 `Add`로 나온 표가 달림
- [ ] 머지 후 Actions의 deploy 통과, CloudFormation 콘솔에 `dameokja-dev` 스택 `CREATE_COMPLETE`
- [ ] Discord 알림 수신

이후는 아래 2~4단계를 **PR 하나씩** 올리면 됩니다. 로컬에서 직접 `deploy`하지 말고 PR로만 적용해야 Git과 실제가 어긋나지 않습니다.


#### 알아둘 점

- **plan 단계가 만드는 빈 스택**: 스택이 아직 없을 때 PR plan을 돌리면 `REVIEW_IN_PROGRESS` 상태의 빈 스택이 생깁니다. 정상이고, main 머지 때 그 스택에 실제로 생성됩니다.
- **첫 생성 실패**: main 배포에서 스택 첫 생성이 실패하면 `ROLLBACK_COMPLETE`가 되어 다시 배포가 안 됩니다. 콘솔에서 스택을 삭제하고 수정 PR을 머지하세요. 업데이트 실패는 자동 롤백되므로 고쳐서 다시 머지하면 됩니다.
- **Replacement 표시**: PR 댓글 표에서 `Replacement`가 `True`인 리소스는 지우고 새로 만들어집니다(예: 서브넷 CIDR 변경). 머지 전에 꼭 확인하세요.
- **실행 역할 권한**: `dameokja-cfn-execution`은 다음 날 ecs 스택(IAM 역할 생성 포함)까지 쓰려고 `AdministratorAccess`로 두었습니다. main에 머지할 수 있는 사람은 사실상 계정 관리자 권한을 갖게 되므로, main 브랜치 보호 규칙(PR 리뷰 1명 필수)을 같이 켜는 걸 추천합니다.
- **역할 위임이 실패할 때**: `Not authorized to perform sts:AssumeRoleWithWebIdentity`가 나오면 토큰의 `sub`와 부트스트랩 템플릿 조건이 다른 것입니다. 실제 `sub`는 CloudTrail 이벤트 기록에서 `AssumeRoleWithWebIdentity` 실패 이벤트의 `userIdentity.userName`으로 확인합니다. 이 조직은 이름 뒤에 ID가 붙는 형식(`repo:100-hours-a-week@167328634/KTB4-5th-CLOUD@1349507673:pull_request`)이라 템플릿 파라미터 기본값에 ID를 넣었습니다(2026-10-08 첫 PR에서 확인).
- **Fork PR**: 다른 사람 fork에서 온 PR은 OIDC 토큰을 받을 수 없어 plan이 실패합니다. 팀원은 같은 저장소의 브랜치로 PR을 올리면 됩니다.
- **스택이 늘어나면**: 10/8 ecs, service 스택이 생기면 `env`의 스택 하나를 `matrix`(스택 이름, 템플릿, 파라미터 파일 묶음)로 바꿔 순서대로 배포하게 확장합니다.

#### 일정 영향

GitHub OIDC 역할은 원래 M16에 있었는데, 인프라용 역할을 10/7에 먼저 만듭니다. M16(10/13)에서는 앱 배포용(ECS Blue/Green) 역할만 이 부트스트랩 스택에 추가합니다. 이 때문에 일정을 하루씩 밀고 버퍼를 하루 썼습니다([v2 구현 계획.md](../design/v2%20구현%20계획.md)).

### 1단계: 클러스터 + 인스턴스 (첫 PR)

`infra/v2/dev.yaml`에 들어 있는 것:

| 리소스 | 하는 일 |
| --- | --- |
| `Cluster` | ECS 클러스터 `dameokja-dev` |
| `InstanceSecurityGroup` | 80, 443을 인터넷에 엶. 22번은 열지 않음 |
| `InstanceRole` + `InstanceProfile` | ECS 에이전트가 클러스터에 등록하는 권한, SSM 접속 권한 |
| `Instance` | ECS 최적화 Amazon Linux 2023(x86_64) AMI. UserData로 클러스터 이름만 설정. 퍼블릭 IP는 서브넷 설정으로 자동 할당 |

읽는 법:
- `AmiId`의 `AWS::SSM::Parameter::Value<...>` 타입은 AWS가 공개해 둔 "최신 ECS 최적화 AMI ID"를 배포할 때 읽어 옵니다. AMI ID를 직접 적지 않아도 됩니다.
- `InstanceType` 기본값 `t3.medium`(x86, 메모리 4GiB): v1은 가격을 우선해 ARM(t4g)을 썼지만 v2는 **범용성**(x86 이미지·도구 호환)을 우선합니다(2026-10-08 사용자 결정). 메모리는 v1 dev가 2GiB에서 메모리 예산(2.2GiB)이 부족했고 이번에 Redis가 더해져 4GiB로 둡니다. 크기는 이 값만 바꾸면 됩니다.
- OS는 Amazon Linux 2023입니다(위 I6). Ubuntu는 ECS 최적화 AMI가 없어 Docker·ECS 에이전트를 직접 설치해야 해서 쓰지 않습니다. 앱은 컨테이너 안에서 돌기 때문에 호스트 OS가 달라도 FE·BE 이미지는 그대로입니다. 접속은 SSM Session Manager(사용자 `ssm-user`, 패키지 관리자 `dnf`).
- AMI는 x86_64용(`/aws/service/ecs/optimized-ami/amazon-linux-2023/recommended/image_id`)입니다. 다시 ARM(t4g 등)으로 가면 경로에 `/arm64`를 넣어야 합니다.
- **FE·BE 이미지가 amd64(x86)로 빌드돼 있어야 합니다.** v1이 t4g(ARM)에서 돌았다면 GHCR 이미지가 arm64 전용일 수 있으니, 각 저장소의 빌드 설정(`platforms`)을 확인하고 필요하면 `linux/amd64`를 추가합니다.
- 접속은 SSH 대신 **Session Manager**(EC2 콘솔 → 인스턴스 → 연결 → Session Manager)로 합니다.

파라미터 파일 `params/dev.json`에 넣을 값:
- `VpcId`: DB가 있는 172.31 VPC ID
- `SubnetId`: 그 VPC의 **ap-northeast-2b public 서브넷** ID (VPC 콘솔 → 서브넷에서 AZ가 2b이고 라우팅 테이블에 `0.0.0.0/0 → igw-`가 있는 것). 그 서브넷의 **"퍼블릭 IPv4 주소 자동 할당"이 "예"**인지도 확인 (기본 VPC 서브넷은 기본으로 켜져 있음)

### 2단계: 도메인 + DB 접근 (다음 PR)

- Route 53 A 레코드 `v2.dameokja.com` → 인스턴스 퍼블릭 IP(`!GetAtt Instance.PublicIp`) (파라미터 `HostedZoneId` 추가)
- 기존 dev DB 보안그룹에 "인스턴스 SG에서 오는 3306" 규칙 추가 (파라미터 `DbSecurityGroupId` 추가, `AWS::EC2::SecurityGroupIngress` 하나). 기존 규칙은 건드리지 않음
- MySQL 계정이 IP 하나로 묶여 있으면 새 인스턴스 IP(사설 IP)로 계정을 추가해야 함(10/1 트러블슈팅과 같은 원인)

### 3단계: 설정값 (콘솔·CLI로 1회, Git에 넣지 않음)

- BE·FE 환경변수 중 비밀값(DB 비밀번호, JWT 키, Redis 비밀번호 등)은 SSM Parameter Store `SecureString`으로 직접 만듭니다. 템플릿과 Git에는 이름만 들어갑니다.
- DB 접속 주소는 `db-write`, `db-read` 두 값으로 두고 dev는 **둘 다 같은 DB**를 가리킵니다. BE 코드는 prod와 같습니다.
- Redis 주소는 `127.0.0.1:6379`.

### 4단계: Task Definition + Service (다음 PR)

- Task 하나에 nginx, FE, BE, Redis 컨테이너. 네트워크 모드 `host`
- 호스트 폴더: 인증서(`/etc/letsencrypt`), certbot webroot, Redis AOF, nginx·BE 로그(v1과 같은 경로, CloudWatch Agent가 읽음)
- Service: 원하는 Task 수 1. 인스턴스가 1대이고 포트를 직접 쓰므로 배포 설정은 `minimumHealthyPercent: 0`, `maximumPercent: 100`(옛 Task를 내리고 새 Task를 올림, 배포 중 잠깐 끊김)
- 첫 인증서는 v1과 같이 certbot으로 발급
- **S3 (프로필 사진, v2 17번)**: 같은 PR에 dev 버킷과 **Task Role**을 추가
  - 버킷 `dameokja-dev-profile-images-<계정ID>`: 퍼블릭 액세스 차단, 클라이언트 조회는 Presigned URL(임시 기본값)
  - Task Role(BE 컨테이너가 쓰는 IAM 역할)에 이 버킷에 대한 `s3:PutObject`, `s3:GetObject`(삭제 기능이 있으면 `s3:DeleteObject`)만 허용
  - 인스턴스 역할에는 S3 권한을 주지 않음. 인스턴스 역할은 그 위의 모든 컨테이너가 같이 쓰기 때문
  - `host` 네트워크 모드에서 Task Role을 쓰려면 인스턴스 `ecs.config`에 `ECS_ENABLE_TASK_IAM_ROLE_NETWORK_HOST=true`가 필요할 수 있음(이 단계에서 AWS 문서로 기본값 확인 후 UserData에 추가)
  - BE에 S3 업로드 코드가 아직 없으면(구현 계획 리스크 표) 버킷·권한만 만들어 두고 동작 확인은 BE 구현 후
