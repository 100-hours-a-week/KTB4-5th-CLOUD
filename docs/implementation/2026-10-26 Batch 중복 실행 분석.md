# ECS Batch 중복 실행 분석

> 확인일: 2026-10-26 / 시간대: Asia/Seoul

> 후속 결정: Batch 중복 실행 제어는 BE에서 ShedLock으로 처리하기로 했습니다. 인프라의 별도 의사결정 범위에서 제외하며, 아래 내용은 분석 시점의 코드·운영 기록입니다.

**운영 로그에서 서로 다른 ECS Task 두 개의 Batch 중복 실행을 확인했습니다.** 분석 시점의 코드는 단일 인스턴스 처리를 전제하고 있으며, 발송 작업 중복 생성에 대한 일부 제약을 Batch 단일 실행 보장으로 볼 수는 없습니다.

## 1. 운영 환경에서 확인한 사실

AWS API로 조회한 `dameokja-prod` 클러스터의 `dameokja-prod-app` 서비스는 목표 2개·실행 2개·대기 0개이며, 현재 Task Definition은 `dameokja-prod-app:13`입니다. 각 Task에 BE 컨테이너가 포함됩니다. 해당 정의에서 Batch·스케줄 관련 환경 변수 및 Secret 참조, 환경 파일에 의한 실행 대상 분리는 확인되지 않았습니다.

CloudWatch Log Group `/dameokja/v2-prod/backend`에서 다음 실행 기록을 확인했습니다. 오전 8시의 Task ID는 당시 로그의 실행 주체이며, 조회 시점의 Task ID와 같다고 전제하지 않습니다.

| 한국 시간 | Task ID | 확인한 기록 |
|---|---|---|
| 2026-10-26 08:00:00.000 | `5d22caa3ddfe4882880ce03aa100a194` | 임박·만료 알림 Batch 시작 |
| 2026-10-26 08:00:00.000 | `7d21c51bd4f347e0a0217d5d9c3577ef` | 동일 Batch 시작 |
| 2026-10-26 08:00:01.420 | `5d22caa3ddfe4882880ce03aa100a194` | 생성 단계 완료: `refrigeratorCount=100`, `failedRefrigeratorCount=0` |
| 2026-10-26 08:00:01.307 | `7d21c51bd4f347e0a0217d5d9c3577ef` | 생성 단계 완료: `refrigeratorCount=100`, `failedRefrigeratorCount=0` |

2026-10-23 03:00에도 같은 두 Task의 알림 보관 정리 완료 로그가 각각 기록되어 있습니다.

이 기록은 스케줄 작업의 중복 실행을 보여줍니다. 사용자별 알림 중복 저장 건수나 동일 푸시의 실제 중복 수신 여부는 DB·발송 결과까지 대조하지 않았으므로 확정하지 않았습니다.

## 2. 코드의 제어 범위

### 스케줄 실행

BE의 `SchedulingConfig`는 조건 없이 `@EnableScheduling`을 활성화합니다. `NotificationScheduler`에는 08시 알림 생성·발송과 03시 정리 작업이 등록되어 있습니다. 해당 경로에서 분산 락·리더 선출·단일 실행 Task 지정은 확인되지 않았습니다.

`PUSH_EXPIRATION_BATCH_ENABLED=false`는 `sendPushNotifications()`의 푸시 생성·발송을 생략합니다. 08시 인앱 알림 생성과 03시 정리 작업까지 비활성화하는 설정은 아닙니다. 설정 파일의 스케줄러 빈 등록을 끈다는 주석과 실제 구현의 적용 범위가 다릅니다.

### 알림·발송 작업 생성

`ExpirationNotificationService.generate()`는 대상 재료로 알림을 만들고 저장합니다. 현재 `notifications` DDL에는 날짜·냉장고·알림 유형을 묶어 같은 일일 Batch 결과를 식별하는 UNIQUE 제약이 없습니다.

`PushNotificationRepository.findInboxPushTargets()`의 `not exists`와 `push_notifications`의 `uk_push_dispatch_subscription`은 동일한 논리 발송 키·구독·구독 버전의 발송 작업이 중복 생성되는 것을 제한합니다. 그러나 발송 키가 `INBOX:<notification_id>`이므로, 중복 Batch가 서로 다른 알림 ID를 생성한 경우에는 같은 업무 알림으로 묶이지 않습니다.

### 발송 작업 처리

`PushDispatchService`는 `PENDING`·`RETRY` 작업을 조회하여 가상 스레드로 발송하고, 결과 상태는 이후 별도 트랜잭션으로 갱신합니다. 여러 인스턴스가 같은 작업을 읽지 못하도록 하는 작업 선점 처리는 확인되지 않았습니다.

`PushNotification`에는 단일 인스턴스 전제로 `lease_until`·`claim_token`을 매핑하지 않는다는 주석이 있고, `PushNotificationStatus`에도 같은 이유로 `PROCESSING`을 두지 않는다고 명시되어 있습니다. DDL에 해당 컬럼과 상태가 존재하는 것만으로 실제 선점 기능이 동작하지는 않습니다.

가상 스레드의 동시 발송 수를 제한하는 Semaphore는 한 BE 프로세스 내부의 제한이며, 다른 ECS Task의 발송을 제어하지 않습니다.

## 3. 판단

분석 시점에는 일부 DB 중복 제약이 존재하지만, 여러 BE 인스턴스 사이의 Batch 단일 실행과 발송 작업 단일 처리는 보장하지 않는 것으로 판단했습니다. 운영 로그에서도 Batch 중복 실행이 확인됐으므로 Kubernetes 전환으로 새롭게 생기는 문제가 아니라 ECS 운영에서도 발생한 사항으로 분류했습니다.

후속 협의에서 통합 BE를 유지하고, 중복 실행 제어는 BE에서 ShedLock으로 처리하기로 했습니다. 해당 제어의 구현·검증은 BE 담당 범위로 두고 인프라의 미정 항목에서 제외했습니다. 독립 Batch·Worker 분리는 기존 고도화 범위로 유지합니다.

## 4. 확인 범위와 근거

- 운영 조회: ECS 서비스·Task Definition, CloudWatch의 Batch 시작·완료 로그를 읽기 전용으로 확인했습니다.
- 코드 확인: BE 저장소의 `feature/multiarch-image-build` 작업 사본과 DDL·테스트를 정적으로 확인했습니다. 운영 이미지와 작업 사본의 소스가 완전히 동일하다는 검증은 수행하지 않았습니다.
- DB 데이터 대조나 동시 실행 재현 시험, 애플리케이션·운영 설정 변경은 수행하지 않았습니다.
- 코드 근거: `SchedulingConfig`, `NotificationScheduler`, `ExpirationNotificationService`, `PushNotificationRepository`, `PushDispatchService`, `PushNotification`, `PushNotificationStatus`, `db/schema.sql`, `NotificationSchedulerTest`.
- Spring의 스케줄 실행 설명: [Task Execution and Scheduling](https://docs.spring.io/spring-framework/reference/integration/scheduling.html).
