## 1. 설계 방향과 요구사항
>
> **AWS EKS에서 서비스별 배포, 자원, 장애 대응을 표준화합니다.** 이 문서는 AWS 주 운영 환경의 구성과 운영 정책을 설명합니다.
>
> - 서비스, 조직의 변화와 Kubernetes 도입 목적은 [설계 배경](v3%20인프라%20설계%20전%20배경.md)에서 다룹니다.
>
> ### 1.1 운영 요구사항
> >
> > | 요구사항 | 설계 방향 |
> > |---|---|
> > | 배포와 운영 표준화 | FE, BE, AI API를 하나의 공통 Helm Chart와 환경별 Values로 각각 배포합니다. BE 내부의 API, Consumer, Batch는 통합 실행을 유지합니다. |
> > | 자원 관리, 확장 | 컨테이너마다 requests, limits를 두고, 환경별 NodePool과 Karpenter로 Node를 공급합니다. 알림, AI 처리의 동시 실행량은 Kafka와 고정 Replica로 외부 서비스 처리 한도 안에 둡니다. |
> > | 권한, 민감 정보 관리 | Secret을 앱별로 나누고 원본 값은 환경별 SSM 경로로 구분합니다. 팀별 Kubernetes 직접 권한은 아직 두지 않았습니다(7.1절). |
> > | 구축, 배포 설정 재사용 | 기존 AWS 네트워크와 CloudFormation, GitHub Actions, GHCR를 재사용하고, 세 환경이 같은 Chart와 같은 Workflow를 씁니다. |
> >
> > - Kubernetes와 ECS 개선안의 비교 및 검증 기준은 [Kubernetes 도입 근거](v3%20인프라%20설계%20의사결정%20근거.md#11-kubernetes-도입)에 정리했습니다.
> >

> >
> > #### 2.1.1 요청 흐름
> > >
> > > ##### 2.1.1.1 화면, API 요청
> > > >
> > > > 1. 사용자가 서비스 도메인에 접속하면 DNS 조회로 Route 53에 연결된 CloudFront 주소를 확인합니다.
> > > > 2. 브라우저는 서비스 도메인으로 CloudFront에 HTTPS 요청을 보내고, CloudFront에서 HTTPS를 종료합니다.
> > > > 3. CloudFront는 VPC Origin을 통해 Internal ALB에 HTTP로 요청을 전달합니다.
> > > > 4. ALB는 Host와 경로에 따라 해당 환경의 FE 또는 BE Pod로 요청을 전달합니다. Target Group은 Pod IP를 대상으로 합니다.
> > > > 5. 화면 요청은 FE가 처리하고, 업무 API 요청은 BE가 처리합니다. FE 서버가 넘기는 API 요청도 같은 Namespace의 BE Service로 갑니다.
> > > > 6. BE는 필요한 작업에 따라 같은 환경의 MySQL, Redis, Kafka에 접근합니다.
> > > > 7. FE 또는 BE의 응답은 ALB, CloudFront를 거쳐 브라우저에 전달됩니다.
> > > >
> > > ##### 2.1.1.2 AI 처리 요청
> > > >
> > > > 1. BE가 같은 Namespace의 `ai-api` ClusterIP Service에 HTTP(TCP 8000)로 이미지 분석 또는 추천을 요청합니다.
> > > > 2. AI API는 NAT Gateway를 경유해 RunPod 환경의 AI Server에 HTTPS로 모델 추론을 요청합니다.
> > > > 3. AI API는 처리 결과를 같은 환경 BE의 내부 콜백 주소(`/api/v1/internal/image-analyses/callback`, TCP 8080)로 보냅니다.
> > > > 4. BE가 결과를 DB에 반영합니다.
> > > >
> > > > Kafka를 통한 AI 작업 교환은 AI 저장소의 Kafka 코드가 병합된 뒤 연결됩니다. 이를 위해 환경별 AI 토픽과 AI의 Kafka 설정값(`KAFKA_ENABLED` 등)은 미리 넣어 두었고, 지금 AI 이미지는 이 값을 읽지 않습니다(4.5절).
> > > >
> > > ##### 2.1.1.3 이미지 업로드, 조회
> > > >
> > > > 1. BE가 해당 환경 S3 접두사(`image/`, `image/stage/`, `image/prod/`)에 대한 presigned URL을 발급합니다.
> > > > 2. 브라우저는 그 URL로 S3에 직접 이미지를 올리고 받습니다. 이미지 요청은 CloudFront를 거치지 않습니다.
> > > > 3. BE, AI API는 환경별 IRSA 역할로 같은 접두사의 객체에만 접근합니다.
> > > >
> > #### 2.1.2 운영 배치
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | Node 배치 | `tool`의 관리 도구와 `kube-system`의 CoreDNS, EBS CSI Controller, Metrics Server, 각 환경의 Kafka Topic Operator는 상시 운영하는 EC2 한 대의 시스템용 Node에 둡니다. 각 환경의 앱, Redis, Kafka는 Karpenter가 관리하는 환경별 NodePool(`dev-app`, `stage-app`, `prod-app`)에 둡니다. |
> > > | 로그, 메트릭 경로, 청록 실선 | Alloy를 모든 Worker Node에 DaemonSet으로 실행하여 Pod 로그를 관측 EC2의 Loki로, kubelet, cAdvisor, kube-state-metrics, BE 메트릭을 Prometheus remote-write로 보냅니다. 그림에서는 Node별 배치를 묶어 표시했습니다. |
> > > | 관측 EC2 내부 | Grafana가 Prometheus와 Loki를 조회하며, 같은 EC2 내부의 조회선은 전체 그림에서 생략했습니다. |
> > > | Grafana 접속 | 팀원은 별도 CloudFront(`grafana.dameokja.com`)와 VPC Origin을 거쳐 관측 EC2의 Grafana에 접속합니다(8절). |
> > >
> > > 환경별 도메인, 라우팅은 4.4절에서 다룹니다.
> > >
> > > Kafka는 환경별 클러스터와 저장 데이터를 분리하여 Strimzi로 운영합니다. dev는 단일 Kafka Pod, stage, prod는 Broker, Controller 겸용 Pod 3개를 사용합니다. 각 환경의 DB EC2에는 MySQL과 AI용 PostgreSQL을 별도 엔진으로 함께 실행합니다. Private Node의 이미지 다운로드와 외부 API 요청은 기존 NAT Gateway를 경유합니다.

> ### 2.2 기존 인프라 재사용
> >
> > - v2에서 다음 구성과 데이터를 이어받습니다.
> >
> > | 대상 | 유지 범위 |
> > |---|---|
> > | VPC, Subnet | 기존 prod VPC `10.20.0.0/16`과 2개 AZ의 Private Subnet(`10.20.32.0/20`, `10.20.48.0/20`)을 EKS, ALB에 재사용합니다. 이 네트워크는 v2 `dameokja-prod` 스택이 계속 소유하며, v2 앱 자원을 지울 때 네트워크 자원에 Retain을 걸고 스택 삭제 보호를 켰습니다(#321). |
> > | NAT Gateway | 기존 prod VPC의 NAT Gateway와 Private Subnet의 외부 송신 경로를 재사용합니다. |
> > | EC2 사양, OS | Worker Node는 `m7i.large`, Amazon Linux 2023을 유지하고 EKS용 AMI로 바꿉니다. stage, prod DB EC2는 v2 prod와 같은 `t3.medium`입니다. |
> > | MySQL, 데이터 | 자체 구축 MySQL과 기존 prod 업무 데이터를 유지합니다. prod 데이터는 새 prod DB EC2로 옮겼고, v2 DB 볼륨은 EBS 스냅샷으로 보관합니다(2.5절). |
> > | dev DB | 기본 VPC의 기존 dev DB EC2를 VPC Peering으로 연결해 재사용합니다. |
> > | CI, 이미지 공급 | GitHub Actions, GHCR, 빌드 명령, Dockerfile을 활용합니다. |
> > | IaC | AWS 기반 자원은 CloudFormation으로 관리합니다. |
> > | Secret 원본 | 앱 Secret의 원본 값은 SSM Parameter Store에 둡니다. dev, stage는 v3 이름의 경로로 옮겼고, prod는 v2 prod 경로를 그대로 읽습니다(7.2절). |

> ### 2.4 VPC와 네트워크
> >
> > | 항목 | 구성 |
> > |---|---|
> > | 워크로드 배치 | 앱, 시스템 Node와 stage, prod DB, 관측 EC2는 모두 단일 AZ `ap-northeast-2b`의 Private Subnet에 둡니다. AWS 내부의 DB Multi-AZ 대기 구성은 두지 않습니다. |
> > | EKS 등록 Subnet | 클러스터 생성 요건에 따라 서로 다른 2개 AZ의 Private Subnet을 지정합니다. |
> > | ALB Subnet | Internal ALB 구성 요건에 따라 같은 2개 AZ의 Private Subnet을 지정합니다. |
> > | 주소 대역 | Service CIDR은 `192.168.0.0/16`으로 VPC, 기본 VPC 대역과 겹치지 않게 둡니다. |
> > | EKS API | API endpoint는 private만 엽니다. 관리자는 시스템용 Node를 거치는 SSM 포트 포워딩으로 접속합니다. |
> > | Pod 네트워크 | EKS의 Pod 네트워크는 Amazon VPC CNI를 사용합니다. [Pod 네트워크 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#24-vpc와-pod-네트워크) |
> > | NetworkPolicy | dev, stage, prod의 Pod에 기본 수신, 송신 차단 정책을 적용하고, 아래 허용표에 정의한 연결만 허용합니다. |
> > | Pod별 보안그룹 | Security Groups for Pods를 사용하고, 환경, 서비스별로 나눈 SG를 SecurityGroupPolicy로 Pod에 연결합니다. |
> > | 통신 정책 관리 | Amazon VPC CNI의 NetworkPolicy와 Pod별 SG 기능을 켭니다. AWS SG는 CloudFormation(`<환경>-pod-sg` 스택)으로, NetworkPolicy와 SecurityGroupPolicy는 `v3/charts/platform` 차트로 관리합니다. |
> > | 내부 호출 | 애플리케이션 Pod 간 HTTP 호출은 ClusterIP Service를 사용하며, DB는 VPC 사설 경로(dev는 VPC Peering)로, Kafka는 환경별 bootstrap Service로 연결합니다. |
> > | 외부 송신 | Private Node는 기존 NAT Gateway를 통해 GHCR과 RunPod 등 외부 서비스에 접속합니다. |

> > #### 2.4.1 접근 제어 구성
> > >
> > > | 구성 | 적용 방식 |
> > > |---|---|
> > > | 환경, 서비스 식별 | Namespace는 `dev`, `stage`, `prod`, Pod 라벨 `app.kubernetes.io/name`은 `fe`, `be`, `ai-api`, `redis`로 구분합니다. Blue, Green Pod에도 같은 서비스 라벨을 유지합니다. Kafka는 Strimzi의 `strimzi.io/name` 라벨로 선택합니다. |
> > > | Pod SG 구성 | 각 환경에 `dameokja-v3-<환경>-fe`, `-be`, `-ai`, `-redis`, `-kafka` SG를 둡니다. 같은 환경, 서비스의 Replica는 같은 SG를 사용합니다. ALB는 세 환경이 함께 쓰는 `dameokja-v3-gateway-alb` SG를 사용합니다. |
> > > | Node SG 역할 | 클러스터 운영과 앱 배치에 필요한 연결을 허용하고, DB와 Kafka의 수신 규칙에는 Node SG 대신 해당 환경의 Pod SG를 지정합니다. |
> > > | CNI 적용 모드 | `ENABLE_POD_ENI=true`, `POD_SECURITY_GROUP_ENFORCING_MODE=standard`, `NETWORK_POLICY_ENFORCING_MODE=standard`로 구성하여 Pod SG와 NetworkPolicy를 함께 적용합니다. |
> > > | dev DB SNAT 예외 | dev DB 호스트(`172.31.4.192/32`)로 가는 트래픽은 `AWS_VPC_K8S_CNI_EXCLUDE_SNAT_CIDRS`로 Node IP 변환에서 뺍니다. DB SG가 Peering 너머에서도 Pod SG를 알아보게 하기 위해서입니다(#220, #226). |
> > > | 환경 격리 | NetworkPolicy의 Namespace, Pod 선택자를 함께 사용합니다. DB와 Kafka의 SG는 같은 환경의 허용된 Pod SG만 수신 대상으로 등록합니다. |
> > > | 송신 범위 | VPC 내부 목적지는 Pod, 사설 IP와 포트로 제한합니다. VPC 외부 HTTPS는 사설 대역을 뺀 TCP 443으로 허용하며, standard 모드의 외부 송신에는 Node SG가 적용됩니다. |
> > > | 정책 범위 | 별도 허용 규칙이 없는 앱 연결은 차단합니다. HTTPS 송신 허용은 특정 도메인만 허용하는 정책이 아닙니다. |
> > >
> > #### 2.4.2 환경별 통신 범위
> > >
> > > | 출발 환경 | dev 앱, DB, Kafka | stage 앱, DB, Kafka | prod 앱, DB, Kafka |
> > > |---|---|---|---|
> > > | dev 앱 | 서비스별 허용표 적용 | 차단 | 차단 |
> > > | stage 앱 | 차단 | 서비스별 허용표 적용 | 차단 |
> > > | prod 앱 | 차단 | 차단 | 서비스별 허용표 적용 |
> > >
> > > 공용 ALB, DNS, 관측과 관리 도구는 아래 운영 통신만 예외로 허용합니다. 같은 환경이라도 모든 서비스 간 통신을 허용하지 않습니다.
> > >
> > #### 2.4.3 서비스별 통신 허용표
> > >
> > > 아래 표는 세 환경에 동일하게 적용하며, 목적지는 모두 출발 Pod와 같은 환경으로 한정합니다. 포트는 컨테이너와 서버의 수신 포트를 기준으로 합니다.
> > >
> > > | 출발 | 목적지 | 프로토콜, 포트 | 용도, 제어 |
> > > |---|---|---|---|
> > > | 공용 ALB | FE Pod | TCP 3000 | 화면 제공, ALB SG에서 FE Pod SG로 허용하고 NetworkPolicy에는 ALB 배치 Subnet 대역의 수신을 허용합니다. |
> > > | 공용 ALB | BE Pod | TCP 8080 | 업무 API, ALB SG에서 BE Pod SG로 허용하고 NetworkPolicy에는 ALB 배치 Subnet 대역의 수신을 허용합니다. |
> > > | FE Pod | BE Pod | TCP 8080 | FE 서버의 API 전달, 같은 Namespace의 FE만 BE 수신 대상으로 허용합니다. |
> > > | BE Pod | AI API Pod | TCP 8000 | 이미지 분석, 추천 요청 |
> > > | AI API Pod | BE Pod | TCP 8080 | AI 처리 결과 콜백 |
> > > | BE Pod | Redis Pod | TCP 6379 | 세션, 알림, 임시 상태, Redis SG와 NetworkPolicy에서 같은 환경의 BE만 허용합니다. |
> > > | BE Pod | DB EC2의 MySQL | TCP 3306 | DB SG에서 같은 환경의 BE Pod SG만 허용합니다. |
> > > | AI API Pod | DB EC2의 PostgreSQL | TCP 5432 | DB SG에서 같은 환경의 AI API Pod SG만 허용합니다. |
> > > | BE, AI API Pod | Kafka Pod | TCP 9092 | 환경별 내부 bootstrap Service로 접속하고, Kafka Pod SG와 NetworkPolicy에서 같은 환경의 BE, AI API Pod만 허용합니다. |
> > > | AI API Pod | RunPod, Tavily, S3 | TCP 443 | 추론 요청과 이미지 조회, NAT 경유 HTTPS 송신으로 허용합니다. |
> > > | FE Pod | 외부 Webhook | TCP 443 | 버그 리포트 전송(Discord Webhook)에 필요한 HTTPS 송신을 허용합니다. |
> > > | BE Pod | Kakao, Sentry, S3 등 외부 API | TCP 443 | 업무 처리에 필요한 HTTPS 송신을 허용합니다. |
> > >
> > > FE의 DB, Redis, Kafka 접근, BE의 PostgreSQL 접근, AI API의 MySQL과 Redis 접근은 허용하지 않습니다. 브라우저에서 S3로 업로드하거나 CloudFront로 요청하는 연결은 Pod 송신 정책의 적용 대상이 아닙니다.

> > #### 2.4.4 공통 운영 통신
> > >
> > > | 출발 | 목적지 | 프로토콜, 포트 | 허용 범위 |
> > > |---|---|---|---|
> > > | 앱, 관리 Pod | `kube-system`의 CoreDNS | UDP, TCP 53 | DNS 조회를 허용하고 Node SG에서도 각 Pod SG의 53 연결을 허용합니다. |
> > > | Worker Node의 kubelet | FE, BE, AI API Pod | TCP 3000, 8080, 8000 | 해당 Node SG에서 Probe 대상 Pod SG로 허용합니다. Redis Probe는 컨테이너 내부 exec로 수행합니다. |
> > > | Node별 Alloy | BE Pod | TCP 8080 | `/actuator/prometheus` 메트릭 수집입니다. NetworkPolicy는 `tool`의 Alloy에서 오는 8080만 추가로 열고, Alloy는 Pod SG 없이 Node SG로 나가므로 Probe용 Node SG 규칙을 그대로 통과합니다. |
> > > | Node별 Alloy | 관측 EC2의 Loki, Prometheus | TCP 3100, 9090 | 로그 전송과 메트릭 remote-write입니다. 관측 SG에서 Node SG의 연결을 허용합니다. |
> > > | Kafka Pod | EKS API | TCP 443 | 브로커가 시작할 때 API에서 자기 설정 Secret을 읽습니다. NetworkPolicy는 API ENI가 놓이는 Subnet 2개와, DNAT 전 주소로 판단하므로 kubernetes Service 주소 `192.168.0.1/32`를 함께 엽니다(#222, #224, #275, #276). |
> > > | Strimzi Operator, Topic Operator | 해당 환경의 Kafka Pod | TCP 9091, 8443 | 복제 리스너와 Kafka Agent에 대한 상태 검사, 토픽 조정을 허용합니다. |
> > > | 같은 환경의 Kafka Pod | Kafka Pod | TCP 9090, 9091 | stage, prod의 Broker, Controller 겸용 Pod 사이의 KRaft Controller, 복제 연결입니다. 다른 환경의 Kafka 연결로 확대하지 않습니다. |
> > > | Argo CD, Karpenter, Controller | EKS API와 필요한 Webhook | API TCP 443, Chart의 Webhook 포트 | 도구의 조정, 배포에 필요한 연결만 허용합니다. |
> > > | Worker Node, 공통 관리 도구 | GHCR, GitHub, 필요한 AWS API | TCP 443 | 이미지 다운로드, Git 동기화, AWS 자원 제어를 허용합니다. Node의 이미지 다운로드는 앱 Pod의 Egress와 구분합니다. |
> > >
> > > 운영 예외는 서비스 간 교차 환경 통신 허용으로 확장하지 않습니다. Pod별 SG, DB, Kafka SG와 NetworkPolicy는 동일한 허용표를 기준으로 관리합니다.

> ### 2.5 데이터 배치
> >
> > | 대상 | 운영 구성 |
> > |---|---|
> > | MySQL | dev, stage, prod의 데이터와 DB 서버를 분리하고, 환경마다 Kubernetes 외부 EC2의 MySQL 1대에 연결합니다. AWS 내부의 별도 Multi-AZ Standby는 두지 않습니다. |
> > | dev DB | 기본 VPC의 기존 dev DB EC2(`172.31.4.192`)를 VPC Peering으로 연결합니다. 기존 AI용 PostgreSQL은 AI EC2의 `127.0.0.1`에서만 받아 Pod가 닿을 수 없으므로, 같은 dev DB EC2에 PostgreSQL을 새로 설치했습니다(#225). |
> > | stage DB | EKS VPC에 `stage-db` EC2(`t3.medium`, MySQL 8.4 GTID와 PostgreSQL 16)를 둡니다. v2 stage DB는 v2 stage 스택에 묶여 v2 정리 때 함께 지워지므로 새로 만들었습니다(#256, #257). 데이터는 옮기지 않고 dev의 BE 스키마와 AI 스키마, 기준 데이터만 넣었습니다(#266). stage를 끌 때 함께 중지합니다. |
> > | prod DB | EKS VPC에 stage-db와 같은 구성의 `prod-db` EC2(`t3.medium`)를 둡니다(#302, #305). v2 prod 데이터를 dump로 옮긴 뒤 BE 스키마와 AI 마이그레이션을 따로 적용했고, v2 DB는 EBS 스냅샷으로 보관한 뒤 삭제했습니다(#321). |
> > | PostgreSQL | 각 환경의 MySQL과 같은 DB EC2에서 별도 엔진으로 실행합니다. AI API는 같은 환경의 PostgreSQL에 연결하고, 엔진별 계정과 데이터 경로를 구분합니다. |
> > | Redis | dev, stage, prod Namespace에 각각 단일 Pod와 전용 PVC를 배치합니다. Refresh Token과 회전, 폐기 상태, AI 작업 상태 등 재기동 후에도 유지할 데이터를 AOF로 기록합니다. v2 Redis의 데이터는 옮기지 않았습니다. 운영 정책은 5.5절을 적용합니다. |
> > | Kafka | Strimzi 기반 환경별 Kafka 클러스터를 운영합니다. dev는 단일 Pod와 10Gi PVC, stage, prod는 Pod 3개와 Pod마다 10Gi PVC를 사용합니다. 환경마다 bootstrap 주소, cluster ID, Topic, Consumer Group, offset과 KRaft 메타데이터를 분리합니다(4.5절). |
> >
> > - Redis 재시작과 Pod 재생성 시 같은 PVC의 AOF로 상태를 복원합니다. 단일 Pod의 복구 중단, 장애 직전 쓰기와 볼륨 손실에 따른 데이터 유실 가능성은 남습니다.
> >
> > - DB, Redis의 실행 위치 선택은 [데이터 계층 근거](v3%20인프라%20설계%20의사결정%20근거.md#25-데이터-배치)에 정리했습니다.

## 3. EKS 클러스터와 Worker Node
>
> ### 3.1 플랫폼과 클러스터 범위
> >
> > | 환경 | 플랫폼 | 리전 | 클러스터 수 | 관리 범위 |
> > |---|---|---|---|---|
> > | AWS 주 운영 | EKS `dameokja-v3`, Kubernetes 1.35 | 서울 `ap-northeast-2` | 1개 | Control Plane은 AWS가 관리하고, Cloud 팀은 Node, 워크로드, 공통 운영 구성을 관리합니다. |
> >
> > - 클러스터 인증은 API Access Entry를 사용합니다. 생성자의 암묵적 관리자 권한은 끄고, 지정한 관리자 principal과 Node 역할, stage 켜기, 끄기용 역할만 등록합니다.
> > - VPC CNI, kube-proxy, CoreDNS, EBS CSI Driver, Metrics Server는 고정 버전 add-on으로 별도 스택에서 관리합니다.
> > - EKS, kubeadm의 비교, 선택 이유는 [플랫폼 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#31-플랫폼과-클러스터-범위)에 정리했습니다.

> ### 3.2 Worker Node 운영 구조
> >
> > **앱 Node**: Karpenter를 직접 설치하여 ASG 없이 환경별 NodePool로 Node를 공급, 정리합니다.
> >
> > **시스템용 Node**: Self-managed EC2 한 대를 상시 운영하고, 관리 도구와 클러스터 공통 구성요소를 실행합니다.
> >
> > | 관리 대상 | 운영 방향 |
> > |---|---|
> > | 시스템용 Node | ASG 없이 EC2 한 대(`dameokja-v3-system-node` 스택)를 운영합니다. 라벨 `dameokja.com/node-role=system`, taint `dameokja.com/system=true:NoSchedule`을 둡니다. 초기화, 클러스터 등록, 업데이트와 장애 시 인스턴스 복구, 교체는 Cloud 팀이 직접 수행합니다. |
> > | 시스템용 Node의 구성요소 | `tool`: Karpenter, Argo CD, Sealed Secrets Controller, Strimzi Cluster Operator, AWS Load Balancer Controller, kube-state-metrics, 이벤트 수집 Alloy. `kube-system`: CoreDNS 1개, EBS CSI Controller, Metrics Server. 각 환경 Kafka의 Topic Operator도 이 Node에 둡니다. 모두 Replica 1개입니다. |
> > | 기본 대수, 사양, OS | 시스템용 Node는 EC2 1대이며, 사양은 `m7i.large`, OS는 Amazon Linux 2023입니다. 앱 Node도 같은 사양, OS를 사용합니다. |
> > | Node AMI | EKS용 AL2023 AMI(`amazon-eks-node-al2023-x86_64-standard-1.35-v20261031`)를 ID로 고정하고, 실행 때마다 recommended를 따라가지 않습니다. 시스템용 Node와 앱 Node가 같은 AMI를 씁니다. |
> > | Node 설정 | AL2023 nodeadm UserData, IMDSv2 필수, 암호화된 gp3 루트 볼륨을 사용합니다. 루트 디스크는 종료 시 삭제되므로 업무 데이터의 유일한 사본을 두지 않습니다. |
> > | 도구 버전 | Karpenter 1.15.1, Strimzi 1.3.0(Kafka 4.2.2), Sealed Secrets 차트 2.22.0, Argo CD 차트 10.11.6, AWS Load Balancer Controller 3.6.2, Gateway API CRD 1.6.0, kube-state-metrics 9.0.0, Alloy 1.15.0입니다. Controller와 CRD의 버전, 적용 시점 및 롤백은 직접 관리합니다. |
> > | 운영 책임 | Cloud 팀이 AMI, 보안 패치, Node 복구와 Controller 로그, 메트릭, EC2 진단을 관리합니다. |
> >
> > - 시스템용 Node가 멈추면 CoreDNS도 함께 멈추므로 클러스터 DNS가 중단됩니다. 복구 자동화는 [고도화 계획 11절](v3%20인프라%20고도화%20계획.md#11-시스템용-node-복구-자동화)에서 다룹니다.
> >
> > [Node 운영 근거](v3%20인프라%20설계%20의사결정%20근거.md#32-worker-node-운영-구조)를 별도로 관리합니다.

> ### 3.3 애플리케이션용 NodePool
> >
> > 앱 Node는 환경마다 별도 NodePool로 나눕니다. stage를 끌 때 stage Node만 0대로 줄이기 위해 dev와 나누었고(#258, #259), prod도 stage와 같은 사양으로 나누었습니다(#304).
> >
> > | NodePool | 받는 Pod | 물리 자원 상한 | 정리 정책 |
> > |---|---|---|---|
> > | `dev-app` | 라벨 `dameokja.com/node-role=app`, taint 없음. dev의 FE, BE, AI API, Redis, Kafka | CPU 26 vCPU, 메모리 104Gi | `WhenEmptyOrUnderutilized` |
> > | `stage-app` | 라벨 `dameokja.com/environment=stage`와 같은 이름의 `NoSchedule` taint. 같은 nodeSelector, toleration을 둔 stage Pod만 받음 | CPU 16 vCPU, 메모리 64Gi | `WhenEmpty` |
> > | `prod-app` | 라벨, taint `dameokja.com/environment=prod`. prod Pod만 받음 | CPU 16 vCPU, 메모리 64Gi | `WhenEmpty` |
> >
> > | 항목 | 구성 |
> > |---|---|
> > | 공통 조건 | 세 NodePool 모두 `m7i.large`, `ap-northeast-2b`, On-Demand, 같은 AMI와 Node SG를 사용하고 `expireAfter: Never`로 수명 만료 교체를 끕니다. |
> > | GPU 실행 | AI 모델의 GPU 실행은 외부 RunPod가 담당합니다. |
> > | Kafka 배치 | dev의 단일 Kafka Pod는 `dev-app`에 둡니다. stage, prod의 Kafka Pod 3개는 필수 anti-affinity로 해당 환경 Node마다 1개씩 놓이므로 stage, prod는 Node가 각각 3대 이상입니다. |
> > | 상한의 의미 | 상한은 상시 실행 대수가 아니며, Pending Pod가 있을 때만 Karpenter가 Node를 만듭니다. stage, prod 상한은 평시 Pod와 Kafka 3개에 HTTP Blue/Green 여유를 둔 값입니다. |

> ### 4.3 Pod 구성
> >
> > #### 4.3.1 배포 단위
> > >
> > > FE, BE, AI API는 각각 별도 Pod로 배포합니다. 이미지는 GHCR의 `image@sha256` digest로만 지정하며 태그는 받지 않습니다.
> > >
> > #### 4.3.2 공통 기능
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | Sidecar | nginx와 로그 수집용 Sidecar는 추가하지 않으며, 외부 라우팅은 ALB가, 로그 수집은 Node별 Alloy DaemonSet이 담당합니다. |
> > > | 실행 사용자 | 컨테이너는 일반 사용자로 실행합니다. FE는 이미지의 `node`(1000), BE, AI API는 10001을 씁니다. AI 이미지의 `/app`은 root 소유이므로 AI 로그는 `/tmp`(emptyDir)에 씁니다. |
> > > | 환경별 주소 | 클러스터 안에서 주소가 정해지는 값(`AI_BASE_URL`, `SPRING_DATA_REDIS_*`, `CALLBACK_URL`, `KAFKA_BOOTSTRAP_SERVERS` 등)은 Secret에서 빼고 환경 값의 env로 둡니다. |
> > > | 이미지 받기 | 각 Namespace의 `ghcr-pull` Secret으로 비공개 GHCR 패키지를 받습니다. |
> > > | 종료 대기 | `terminationGracePeriodSeconds`는 앱 60초, Kafka 120초입니다. |
> > >
> > #### 4.3.3 AI API 연동
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 작업 연동 | BE가 같은 Namespace의 `ai-api` ClusterIP Service에 HTTP로 요청하고, AI API는 BE 내부 콜백으로 결과를 돌려줍니다. |
> > > | 모델 호출 | RunPod는 EKS 외부의 모델 서빙 환경이며, 각 AI API Pod에서 HTTPS로 호출합니다. |
> > > | 호출 설정 | RunPod 호출 주소와 인증 정보는 환경별 `ai-secrets`로 공급합니다. |
> > > | Kafka 연결 | 환경별 AI 토픽과 `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_ENV`, `KAFKA_ENABLED` 설정은 미리 넣어 두었습니다. 지금 AI 이미지는 이 값을 읽지 않으며, AI 저장소의 Kafka 코드가 병합되면 바로 연결됩니다. 알림과 요리 기록 등 BE의 Consumer는 이미 Kafka를 사용합니다. |
> > >
> > #### 4.3.4 Probe 기본 정책
> > >
> > > FE, BE, AI API, Redis의 컨테이너에 아래 정책을 적용하며 세 환경이 같은 값을 사용합니다. 기동 완료 전에는 Startup만 검사하고 성공한 뒤 Readiness, Liveness를 실행합니다.
> > >
> > > | 대상 | Startup 검사 | 기동 예산, 실패 횟수 | Readiness 검사 | Liveness 검사 |
> > > |---|---|---|---|---|
> > > | FE | TCP `3000` | 약 2분, 12회 | TCP `3000` | TCP `3000` |
> > > | BE | HTTP `8080/actuator/health/readiness` | 약 5분, 30회 | HTTP `8080/actuator/health/readiness` | HTTP `8080/actuator/health/liveness` |
> > > | AI API | HTTP `8000/health/live` | 약 3분, 18회 | HTTP `8000/health/live` | HTTP `8000/health/live` |
> > > | Redis | exec로 로컬 `PING`의 `PONG` 응답 확인 | 약 10분, 60회 | exec로 `PONG` 확인 | exec로 `PONG` 확인 |
> > >
> > > | 공통 설정 | Startup | Readiness | Liveness |
> > > |---|---|---|---|
> > > | `periodSeconds` | 10 | 5 | 10 |
> > > | `timeoutSeconds` | 3 | 3 | 3 |
> > > | `failureThreshold` | 대상별 기동 예산 적용 | 3 | 6 |
> > > | `successThreshold` | 1 | 1 | 1 |
> > > | 실패 후 동작 | 허용 횟수 초과 시 컨테이너 재시작 | Service의 요청 전달 대상에서 제외 | 연속 실패 허용 횟수 초과 시 컨테이너 재시작 |
> > >
> > > `initialDelaySeconds`는 0으로 두고 Startup으로 기동을 보호합니다. 기동 예산은 `periodSeconds × failureThreshold` 기준입니다.
> > >
> > > | 적용 기준 | 구성 |
> > > |---|---|
> > > | 외부 의존성과 재시작 구분 | BE, AI API의 Liveness는 컨테이너 자체의 응답만 확인하고 DB, Redis, Kafka, RunPod의 일시 장애를 재시작 조건으로 사용하지 않습니다. |
> > > | BE 검사 범위 | Spring Boot가 Kubernetes 안에서 켜는 Actuator Readiness, Liveness 그룹을 주 서비스 포트 8080에서 확인합니다. 외부 의존성을 포함하는 전체 `/actuator/health`를 Liveness에 사용하지 않습니다. |
> > > | AI API 검사 연결 | Readiness도 프로세스 생존(`/health/live`)만 확인합니다. `/health/ready`는 RunPod Worker가 꺼져 있으면 503을 돌려주어, 이를 쓰면 Pod가 Service에서 계속 빠지기 때문입니다(#230). |
> > > | Redis 검사 연결 | 인증 정보는 Secret에서 공급하고 `redis-cli`의 종료 코드뿐 아니라 `PONG` 응답을 확인합니다. AOF 복원 중에는 Startup으로 보호하고, 복원이 끝나 요청을 받을 수 있을 때 준비 완료로 판정합니다. |
> > > | ALB 헬스 체크 | Target Group 헬스 체크는 FE `/manifest.webmanifest`, BE `/actuator/health/readiness`입니다. FE의 `/`는 로그인하지 않은 요청을 307로 넘기므로 unhealthy가 되어 redirect 대상에서 빠지는 manifest를 씁니다(#233). |
> > > | 적용 대상 구분 | MySQL, PostgreSQL과 관측 서버는 EKS 외부 EC2이므로 이 컨테이너 Probe의 적용 대상에 포함하지 않습니다. Kafka는 Strimzi가 관리하는 Probe를 사용하고, 관리 도구는 공식 Helm Chart가 제공하는 Probe를 사용합니다. |
> > >
> > > [Probe 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#probe-기본-정책)

> >
> > #### 4.4.1 Controller 운영
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 설치, 권한 | Controller는 Helm으로 설치하고 전용 ServiceAccount에 IAM Role을 연결합니다. 권한은 v3 ALB로 좁혀 같은 계정의 다른 ALB에 닿지 않게 합니다(#232). |
> > > | GatewayClass, ALB | GatewayClass의 `controllerName`은 `gateway.k8s.aws/alb`, LoadBalancerConfiguration의 `scheme`은 `internal`, 이름은 `dameokja-v3-gateway`로 설정하며 ALB는 2개 AZ의 Private Subnet에 배치합니다. |
> > > | SG 관리 | ALB SG는 CloudFormation이 소유하고 Controller에는 지정만 합니다(`manageBackendSecurityGroupRules: false`). SG를 IaC가 관리하도록 Controller에 SG 생성, Pod SG 규칙 변경 권한을 주지 않습니다(#232). |
> > > | Target Group | Pod IP를 대상으로 하며, 헬스 체크 경로는 앱별 `TargetGroupConfiguration`으로 지정합니다. |
> > > | 버전 관리 | Controller 3.6.2, Gateway API CRD 1.6.0을 직접 관리합니다. |
> > >
> > #### 4.4.2 도메인, 라우팅
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | DNS | Route 53에서 세 도메인을 같은 CloudFront 배포로 연결합니다. `dev.dameokja.com`, `dameokja.com`은 가중치 레코드(SetIdentifier `v3`, 가중치 100)이고, `stage.dameokja.com`은 단순 별칭 레코드입니다. |
> > > | 운영 전환 | v2에서 v3로의 전환은 가중치 레코드로 v3를 0에서 100으로 올려 진행했습니다. 가중치 0 상태에서 CloudFront 주소로 사전 시험을 하고 되돌릴 경로를 남기기 위해서입니다(#237, #315). |
> > > | Service 선택 | CloudFront는 Host, 경로를 전달하고 각 Namespace의 HTTPRoute가 FE, BE Service를 선택합니다. |
> > > | Namespace 연결 | 각 Route는 `tool` Namespace의 공용 Gateway(HTTP 80)에 연결하며, Gateway의 `allowedRoutes`는 `dameokja.com/gateway-access: 'true'` 라벨이 있는 Namespace만 허용합니다. |
> > > | 호스트 제한 | Route의 `hostnames`는 해당 환경의 도메인으로 한정하고 일치하지 않는 요청은 거부합니다. |
> > > | ALB 접근 제한 | ALB SG는 CloudFront origin-facing prefix list에서 오는 TCP 80만 받으므로 VPC 밖에서 ALB로 직접 들어올 수 없습니다. |
> > >
> > #### 4.4.3 HTTPS, 인증서
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | HTTPS 종료 | 사용자 HTTPS는 CloudFront에서 종료합니다. HTTP 요청은 HTTPS로 넘기고, 최소 프로토콜은 `TLSv1.2_2021`입니다. |
> > > | 인증서 발급, 갱신 | ACM 인증서는 `us-east-1`에서 발급하고 Route 53 DNS 검증, 자동 갱신을 사용합니다(`edge-cert` 스택). |
> > > | 인증서 도메인 | 공용 배포의 인증서는 `dev.dameokja.com`, `stage.dameokja.com`, `dameokja.com`을 모두 포함합니다. 이전 단계의 dev, dev·stage 인증서는 남겨 둡니다. 교체하며 지우면 같은 검증 CNAME이 함께 지워질 위험이 있기 때문입니다(#270, #303). |
> > > | 내부 통신 | VPC Origin은 `http-only`, Gateway는 HTTP Listener를 사용하며 ALB→Pod도 HTTP로 연결합니다. |
> > >
> > #### 4.4.4 이미지, 캐시
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | CloudFront 캐시 | 캐시는 끄고(`Managed-CachingDisabled`) Host, 쿠키, Authorization, 쿼리 문자열을 모두 오리진에 전달합니다(`Managed-AllViewer`). |
> > > | 이미지 경로 | 이미지는 BE가 발급한 presigned URL로 브라우저가 S3에 직접 올리고 받으므로, CloudFront에 S3 오리진과 OAC를 두지 않습니다(#233). |
> > > | S3 접근 | 버킷은 비공개로 두고, BE, AI API의 IRSA 역할에 환경별 접두사(dev `image/`, stage `image/stage/`, prod `image/prod/`)의 권한만 줍니다. prod는 v2 prod와 같은 객체를 씁니다. |
> > > | 배포 등급 | 한국을 포함하는 가장 작은 등급인 `PriceClass_200`을 사용합니다. |
> > >
> > > 공용 CloudFront, ALB 설정 변경의 영향은 세 환경이 함께 받습니다.

> ### 4.5 Kafka 연동
> >
> > Kafka는 MSK 대신 Strimzi 기반으로 직접 운영하며, 환경마다 Kafka 클러스터, bootstrap 주소와 영속 볼륨을 분리합니다. dev는 단일 구성, stage, prod는 Broker, Controller 겸용 Pod 3개 구성입니다.
> >
> > | 운영 항목 | 구성 |
> > |---|---|
> > | 관리 방식 | Strimzi Cluster Operator는 `tool` Namespace의 시스템용 Node에서 실행하고 dev, stage, prod Namespace를 감시합니다. Kafka와 KafkaNodePool, KafkaTopic 리소스는 환경별 데이터 차트(`v3/charts/<환경>-data`)로 Helm 설치하고, 실제 Pod, Service와 PVC는 Strimzi가 조정합니다. Kafka와 Topic 리소스에는 `Prune=false`를 두어 Argo CD가 지우지 않게 합니다. |
> > | 버전, 역할 | Strimzi `1.3.0`과 Kafka `4.2.2` 이미지를 digest로 고정합니다. KRaft 모드로 각 Pod가 Broker, Controller를 겸하며 ZooKeeper는 사용하지 않습니다. |
> > | dev 구성 | `dev` Namespace의 Kafka Pod 1개. CPU request `250m`, limit `2`, 메모리 request와 limit `2Gi`. 토픽 파티션, 복제 수, offsets 내부 토픽 복제 수와 `min.insync.replicas`는 1입니다. |
> > | stage, prod 구성 | Pod 3개를 필수 anti-affinity로 해당 환경 Node마다 1개씩 두고 모두 `ap-northeast-2b`에 놓입니다. 복제 수 3, `min.insync.replicas` 2, 파티션 3이며 Pod마다 CPU request `500m`, limit `2`, 메모리 `2Gi`, JVM Heap `512m`~`1g`입니다. stage가 prod와 같은 검증 환경이므로 같은 구성을 씁니다(#260). |
> > | 영속 저장 | 환경별 Pod마다 `kafka-gp3`(암호화 gp3) PVC `10Gi`를 사용합니다. `deleteClaim: false`, StorageClass `reclaimPolicy: Retain`으로 Pod와 클러스터 재생성 시 기존 메시지, KRaft 메타데이터, offset을 보존합니다. |
> > | 메시지 보관 | 업무 토픽은 `cleanup.policy: delete`, `retention.ms: 2592000000`으로 30일 보관합니다. PVC 용량이 10Gi이므로 30일치 데이터가 항상 수용되는 것은 아니며, 디스크 사용량을 확인하여 용량을 조정합니다. |
> > | 접속, 보안 | 환경별 내부 bootstrap Service(`<환경>-kafka-kafka-bootstrap.<환경>.svc.cluster.local:9092`)로 접속하며 클라이언트 연결은 PLAINTEXT를 사용합니다. 외부 listener는 없습니다. TLS, SASL 클라이언트 인증은 추가하지 않고, SG와 NetworkPolicy로 같은 환경의 BE, AI API Pod만 허용합니다. |
> > | 토픽 | 자동 생성을 끄고 `<환경>.dameokja.` 접두사를 사용합니다. 공통 7개(`refrigerator.events.v1`, `push.dispatch.v1`, `analysis.requested.v1`, `analysis.completed.v1`, `analysis.feedback.v1`, `recommendation.requested.v1`, `recommendation.completed.v1`)에 BE가 쓰는 DLT 2개와 `cooking.applied.v1`을 더하고, dev, prod는 `inventory.expiration-check.requested.v1`도 둡니다. dev, prod 11개, stage 10개입니다. 자동 생성을 꺼 두었으므로 BE가 쓰는 토픽을 미리 만듭니다(#241, #287, #318, #320). |
> > | 장애 수용 범위 | dev는 단일 Pod 장애, 재시작 시 복구까지 Kafka 이용이 중단됩니다. stage, prod는 Pod 1개가 내려가도 `acks=all` 쓰기와 읽기가 계속됩니다. 모든 Pod가 단일 AZ에 있으므로 AZ 장애는 대비하지 않습니다. |
> > | 환경별 소비 | `KAFKA_BOOTSTRAP_SERVERS`, `KAFKA_ENV`로 환경별 주소와 토픽 접두사를 주입하고 같은 환경의 Topic만 구독합니다. 다른 환경의 broker 연결은 허용하지 않습니다. |
> >
> > | 항목 | 구성 |
> > |---|---|
> > | BE 사용 | BE는 `KAFKA_LISTENER_ENABLED`로 Consumer를 켭니다. dev, prod는 만료 알림의 Kafka 경로(`NOTIFICATION_EXPIRATION_KAFKA_ENABLED`)도 켜고, dev는 요리 기록 발행(`COOKING_KAFKA_PUBLISH_ENABLED`)도 켭니다. |
> > | 알림 실패, 저장 | 알림 실패 시 참여는 유지하고 알림만 재처리하며, 참여, 재고, 완성된 알림은 DB에 저장합니다. |
> > | AI 요청, 결과 | `analysis.*`, `recommendation.*` 토픽은 환경별로 만들어 두었습니다. AI 이미지가 Kafka를 읽기 전까지 AI 요청과 결과는 HTTP 요청, 콜백으로 주고받습니다(4.3.3절). |
> > | 순서, 작업 분담 | 같은 냉장고의 이벤트는 냉장고 ID를 키로 같은 Topic, Partition에 전달하고 Consumer Group으로 분담합니다. |
> >
> > - Consumer별 동시 실행 한도, 누락, 중복, 재시도 제어는 애플리케이션 코드와 함께 정합니다. Kafka의 AZ 분산 등 고가용성은 [고도화 계획 10절](v3%20인프라%20고도화%20계획.md#10-kafka-고가용성과-kubernetes-운영)에서 다룹니다.
> >
> > [Kafka 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#45-kafka-연동)

## 5. 자원, 배치, 확장 정책
>
> - Pod의 자원을 기준으로 배치 가능 용량을 판단하고, 환경 값의 고정 Replica에 맞춰 Karpenter가 해당 환경 NodePool의 Node를 공급합니다.
>
> ### 5.1 Pod requests, limits
> >
> > - 애플리케이션, 데이터 컨테이너별 자원은 다음과 같습니다.
> >
> > | 대상 | CPU request | CPU limit | 메모리 request | 메모리 limit |
> > |---|---|---|---|---|
> > | FE | `250m` | `1` | `512Mi` | `1Gi` |
> > | 통합 BE, stage, prod | `500m` | `1` | `1Gi` | `2Gi` |
> > | 통합 BE, dev | `250m` | `1` | `1Gi` | `2Gi` |
> > | AI API | `250m` | `1` | `512Mi` | `1536Mi` |
> > | Redis | `250m` | `500m` | `512Mi` | `1Gi` |
> > | Kafka, dev | `250m` | `2` | `2Gi` | `2Gi` |
> > | Kafka, stage, prod, Pod마다 | `500m` | `2` | `2Gi` | `2Gi` |
> > | Topic Operator, 시스템용 Node | `50m` | `250m` | `128Mi` | `256Mi` |
> >
> > dev는 Node 1대에 모으기 위해 BE, Kafka의 CPU request를 `250m`으로 낮춥니다. dev의 CPU request 합계가 Node 한 대의 할당 가능량을 넘어 Node가 2대 떴지만 실사용은 낮았기 때문입니다(#279, #280). limit은 그대로라 필요하면 더 씁니다.
> >
> > #### 5.1.1 AI API 자원
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 실행 방식 | AI API는 Deployment의 Pod로 운영하고, 활성 버전은 dev, stage, prod 모두 1개를 고정 실행합니다. AI가 분석 결과를 메모리에 두므로 여러 개면 상태가 갈리기 때문입니다(#267). |
> > > | 메모리 | 메모리 limit은 v2 stage, prod의 AI 태스크 메모리 값을 따라 `1536Mi`로 둡니다. |
> > > | 배포 중 실행 | BE, AI API는 두 색상을 함께 띄우지 않습니다(6.3.2절). 배포 중에도 AI API Pod는 환경마다 1개를 넘지 않습니다. |
> > > | 내부 큐 | FastAPI 내부 큐는 유지하지만, 해당 큐만을 작업 보관 수단으로 삼지 않습니다. Kafka 소비 전환과 Pod 종료 후 미완료 작업 재처리는 AI 저장소의 Kafka 코드와 함께 적용합니다. |
> > > | 확장 | HPA는 적용하지 않았습니다. Kafka 연동과 작업 복구를 검증한 뒤 확장 지표, Replica 범위와 NodePool 용량을 함께 정합니다. |
> > >
> > #### 5.1.2 Node, BE 메모리
> > >
> > > `m7i.large`의 물리 자원은 CPU 2 vCPU, 메모리 8Gi이며, 실제 할당 가능 CPU는 약 1.93코어로 확인했습니다(#279). 모든 Node에는 Alloy DaemonSet이 함께 놓이므로 배치 가능 용량은 Node의 Allocatable과 DaemonSet requests를 함께 보고 판단합니다.
> > >
> > > BE의 JVM Heap은 메모리 limit 안에서 다른 JVM 메모리의 여유를 두며, Kafka 연동 후 합산 부하로 기동, 응답, OOM을 확인합니다.
> > >
> > > [초기 자원 산정 근거](v3%20인프라%20설계%20의사결정%20근거.md#51-pod-requests-limits)
> > >
> ### 5.2 시스템용, 앱 Node 배치
> >
> > | 항목 | 구성 |
> > |---|---|
> > | 실행 위치 | 관리 도구와 CoreDNS, EBS CSI Controller, Metrics Server, Topic Operator는 시스템용 Node에, 각 환경의 FE, BE, AI API, Redis, Kafka는 해당 환경 NodePool에 배치합니다. |
> > | Node 선택 | 시스템용 Node는 `dameokja.com/node-role=system` 라벨과 `dameokja.com/system=true:NoSchedule` taint로 일반 앱 Pod의 배치를 막습니다. dev Pod는 `dameokja.com/node-role: app`을, stage, prod Pod는 `dameokja.com/environment: <환경>` nodeSelector와 같은 이름의 toleration을 둡니다. |
> > | Pod별 설정 | 각 도구에는 해당 toleration을 설정하고, 컨테이너별 requests, limits와 도구별 ServiceAccount를 구성합니다. Alloy는 시스템용, stage, prod Node에도 놓이도록 toleration을 둡니다. |
> > | Node 교체 | 시스템용 EC2를 수동으로 교체, 재등록할 때도 같은 라벨, taint를 적용합니다. |
> >
> ### 5.3 FE, BE HPA와 Replica
> >
> > - FE, BE, AI API는 환경 값에 정한 Replica로 고정 실행합니다. FE, BE HPA는 아직 적용하지 않았으며, Metrics Server만 설치해 두었습니다. CPU 기반 HPA 도입은 [고도화 계획 2절](v3%20인프라%20고도화%20계획.md#2-자원-확장-정책-개선)에서 다룹니다.
> > - VPA도 사용하지 않습니다.
> >
> > [HPA 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#53-fe-be-hpa와-replica)를 별도로 관리합니다.
> >
> > #### 5.3.1 환경별 Replica와 운영 용량
> > >
> > > | 환경 | FE Replica | BE Replica | AI API Replica | Redis | Kafka | 앱 Node |
> > > |---|---:|---:|---:|---:|---:|---|
> > > | dev | 1 | 1 | 1 | 1 | 1 | 1대 |
> > > | stage | 2 | 2 | 1 | 1 | 3 | 켰을 때 3대 이상, 끄면 0대 |
> > > | prod | 2 | 2 | 1 | 1 | 3 | 3대 이상 |
> > >
> > > ##### 5.3.1.1 운영 용량 검토
> > > >
> > > > 아래는 5.1절의 자원값으로 계산한 환경별 requests, limits 합계입니다. 시스템용 Node의 관리 도구, Topic Operator와 Node마다 놓이는 Alloy, EKS 외부의 DB, 관측 EC2는 제외합니다.
> > > >
> > > > | 환경 | CPU requests | 메모리 requests | 메모리 limits | Node 수를 정하는 조건 |
> > > > |---|---:|---:|---:|---|
> > > > | dev | 1.25 vCPU | 4.5Gi | 7.5Gi | CPU requests가 Node 1대의 할당 가능량 안에 듭니다. |
> > > > | stage | 3.5 vCPU | 10Gi | 14.5Gi | Kafka Pod 3개가 Node마다 1개씩 놓여 최소 3대입니다. |
> > > > | prod | 3.5 vCPU | 10Gi | 14.5Gi | stage와 같습니다. |
> > > >
> > > > | 항목 | 구성 |
> > > > |---|---|
> > > > | requests, limits 기준 | 실제 스케줄링은 CPU, 메모리 requests를 기준으로 하며 용량 검토에서는 메모리 limits 합계도 함께 확인합니다. CPU limits 합계만큼의 동시 CPU 사용을 보장하는 구성은 아니므로 피크 응답 지연과 CPU 경합은 부하 시험으로 확인합니다. |
> > > > | 실제 Node 수 | 표의 값은 계산 기준입니다. 실제 Allocatable, DaemonSet, Pod ENI, PVC와 배치 조건에 따라 필요한 Node 수가 달라지면 자원값과 상한을 재검토합니다. |
> > > > | 시스템용 Node | `m7i.large` 1대를 별도로 유지하고, 관리 도구 requests 합계가 실제 가용 자원 안에 들어오는지 확인합니다. |
> > > > | Consumer 실행량 | BE 내부 Consumer, Batch의 부하도 같은 Pod에서 처리되므로 BE Replica를 늘릴 때는 전체 작업 실행량을 외부 서비스 한도에 맞춰 제어합니다. |
> > > >
> ### 5.4 Karpenter Node 확장, 정리
> >
> > - Karpenter는 배치할 수 없는 Pod의 자원, 조건에 맞춰 해당 환경 NodePool의 앱 Node를 공급합니다.
> > - BE 용량은 API, Batch, Consumer의 합산 부하로 검증하고, Kafka 용량은 이벤트량, 메시지 크기, 보관 기간, 복제 구성으로 별도 산정합니다.
> >
> > ```mermaid
> > flowchart TB
> >     replicas["환경 값의 Replica, Kafka Pod 수"] --> scheduler["Scheduler, Pod 배치"]
> >     scheduler --> capacity{"해당 환경 Node에 배치 가능?"}
> >     capacity -->|"가능"| running["Pod 실행, Readiness 확인"]
> >     capacity -->|"불가"| pending["Pod Pending, 미충족 자원, 배치 조건"]
> >
> >     subgraph systemNodes["시스템용 Node, EC2 1대 상시 운영"]
> >         karpenter["Karpenter Controller, 직접 운영"]
> >     end
> >
> >     pending --> karpenter
> >     karpenter -->|"환경 라벨, taint에 맞는 NodePool과 상한 확인"| nodeSupply["m7i.large 앱 Node 공급, 2b On-Demand"]
> >     nodeSupply -->|"Node 등록 후 재배치"| scheduler
> > ```
> >
> > - NodePool 상한에 시스템용 Node 1대는 포함하지 않습니다. 상한은 상시 실행 대수가 아니며 필요한 Node는 Karpenter가 공급합니다.
> > - 스토리지, 할당량, 배치 정책이 원인이면 Node를 추가해도 Pod는 Pending으로 남을 수 있습니다.
> >
> > 앱 NodePool의 정리, 교체 정책은 다음과 같습니다.
> >
> > | 항목 | 설정 | 동작 |
> > |---|---|---|
> > | 정리 대상, dev | `consolidationPolicy: WhenEmptyOrUnderutilized` | 빈 Node뿐 아니라 덜 찬 Node도 합쳐 dev를 1대로 모읍니다. dev CPU 요청을 낮춘 것과 함께 dev Node를 2대에서 1대로 줄여 월 약 $90을 줄였습니다(#279, #280). |
> > | 정리 대상, stage, prod | `consolidationPolicy: WhenEmpty` | 일반 앱 Pod가 없는 빈 Node만 정리합니다. stage를 끄면 빈 stage Node가 이 정책으로 0대가 됩니다. |
> > | 정리 대기 | `consolidateAfter: 5m` | Pod 추가, 제거 후 5분간 배치 변화가 없는 Node를 정리 대상으로 검토합니다. |
> > | 동시 정리, 교체 | `budgets`의 `nodes: "1"` | 자발적인 정리와 설정 변경에 따른 교체는 한 번에 한 대씩 진행합니다. |
> > | 수명 만료 | `expireAfter: Never` | 수명 만료에 의한 자동 교체는 하지 않습니다. |
> >
> > - EC2NodeClass의 태그와 AMI는 Karpenter drift 판단에 들어가므로, 바꾸면 해당 NodePool의 Node가 교체됩니다.
> > - 시스템용 EC2의 수동 교체와 앱 Node의 장애에 의한 종료는 별도로 관리합니다.
> >
> ### 5.5 Redis 운영
> >
> > #### 5.5.1 실행과 자원
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 실행 구성 | dev, stage, prod Namespace마다 `redis` StatefulSet을 Replica 1개로 운영합니다. 이미지는 `redis:8.6.4-alpine`을 digest로 고정합니다. 읽기 Replica와 HPA는 적용하지 않습니다. |
> > > | 접속 | StatefulSet의 식별자는 `redis-headless` Headless Service로 관리하고, BE는 별도의 `redis` ClusterIP Service에 TCP 6379로 접속합니다. 비밀번호는 `cloud-secrets`의 `REDIS_PASSWORD`로 공급합니다. |
> > > | AOF 정책 | v2 prod의 `appendonly yes`, `appendfsync everysec`를 유지합니다. `/data`에 전용 PVC를 마운트하고 AOF 파일을 기록합니다. |
> > > | 자원 관리 | CPU request `250m`, limit `500m`, 메모리 request `512Mi`, limit `1Gi`입니다. 사용량을 확인하여 수동 조정하며 자동 자원 조정은 적용하지 않습니다. |
> > > | 메모리 여유 | `maxmemory`는 `512mb`로 설정하여 메모리 limit `1Gi` 안에 AOF 처리, 클라이언트 버퍼, 내부 관리 메모리와 메모리 단편화에 대한 여유를 확보합니다. |
> > >
> > #### 5.5.2 영속 볼륨 공급과 복구
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 드라이버 | AWS EBS CSI Driver를 EKS add-on으로 설치하고 전용 IAM Role로 EBS 생성, 연결 권한을 부여합니다. |
> > > | StorageClass | `redis-gp3`를 사용합니다. `provisioner: ebs.csi.aws.com`, `type: gp3`, `encrypted: "true"`, `volumeBindingMode: WaitForFirstConsumer`, `allowVolumeExpansion: true`로 설정합니다. Kafka용 `kafka-gp3`도 같은 설정입니다. |
> > > | PVC 생성 | StatefulSet의 `volumeClaimTemplates`에 `data`를 정의하고, 환경별 `data-redis-0` PVC를 생성합니다. 각 PVC는 `redis-gp3`, ReadWriteOnce, 요청 용량 `10Gi`를 사용합니다. |
> > > | PV와 EBS 공급 | PVC를 사용하는 Pod의 배치 조건에 맞춰 EBS CSI Driver가 같은 AZ에 gp3 EBS와 PV를 동적으로 공급하고 PVC에 바인딩합니다. 환경별 EBS 한 개씩, 총 `30Gi`를 사용하며 PV를 수동으로 미리 만들지 않습니다. |
> > > | Pod 재생성 | StatefulSet은 기존 PVC를 재사용합니다. Node가 바뀌면 같은 AZ에서 기존 EBS의 연결 해제, 재연결을 거쳐 `/data`를 마운트하고 AOF 복원 후 요청을 받습니다. 특정 Node에 고정하지 않습니다. |
> > > | 데이터 보존 | StatefulSet의 PVC 보존 정책은 `whenDeleted: Retain`, `whenScaled: Retain`, StorageClass의 `reclaimPolicy`는 `Retain`으로 설정합니다. StatefulSet이나 PVC 삭제가 EBS 자동 삭제로 이어지지 않도록 하고, 환경 폐기 시 Cloud 팀이 남은 PV와 EBS를 확인해 정리합니다. stage를 끌 때도 PVC는 남습니다. |
> > > | 복구 범위 | 볼륨 재연결과 AOF 로딩 동안 해당 환경의 Redis는 중단될 수 있습니다. 볼륨 자체의 손실과 AZ 장애는 이 구성만으로 복구하지 않으며, Kafka도 Redis의 인증, 서비스 상태를 자동 복원하지 않습니다. |
> > >

> >
> > AWS IaC는 CloudFormation을 사용하며, 템플릿은 `infra/v3/cloudformation/`, 입력은 `infra/v3/params/`에 둡니다.

> > | 스택 간 값 전달 | EKS 스택이 만드는 endpoint, OIDC, 역할, SG는 Export와 ImportValue로 전달합니다. Export 길이 제한을 넘는 클러스터 CA는 SSM Parameter로 전달합니다. 재사용 VPC, Subnet은 ID로 참조합니다. |
> > | Kubernetes 구성 | 관리 도구, `v3/charts/platform`(NodePool, StorageClass, Gateway, NetworkPolicy, SecurityGroupPolicy), 환경별 데이터 차트는 관리자가 SSM 포트 포워딩을 연 상태에서 Helm으로 설치합니다. 애플리케이션과 SealedSecret은 6.3절의 Argo CD 범위입니다. |
> > | Controller 관리 범위 | Karpenter가 공급하는 앱 Node, AWS Load Balancer Controller가 구성하는 ALB, Strimzi가 조정하는 Kafka 자원과 EBS CSI Driver가 PVC에 따라 공급하는 Redis, Kafka용 EBS는 각 Controller의 관리 범위로 구분합니다. |
> > | 인프라 변경 절차 | PR에서는 `cfn-lint`만 실행합니다. 병합 뒤 main에서 수동 Workflow(`infra-v3-cfn.yml`)를 plan으로 실행해 Change Set의 생성, 수정, 삭제, 교체 대상을 확인하고, 같은 스택을 apply로 실행하면 가장 최근 plan의 Change Set을 그대로 적용합니다. |
> > | 적용 승인 | apply에 GitHub Environment 승인 단계는 아직 두지 않았습니다([고도화 계획 5.1](v3%20인프라%20고도화%20계획.md#51-iac-전환과-적용-절차)). |

> >     mainBranch --> changeSet["수동 Workflow plan, Change Set 검토"]

> ### 6.2 CI와 이미지 공급
> >
> > - FE, BE, AI 저장소의 GitHub Actions가 검증, 빌드하고 GHCR에 이미지를 발행합니다. 기존 Workflow, 빌드 명령, Dockerfile을 활용합니다.
> > - 앱 CI는 이미지를 발행한 뒤 `CLOUD_DISPATCH_TOKEN`으로 CLOUD 저장소의 이미지 반영 Workflow를 실행합니다. CLOUD Workflow는 `ubuntu-24.04` GitHub-hosted runner에서 실행합니다.
> > - GHCR 패키지는 비공개로 두고, EKS는 각 Namespace의 `ghcr-pull` Secret으로 이미지를 받습니다.
> >
> > | Workflow | 역할 |
> > |---|---|
> > | `v3-dev-image.yml` | `v3/environments/dev/<앱>.yaml`의 활성 색상 이미지를 바꿔 main에 커밋합니다. |
> > | `v3-stage-image.yml` | 같은 방식으로 stage 값을 커밋합니다. 실행 이름에 요청 저장소, 실행 ID, 이미지를 넣어 prod 승인에서 짝을 맞춥니다. |
> > | `prod-approval.yml` | 같은 이미지의 stage 반영 실행이 성공했는지 확인한 뒤 prod 반영을 호출합니다. |
> > | `v3-prod-image.yml` | GitHub Environment `prod` 승인을 받은 뒤 prod 값을 커밋합니다. |

> ### 6.3 CD: Helm, Argo CD와 Blue/Green
> >
> > #### 6.3.1 GitOps 구성
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 배포 정의 | 공통 Helm Chart `v3/charts/application`과 환경별 Values를 CLOUD 저장소에서 관리하고 Argo CD로 배포, 동기화합니다. Application 정의는 `v3/argocd/`에 둡니다. |
> > > | 이미지 버전 반영 | GitHub runner는 사설 EKS API에 닿지 않으므로, Workflow는 이미지 값을 main에 커밋만 하고 Argo CD가 그 커밋을 가져갑니다(#306). |
> > > | Application 구성 | 환경마다 `<환경>-secrets`, `<환경>-fe`, `<환경>-be`, `<환경>-ai-api` Application을 둡니다. AppProject는 해당 Namespace의 Deployment, Service, ConfigMap, ServiceAccount, SealedSecret, HTTPRoute, TargetGroupConfiguration만 허용합니다. |
> > > | 동기화 정책 | dev 앱은 자동 동기화(prune), stage는 수동 동기화, prod는 Secret 수동, 앱 자동(prune, selfHeal 끔)입니다. Secret Application은 모든 환경에서 수동이며 앱보다 먼저 동기화합니다. `FailOnSharedResource`로 다른 Application이나 Helm이 만든 자원을 덮어쓰지 않습니다. |
> > > | Argo CD 배치 | `tool` Namespace의 Pod로 시스템용 Node에서 실행합니다. ApplicationSet, Dex, Notifications는 끕니다. |
> > > | 관리 UI | 관리자가 port-forward로만 접속합니다. 관리용 도메인 연결은 아직 적용하지 않았습니다. |
> > > | 로그인 인증 | Argo CD의 기본 로컬 계정으로 인증합니다. Cloud 팀이 계정을 관리하고 익명 접근은 비활성화합니다. |
> > > | 로그인 후 권한 | 기본 정책은 `role:readonly`이며, Kubernetes 직접 접근 권한과 구분해 관리합니다. |
> > >
> > #### 6.3.2 Blue/Green 배포
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 배포 단위 | FE, BE, AI API는 각각 Blue, Green Deployment와 운영 Service `<앱>`, 색상별 Service `<앱>-blue`, `<앱>-green`을 구성합니다. 운영 Service는 `activeColor`의 Pod를 가리킵니다. |
> > > | 버전 반영 | 이미지 반영 Workflow는 활성 색상의 이미지를 바꿉니다. Deployment 전략은 `Recreate`로, 기존 Pod를 내린 뒤 새 Pod를 띄웁니다. |
> > > | 동시 실행 제한 | BE, AI API는 두 색상을 동시에 실행하지 않습니다(`allowConcurrentConsumers: false`면 Chart가 거부). 같은 Kafka Consumer와 메모리 작업 큐가 두 벌 떠서 작업을 중복 처리하지 않게 하기 위해서입니다. |
> > > | 색상 전환 | 운영 Service selector를 새 색상으로 바꾸는 전환은 Kafka 동시 소비 안전성을 확인한 뒤로 미룹니다([고도화 계획 5.2](v3%20인프라%20고도화%20계획.md#52-kafka-consumer의-bluegreen-전환)). |
> > > | 실패 대응 | 새 Pod는 Readiness를 통과해야 Service 대상에 들어갑니다. 되돌릴 때는 환경 값의 이미지를 이전 digest로 바꿔 커밋하고 동기화합니다. |
> > > | 추가 Controller | 별도 Rollouts Controller를 사용하지 않습니다. |
> > > | 배치 작업 | BE의 정기 Batch는 기존 ShedLock으로 중복 실행을 제어합니다. |
> > >
> > > ```mermaid
> > > flowchart TB
> > >     sourceGit["FE, BE, AI 저장소"] --> ci["GitHub Actions, 검증, 이미지 빌드"]
> > >     ci -->|"이미지 발행"| ghcr["GHCR, 비공개 패키지"]
> > >     ci -->|"v3-dev-image, v3-stage-image"| deployGit["CLOUD main, 환경별 Values"]
> > >     ci -->|"prod-approval, stage 성공 확인"| prodGate["GitHub Environment prod 승인"]
> > >     prodGate -->|"v3-prod-image"| deployGit
> > >     deployGit --> argo["Argo CD, tool Namespace, 시스템용 Node"]
> > >     argo -->|"dev 자동, stage 수동, prod 앱 자동"| eksWorkloads["EKS, dev, stage, prod"]
> > >     ghcr -.->|"ghcr-pull Secret"| eksWorkloads
> > > ```

> > #### 6.3.3 stage 켜기, 끄기
> > >
> > > stage는 비용 때문에 쓸 때만 켭니다(#272, #273). main에서 `v3-stage-power.yml`을 `start` 또는 `stop`으로 실행합니다.
> > >
> > > | 항목 | 구성 |
> > > |---|---|
> > > | 실행 경로 | GitHub runner는 사설 EKS API에 닿지 않으므로 SSM으로 시스템용 Node에서 `v3/environments/stage/power.sh`를 실행합니다. 스크립트는 stage Namespace의 `stage-power` Role만 가진 kubectl 역할을 씁니다. DB EC2는 Workflow가 시작, 중지합니다. |
> > > | 끄기 | 앱 0 → Kafka 조정 일시정지(`strimzi.io/pause-reconciliation`), StrimziPodSet 삭제 → Redis 0 → DB 중지. PVC는 남고, 빈 stage Node는 Karpenter가 5분 뒤 지웁니다. |
> > > | 켜기 | DB 시작 → Redis 1 → Kafka 조정 재개 → Argo stage 앱 sync → FE 2, BE 2, AI 1 |
> > > | 꺼진 동안 | 반영된 stage 이미지는 다음 켜기 때 적용됩니다. Argo의 stage 앱은 OutOfSync로 보이며, 수동 동기화이므로 되돌리지 않습니다. |

> > > Argo CD 배포 권한은 Kubernetes 직접 접근 권한과 구분합니다. stage 켜기, 끄기에 쓰는 `stage-power` Role은 stage의 Deployment, StatefulSet scale, Kafka 조정 annotation, StrimziPodSet 삭제, Pod 조회만 허용합니다.

> ### 7.2 Secret 구분과 공급
> >
> > | 항목 | 구성 |
> > |---|---|
> > | Secret 이름 | 환경마다 `fe-secrets`, `be-secrets`, `ai-secrets`, `cloud-secrets`(Redis 비밀번호), `ghcr-pull`(GHCR 인증) 5개를 둡니다. |
> > | 원본 값 | 앱 Secret은 환경별 SSM 경로(dev `/dameokja-v3-dev`, `-ai`, `-fe`, stage `/dameokja-v3-stage*`, prod `/dameokja-v2-prod*`)에서, `ghcr-pull`은 Secrets Manager에서 읽습니다. 클러스터 주소에 따라 바뀌는 키는 Secret에서 빼고 Values의 env로 둡니다. |
> > | 봉인, 커밋 | 팀은 SSM 값만 바꾸고, 관리자가 환경별 `seal-secrets.sh`로 값을 읽어 SealedSecret을 만든 뒤 `v3/environments/<환경>/secrets/*.yaml`만 커밋합니다. 스크립트는 값을 화면에 출력하지 않고 평문 임시 파일을 지웁니다. |
> > | Git 보관 | Git에는 Sealed Secrets의 공개키(`v3/platform/sealed-secrets-cert.pem`)로 암호화한 SealedSecret을 보관합니다. |
> > | 암호화 범위 | 이름, Namespace에 결합되는 기본 `strict` 범위를 사용합니다. |
> > | 반영 | Argo CD의 `<환경>-secrets` Application을 수동 동기화하면 Controller가 Secret을 만들거나 갱신합니다. |

## 8. 관측: Prometheus, Loki, Grafana
>
> - Prometheus, Loki, Grafana는 EKS 외부의 관측 EC2(`t3.medium`, 시스템용 Node와 같은 Private Subnet)에 docker compose로 배치합니다.
> - 수집은 클러스터 안의 Alloy가 맡아 관측 EC2로 보냅니다. 관측 EC2에 클러스터 자격 증명이 필요 없고, 관측 EC2에서 Node, Pod로 들어오는 10250, 8080 수신을 열지 않아도 되기 때문입니다(#246).
> - 관측 서버의 OS, 프로세스, 스토리지, 복구는 직접 관리합니다.
>
> | 구성요소 | 역할 |
> |---|---|
> | Grafana Alloy | 모든 Worker Node에 DaemonSet Pod 1개를 두어, 자기 Node의 Pod 로그(`/var/log/pods`)를 Loki로, 자기 Node의 kubelet, cAdvisor와 같은 Node의 kube-state-metrics, BE(`/actuator/prometheus`) 메트릭을 Prometheus remote-write로 보냅니다. Node별로 나눠 수집하여 같은 대상을 중복 수집하지 않습니다. |
> | 이벤트 수집 Alloy | Kubernetes 이벤트는 단일 Alloy가 읽어 Loki로 보냅니다. DaemonSet에서 읽으면 Node 수만큼 중복되기 때문입니다. |
> | kube-state-metrics | 클러스터 객체 상태 메트릭을 제공합니다. |
> | Prometheus | Alloy가 remote-write로 보낸 메트릭을 저장합니다. 보존 기간은 15일입니다. |
> | Loki | Alloy가 전달한 로그와 이벤트를 저장, 조회합니다. 보존 기간은 7일입니다. |
> | Grafana | 관측 EC2의 Prometheus, Loki에 연결하여 메트릭, 로그를 조회합니다. |
>
> ```mermaid

> | Grafana 접속 | 팀이 SSM 포트 포워딩 없이 보도록 `grafana.dameokja.com`(전용 CloudFront → VPC Origin → 관측 EC2 3000)으로 엽니다(#288, #289, #296). 관측 SG는 CloudFront prefix list에서 오는 3000만 받습니다. |
> | Grafana 로그인 | GitHub OAuth만 허용하고 비밀번호 로그인과 API Basic 인증은 끕니다. 허용 목록의 GitHub 아이디만 첫 로그인 때 자동 가입되고, 역할은 로그인할 때마다 목록대로 맞춰집니다. 목록 변경은 `observability.yaml`을 고쳐 apply합니다. |
> | 설정, 대시보드 | 관측 EC2 설정과 환경별 대시보드는 State Manager Association이 파일로 넣습니다. 화면에서 고치지 않고 `observability.yaml`을 고쳐 다시 apply합니다. |

## 9. 장애 대응
>
> ### 9.1 워크로드 장애 검토
> >
> > | 장애 상황 | 대응 |
> > |---|---|
> > | Pod 장애 | Probe 실패 시 컨테이너를 재시작하고 Deployment, StatefulSet이 대체 Pod를 실행합니다. FE, BE는 Replica 2개라 1개 장애 동안 남은 Pod가 요청을 받습니다. AI API, Redis는 단일 Pod라 복구 동안 해당 기능이 중단됩니다. |
> > | Node 장애 | Karpenter가 해당 환경 NodePool에 새 Node를 공급하고 Pod를 재배치합니다. stage, prod Kafka는 Node 1대를 잃어도 Pod 1개만 잃어 쓰기, 읽기가 계속됩니다. Redis, Kafka의 EBS는 같은 AZ에서 재연결합니다. |
> > | 시스템용 Node 장애 | Cloud 팀이 EC2를 수동 복구, 교체하고 클러스터에 재등록합니다. 복구 전에는 CoreDNS(클러스터 DNS), Karpenter의 신규 Node 공급과 Argo CD 배포, SealedSecret 공급, Strimzi의 Kafka 구성 조정, Load Balancer Controller의 ALB 조정이 중단됩니다. |
> > | Deployment 실패, Readiness 실패 | `Recreate` 전략이라 기존 Pod를 내린 뒤 새 Pod를 띄우므로, 새 Pod가 준비되지 않으면 해당 서비스가 중단됩니다. Git의 이미지 값을 이전 digest로 되돌려 복구합니다. |
> > | Image Pull 실패 | 이미지 digest, `ghcr-pull` Secret, GHCR 접근성을 확인하고 복구합니다. |
> > | Resource 부족, 신규 Pod Pending | 자원, 배치 조건(환경 라벨, taint, anti-affinity), 스토리지, NodePool 상한을 확인합니다. |
> > | AI API Pod 종료 | 단일 Pod이므로 재기동 동안 분석, 추천 요청이 실패할 수 있습니다. 미완료 작업 재처리와 결과 중복 반영 방지는 AI의 Kafka 소비 전환과 함께 적용합니다. |
> > | AZ, DB 장애 | 앱, DB, Redis, Kafka가 모두 `ap-northeast-2b`에 있어 AZ 장애 시 전체 서비스가 중단됩니다. AWS 내부의 DB 대기 구성은 없으며, prod 데이터 복구는 DB EC2의 볼륨에 의존합니다. AWS 외부 복구 환경은 [v3 GCP 재해복구 설계 초안](v3%20GCP%20재해복구%20설계%20초안.md)에서 계획으로 다룹니다. |
> >
