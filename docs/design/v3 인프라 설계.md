## 1. 설계 방향과 요구사항
>
> **AWS EKS에서 서비스별 배포, 자원, 장애 대응을 표준화합니다.** 이 문서는 AWS 주 운영 환경의 구성과 운영 정책을 설계합니다.
>
> - 서비스, 조직의 변화와 Kubernetes 도입 목적은 [설계 배경](v3%20인프라%20설계%20전%20배경.md)에서 다룹니다.
>
> ### 1.1 운영 요구사항
> >
> > | 요구사항 | 설계 방향 |
> > |---|---|
> > | 배포와 운영 표준화 | FE, BE, AI API를 각각 별도 배포하고 공통 배포 규칙을 적용합니다. BE 내부의 API, Consumer, Batch는 통합 실행을 유지합니다. |
> > | 자원 관리, 확장 | BE의 자원 공유를 고려하고, 알림, AI 처리의 동시 실행량을 외부 서비스 처리 한도에 맞춰 관리합니다. |
> > | 권한, 민감 정보 관리 | FE, BE, AI, Cloud 팀별 담당 범위와 관리 권한을 구분합니다. |
> > | 구축, 배포 설정 재사용 | 기존 AWS 기반 자원과 공통 Helm Chart, 환경별 Values를 활용합니다. |
> >
> > - Kubernetes와 ECS 개선안의 비교 및 검증 기준은 [Kubernetes 도입 근거](v3%20인프라%20설계%20의사결정%20근거.md#11-kubernetes-도입)에 정리했습니다.
> >

> >
> > #### 2.1.1 요청 흐름
> > >
> > > ##### 2.1.1.1 화면, API 요청
> > > >
> > > > 1. 사용자가 서비스 도메인에 접속하면 DNS 조회로 Route 53에 연결된 CloudFront 주소를 확인합니다.
> > > > 2. 브라우저는 서비스 도메인으로 CloudFront에 HTTPS 요청을 보내고, CloudFront에서 HTTPS를 종료합니다.
> > > > 3. CloudFront는 VPC Origin을 통해 Internal ALB에 HTTP로 요청을 전달합니다.
> > > > 4. ALB는 도메인과 경로에 따라 해당 환경의 FE 또는 BE Service로 요청을 전달합니다.
> > > > 5. 화면 요청은 FE가 처리하고, 업무 API 요청은 BE가 처리합니다.
> > > > 6. BE는 필요한 작업에 따라 같은 환경의 MySQL, Redis에 접근합니다.
> > > > 7. FE 또는 BE의 응답은 ALB, CloudFront를 거쳐 브라우저에 전달됩니다.
> > > >
> > > ##### 2.1.1.2 AI 처리 요청
> > > >
> > > > 1. BE가 해당 환경의 Kafka 요청 토픽에 이미지 분석 또는 추천 작업을 발행합니다.
> > > > 2. AI API Pod의 Consumer가 요청을 소비합니다.
> > > > 3. AI API는 기존 NAT Gateway를 경유해 RunPod 환경의 AI Server에 HTTPS로 모델 추론을 요청합니다.
> > > > 4. AI API가 처리 결과를 Kafka 완료 토픽에 발행합니다.
> > > > 5. BE 내부 Consumer가 완료 이벤트를 소비하고 결과를 DB에 반영합니다.
> > > >
> > > ##### 2.1.1.3 요리 추천 이미지 조회
> > > >
> > > > 1. 브라우저의 이미지 요청은 CloudFront의 이미지용 Cache Behavior에서 처리합니다.
> > > > 2. 캐시가 있으면 CloudFront가 저장된 이미지를 바로 응답합니다.
> > > > 3. 캐시가 없으면 CloudFront가 OAC를 사용해 S3에서 원본을 HTTPS로 읽고, 캐시에 저장한 뒤 응답합니다.
> > > >
> > #### 2.1.2 운영 배치
> > >
> > > | 항목 | 설계 |
> > > |---|---|
> > > | Node 배치 | `tool`의 관리 도구는 상시 운영하는 EC2 한 대의 시스템용 Node에, 각 환경의 앱, Redis와 dev Kafka는 Karpenter가 관리하는 앱 NodePool에 배치합니다. |
> > > | 로그 경로, 청록 실선 | Alloy는 수집 대상 Worker Node마다 DaemonSet으로 실행하여 관측 EC2의 Loki로 로그를 전송합니다. 그림에서는 Node별 배치를 묶어 표시했습니다. |
> > > | 메트릭 경로, 청록 점선 | 관측 EC2의 Prometheus가 EKS 워크로드, Node의 메트릭을 수집하는 관계를 나타냅니다. |
> > > | 관측 EC2 내부 | Grafana가 Prometheus와 Loki를 조회하며, 같은 EC2 내부의 조회선은 전체 그림에서 생략했습니다. |
> > >
> > > 환경별 도메인, 라우팅은 4.4절에서 다룹니다.
> > >
> > > Kafka는 환경별 클러스터와 저장 데이터를 분리하여 Strimzi로 운영합니다. dev는 앱 NodePool의 단일 Kafka Pod와 PVC를 사용하며, stage, prod는 장애 대응이 가능한 다중 구성을 별도로 확정합니다. 각 환경의 DB EC2에는 MySQL과 AI용 PostgreSQL을 별도 엔진으로 함께 실행합니다. Private Node의 이미지 다운로드와 외부 API 요청은 기존 NAT Gateway를 경유합니다.

> ### 2.2 기존 인프라 재사용
> >
> > - v2에서 다음 구성과 데이터를 유지합니다.
> >
> > | 대상 | 유지 범위 |
> > |---|---|
> > | VPC, Subnet | 기존 prod VPC `10.20.0.0/16`과 EKS, ALB 구성에 필요한 2개 AZ의 Subnet을 재사용합니다. |
> > | NAT Gateway | 기존 prod VPC의 NAT Gateway와 Private Subnet의 외부 송신 경로를 재사용합니다. |
> > | EC2 사양, OS | 기존 인스턴스 사양과 Amazon Linux 2023을 유지합니다. |
> > | MySQL, 데이터 | 자체 구축 MySQL과 기존 업무 데이터를 유지합니다. |
> > | CI, 이미지 공급 | GitHub Actions, GHCR, 빌드 명령, Dockerfile을 활용합니다. |
> > | IaC | AWS 기반 자원은 기존 CloudFormation으로 관리합니다. |

> ### 2.3 변경하는 구성
> >
> > | 대상 | v2 | v3 |
> > |---|---|---|
> > | 앱 실행, 확장 | ECS, 앱 ASG | EKS, Karpenter |
> > | Node AMI | ECS용 AMI | EKS용 AMI |
> > | 외부 진입점 | ALB | CloudFront |
> > | CD | ECS 배포 | Helm, Argo CD 기반 GitOps |
> > | 관측 | CloudWatch | 별도 EC2의 Prometheus, Loki, Grafana와 Alloy 수집 |
> > | Redis 실행 위치 | EC2 | EKS Pod, AOF와 PVC로 상태 유지 |
> >
> > - 기존 ALB 자원의 인계 가능 여부는 Controller의 관리 방식과 전환 절차를 검증합니다.

> ### 2.4 VPC와 네트워크
> >
> > | 항목 | 설계 |
> > |---|---|
> > | 워크로드 배치 | 앱, 시스템 Node와 MySQL Primary는 단일 AZ에 배치합니다. AWS 내부의 DB Multi-AZ 대기 구성은 두지 않습니다. |
> > | EKS 등록 Subnet | 클러스터 생성 요건에 따라 서로 다른 2개 AZ의 Subnet을 지정합니다. |
> > | ALB Subnet | Internal ALB 구성 요건에 따라 서로 다른 2개 AZ의 Private Subnet을 지정합니다. |
> > | 주소 용량 검토 | Pod IP 수요와 VPC, Pod, Service 주소 대역의 충돌 여부는 구축 전 확인합니다. |
> > | Pod 네트워크 | EKS의 Pod 네트워크는 Amazon VPC CNI를 사용합니다. [Pod 네트워크 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#24-vpc와-pod-네트워크) |
> > | NetworkPolicy | dev, stage, prod의 애플리케이션 Pod에 기본 수신, 송신 차단 정책을 적용하고, 아래 허용표에 정의한 연결만 허용합니다. |
> > | Pod별 보안그룹 | Security Groups for Pods를 도입하고, Namespace와 서비스별로 분리한 SG를 SecurityGroupPolicy로 Pod에 연결합니다. |
> > | 통신 정책 관리 | Amazon VPC CNI의 NetworkPolicy와 Pod별 SG 기능을 활성화합니다. AWS SG는 CloudFormation으로, NetworkPolicy와 SecurityGroupPolicy는 Helm, Argo CD로 관리합니다. |
> > | 내부 호출 | 애플리케이션 Pod 간 HTTP 호출은 ClusterIP Service를 사용하며, DB와 Kafka는 VPC의 사설 경로로 연결합니다. |
> > | 외부 송신 | Private Node는 기존 NAT Gateway를 통해 GHCR과 RunPod 등 외부 서비스에 접속합니다. |
> >
> > #### 2.4.1 접근 제어 구성
> > >
> > > | 구성 | 적용 방식 |
> > > |---|---|
> > > | 환경, 서비스 식별 | Namespace는 `dev`, `stage`, `prod`, Pod 라벨 `app.kubernetes.io/name`은 `fe`, `be`, `ai-api`, `redis`로 구분합니다. Blue, Green Pod에도 같은 서비스 라벨을 유지합니다. |
> > > | Pod SG 구성 | 각 환경에 `sg-<환경>-fe`, `sg-<환경>-be`, `sg-<환경>-ai-api`, `sg-<환경>-redis`, `sg-<환경>-kafka`를 생성합니다. 같은 환경, 서비스의 Replica는 같은 SG를 사용하며 Kafka는 Strimzi의 Kafka Pod 라벨로 선택합니다. |
> > > | Node SG 역할 | 클러스터 운영과 앱 배치에 필요한 연결을 허용하고, DB와 Kafka의 수신 규칙에는 Node SG 대신 해당 환경의 Pod SG를 지정합니다. |
> > > | CNI 적용 모드 | `ENABLE_POD_ENI=true`, `POD_SECURITY_GROUP_ENFORCING_MODE=standard`로 구성하고, 지원 버전에서 NetworkPolicy와 함께 적용합니다. VPC 내부 통신은 적용되는 Node, Pod SG를 모두 충족하도록 구성합니다. |
> > > | 환경 격리 | NetworkPolicy의 Namespace, Pod 선택자를 함께 사용합니다. DB와 Kafka의 SG는 같은 환경의 허용된 Pod SG만 수신 대상으로 등록합니다. |
> > > | 송신 범위 | VPC 내부 목적지는 Pod, 사설 IP와 포트로 제한합니다. NAT를 경유하는 VPC 외부 HTTPS는 TCP 443을 허용하며, standard 모드의 외부 송신에는 Node SG가 적용됨을 반영합니다. |
> > > | 정책 범위 | 별도 허용 규칙이 없는 앱 연결은 차단합니다. HTTPS 송신 허용은 특정 도메인만 허용하는 정책을 의미하지 않으며, 외부 송신 규칙이 다른 환경의 사설 주소를 포함하지 않도록 구성합니다. |
> > > | 배치 용량 | Karpenter가 공급하는 Node에도 Pod ENI 구성을 적용하고, 기존 CPU, 메모리 예산과 함께 branch ENI, Pod IP 수용량을 확인합니다. |
> > >
> > #### 2.4.2 환경별 통신 범위
> > >
> > > | 출발 환경 | dev 앱, DB, Kafka | stage 앱, DB, Kafka | prod 앱, DB, Kafka |
> > > |---|---|---|---|
> > > | dev 앱 | 서비스별 허용표 적용 | 차단 | 차단 |
> > > | stage 앱 | 차단 | 서비스별 허용표 적용 | 차단 |
> > > | prod 앱 | 차단 | 차단 | 서비스별 허용표 적용 |
> > >
> > > 공용 ALB, DNS, 관측과 관리 도구는 아래 운영 통신만 예외로 허용합니다. 같은 환경이라도 모든 서비스 간 통신을 허용하지 않습니다.
> > >
> > #### 2.4.3 서비스별 통신 허용표
> > >
> > > 아래 표는 세 환경에 동일하게 적용하며, 목적지는 모두 출발 Pod와 같은 환경으로 한정합니다. 포트는 컨테이너와 서버의 수신 포트를 기준으로 합니다.
> > >
> > > | 출발 | 목적지 | 프로토콜, 포트 | 용도, 제어 |
> > > |---|---|---|---|
> > > | 공용 ALB | FE Pod | TCP 3000 | 화면 제공, ALB SG에서 FE Pod SG로 허용하고 NetworkPolicy에는 ALB 배치 Subnet 대역의 수신을 허용합니다. |
> > > | 공용 ALB | BE Pod | TCP 8080 | 업무 API, ALB SG에서 BE Pod SG로 허용하고 NetworkPolicy에는 ALB 배치 Subnet 대역의 수신을 허용합니다. |
> > > | FE Pod | BE Pod | TCP 8080 | FE 서버의 API 전달, 같은 Namespace의 FE만 BE 수신 대상으로 허용합니다. |
> > > | BE Pod | AI API Pod | TCP 8000 | 내부 HTTP 조회, 작업 요청과 결과 전달은 Kafka를 사용합니다. |
> > > | BE Pod | Redis Pod | TCP 6379 | 세션, 알림, 임시 상태, Redis SG와 NetworkPolicy에서 같은 환경의 BE만 허용합니다. |
> > > | BE Pod | DB EC2의 MySQL | TCP 3306 | DB SG에서 같은 환경의 BE Pod SG만 허용합니다. |
> > > | AI API Pod | DB EC2의 PostgreSQL | TCP 5432 | DB SG에서 같은 환경의 AI API Pod SG만 허용합니다. |
> > > | BE, AI API Pod | Kafka Pod | TCP 9092 | 환경별 내부 bootstrap Service로 접속하고, Kafka Pod SG와 NetworkPolicy에서 같은 환경의 BE, AI API Pod만 허용합니다. |
> > > | AI API Pod | RunPod, S3 | TCP 443 | 추론 요청과 입력 이미지 조회, VPC 외부 요청은 NAT 경유 HTTPS 송신으로 허용합니다. |
> > > | FE Pod | 외부 오류 수집 API | TCP 443 | 서버 측 오류 전송에 필요한 HTTPS 송신을 허용합니다. |
> > > | BE Pod | 푸시, 인증 등 외부 API | TCP 443 | 업무 처리에 필요한 HTTPS 송신을 허용합니다. |
> > >
> > > FE의 DB, Redis, Kafka 접근, BE의 PostgreSQL 접근, AI API의 MySQL과 Redis 접근은 허용하지 않습니다. 브라우저에서 S3로 업로드하거나 CloudFront로 요청하는 연결은 Pod 송신 정책의 적용 대상이 아닙니다.
> > >
> > #### 2.4.4 공통 운영 통신
> > >
> > > | 출발 | 목적지 | 프로토콜, 포트 | 허용 범위 |
> > > |---|---|---|---|
> > > | 앱, 관리 Pod | `kube-system`의 CoreDNS | UDP, TCP 53 | DNS 조회를 허용하고 CoreDNS 측 SG, 정책도 해당 연결을 허용합니다. |
> > > | Worker Node의 kubelet | FE, BE, AI API Pod | TCP 3000, 8080, 8000 | 해당 Node SG에서 Probe 대상 Pod SG로 허용합니다. Redis Probe는 컨테이너 내부 exec로 수행합니다. |
> > > | 관측 EC2의 Prometheus | 워크로드, Node, 관리 도구의 메트릭 수신점 | BE TCP 8080, kubelet TCP 10250, 그 외 설정된 메트릭 포트 | 관측 SG와 사설 주소에서 수집 포트만 허용합니다. Pod 정책에는 실제 수집 대상만 예외를 추가합니다. |
> > > | Node별 Alloy | 관측 EC2의 Loki | TCP 3100 | Node SG에서 관측 SG로 로그 전송을 허용합니다. Alloy의 실행 방식에 맞춰 Pod 송신 정책도 반영합니다. |
> > > | Argo CD, Karpenter, Controller | EKS API와 필요한 Webhook | API TCP 443, Chart의 Webhook 포트 | 도구의 조정, 배포에 필요한 연결만 허용하며, 클러스터 API의 도구 Webhook 호출도 허용합니다. |
> > > | Strimzi Operator, 같은 환경의 Kafka Pod | 해당 환경의 Kafka 관리, 복제 수신점 | Strimzi 내부 포트 | 상태 검사, Controller와 Broker의 내부 연결에 필요한 SG와 NetworkPolicy 규칙을 허용합니다. 다른 환경의 Kafka 연결로 확대하지 않습니다. |
> > > | Worker Node, 공통 관리 도구 | GHCR, GitHub, 필요한 AWS API | TCP 443 | 이미지 다운로드, Git 동기화, AWS 자원 제어를 허용합니다. Node의 이미지 다운로드는 앱 Pod의 Egress와 구분합니다. |
> > >
> > > 운영 예외는 서비스 간 교차 환경 통신 허용으로 확장하지 않습니다. Pod별 SG, DB, Kafka SG와 NetworkPolicy는 동일한 허용표를 기준으로 관리합니다.

> > | Node AMI | 기존 OS를 유지하되 ECS용 AMI를 EKS용 AMI로 변경합니다. 검증한 버전을 지정하고, 변경 영향 확인 후 적용합니다. |

> > | 운영 책임 | Cloud 팀이 AMI, 보안 패치, Node 복구와 Controller 로그, 메트릭, EC2 진단을 관리합니다. |

> >
> > | 항목 | 설계 |
> > |---|---|
> > | 공유 범위 | FE, 통합 BE, AI API, Redis는 하나의 앱 NodePool을 공유하고 시스템용 EC2와 분리합니다. |

> > | 용량 검증 | NodePool 자원 제한의 병렬 공급, 교체 중 일시적 초과와 실제 배치 가능 용량은 검증합니다. |

> > #### 4.3.1 배포 단위
> > >
> > > FE, BE, AI API는 각각 별도 Pod로 배포합니다.

> > #### 4.3.2 공통 기능
> > >
> > > nginx와 로그 수집용 Sidecar는 추가하지 않으며, 외부 라우팅은 ALB가, 로그 수집은 Node별 Alloy DaemonSet이 담당합니다.

> > #### 4.3.3 AI API 연동
> > >
> > > | 항목 | 설계 |
> > > |---|---|
> > > | 작업 연동 | BE와 AI API는 환경별 Kafka 요청, 완료 토픽으로 작업과 결과를 교환합니다. |
> > > | 내부 접근 | HTTP API가 필요한 내부 조회는 같은 Namespace의 ClusterIP Service로 제공합니다. |
> > > | 모델 호출 | RunPod는 EKS 외부의 모델 서빙 환경이며, 각 AI API Pod에서 HTTPS로 호출합니다. |
> > > | 호출 설정 | RunPod 호출 주소와 인증 정보는 환경별 설정, Secret으로 공급합니다. |
> > > | Consumer 배치 | AI 작업 Consumer는 AI API Pod에서 실행하고, 알림과 AI 결과 Consumer는 통합 BE에 유지합니다. |

> > #### 4.3.4 Probe 기본 정책
> > >
> > > FE, BE, AI API, Redis의 컨테이너에 아래 초안을 적용하며 stage, prod는 같은 정책을 사용합니다. 기동 완료 전에는 Startup만 검사하고 성공한 뒤 Readiness, Liveness를 실행합니다.
> > >
> > > | 대상 | Startup 검사 | 기동 예산, 실패 횟수 | Readiness 검사 | Liveness 검사 |
> > > |---|---|---|---|---|
> > > | FE | TCP `3000` | 약 2분, 12회 | TCP `3000` | TCP `3000` |
> > > | BE | HTTP `8080/actuator/health/readiness` | 약 5분, 30회 | HTTP `8080/actuator/health/readiness` | HTTP `8080/actuator/health/liveness` |
> > > | AI API | HTTP `8000/health/live` | 약 3분, 18회 | exec로 인증하여 로컬 `8000/health/ready` 확인 | HTTP `8000/health/live` |
> > > | Redis | exec로 로컬 `PING`의 `PONG` 응답 확인 | 약 10분, 60회 | exec로 `PONG` 확인 | exec로 `PONG` 확인 |
> > >
> > > | 공통 설정 | Startup | Readiness | Liveness |
> > > |---|---|---|---|
> > > | `periodSeconds` | 10 | 5 | 10 |
> > > | `timeoutSeconds` | 3 | 3 | 3 |
> > > | `failureThreshold` | 대상별 기동 예산 적용 | 3 | 6 |
> > > | `successThreshold` | 1 | 1 | 1 |
> > > | 실패 후 동작 | 허용 횟수 초과 시 컨테이너 재시작 | Service의 요청 전달 대상에서 제외 | 연속 실패 허용 횟수 초과 시 컨테이너 재시작 |
> > >
> > > `initialDelaySeconds`는 0으로 두고 Startup으로 기동을 보호합니다. 기동 예산은 `periodSeconds × failureThreshold` 기준이며 실제 기동, 데이터 복구 시간으로 조정합니다.
> > >
> > > | 적용 기준 | 설계 |
> > > |---|---|
> > > | 외부 의존성과 재시작 구분 | BE, AI API의 Liveness는 컨테이너 자체의 응답만 확인하고 DB, Redis, Kafka, RunPod의 일시 장애를 재시작 조건으로 사용하지 않습니다. |
> > > | BE 검사 범위 | Actuator Probe 그룹을 활성화하고 주 서비스 포트 8080에서 확인합니다. 초기에는 기본 Readiness, Liveness 그룹을 사용하며 외부 의존성을 포함하는 전체 `/actuator/health`를 Liveness에 사용하지 않습니다. |
> > > | AI API 검사 연결 | 기존 `/health/ready`는 내부 API 키 인증과 모델 준비 확인을 포함합니다. Secret 환경변수를 사용하는 exec 검사로 인증하고, 준비 실패는 Readiness 실패로만 처리합니다. Kafka 소비 중지, 재개는 Probe와 별도로 애플리케이션에서 관리합니다. |
> > > | Redis 검사 연결 | 인증 정보는 Secret에서 공급하고 `redis-cli`의 종료 코드뿐 아니라 `PONG` 응답을 확인합니다. AOF 복원 중에는 Startup으로 보호하고, 복원이 끝나 요청을 받을 수 있을 때 준비 완료로 판정합니다. |
> > > | 적용 대상 구분 | MySQL, PostgreSQL과 관측 서버는 EKS 외부 EC2이므로 이 컨테이너 Probe의 적용 대상에 포함하지 않습니다. Kafka는 Strimzi가 관리하는 Probe를 사용하고, 관리 도구는 공식 Helm Chart가 제공하는 Probe를 우선 사용합니다. |
> > >

> ### 4.5 Kafka 연동
> >
> > Kafka는 MSK 대신 Strimzi 기반으로 직접 운영하며, 환경마다 Kafka 클러스터, bootstrap 주소와 영속 볼륨을 분리합니다. dev는 단일 구성으로 먼저 구축하고, stage, prod는 장애 대응이 가능한 Broker, Controller 수와 배치를 별도로 확정합니다.
> >
> > | 운영 항목 | 설계 |
> > |---|---|
> > | 관리 방식 | Strimzi Cluster Operator는 `tool` Namespace의 시스템용 Node에서 실행합니다. Kafka와 KafkaNodePool, KafkaTopic 리소스는 Helm, Argo CD로 관리하고 실제 Pod, Service와 PVC는 Strimzi가 조정합니다. |
> > | dev 버전, 역할 | Kafka `4.2.2`를 지원하는 Strimzi 이미지와 Operator 조합을 사용합니다. `dev` Namespace의 Kafka Pod 1개가 KRaft Broker, Controller를 겸하며 ZooKeeper는 사용하지 않습니다. 기존 `apache/kafka` Compose 이미지를 그대로 배포하지 않습니다. |
> > | dev 자원 | `t3.small`의 2 vCPU, 메모리 2GiB를 자원 상한의 기준으로 삼습니다. CPU request `500m`, limit `2`, 메모리 request와 limit `2Gi`로 시작합니다. Node 인스턴스를 `t3.small`로 바꾸는 것은 아니며 CPU 2개를 상시 보장하는 설정도 아닙니다. |
> > | dev 영속 저장 | EBS CSI 기반 gp3 PVC `10Gi`를 사용합니다. `deleteClaim: false`, StorageClass `reclaimPolicy: Retain`으로 설정하여 Pod와 클러스터 재생성 시 기존 메시지, KRaft 메타데이터, offset을 보존하고, 재구축 시 기존 PVC와 cluster ID를 복원합니다. |
> > | dev 메시지 보관 | 업무 토픽의 `cleanup.policy: delete`, `retention.ms: 2592000000`으로 30일 보관 정책을 적용합니다. 전체 PVC 용량은 10Gi이므로 30일치 데이터가 항상 수용되는 것은 아니며, 디스크 사용량을 확인하여 용량을 조정합니다. |
> > | 접속, 보안 | 환경별 내부 bootstrap Service의 TCP 9092로 접속하며 클라이언트 연결은 PLAINTEXT를 사용합니다. TLS, SASL 클라이언트 인증은 추가하지 않고, SG와 NetworkPolicy로 같은 환경의 BE, AI API Pod만 허용합니다. Strimzi가 관리하는 내부 연결과 인증서 설정은 지원 기본 구성을 사용합니다. |
> > | 토픽 | 자동 생성을 끄고 환경 접두사를 사용합니다. dev는 합의한 `dev.dameokja.`의 7개 토픽을 KafkaTopic으로 생성하며 파티션, 복제 수는 1로 설정합니다. offsets 내부 토픽 복제 수와 dev의 `min.insync.replicas`도 1로 설정합니다. |
> > | dev 장애 수용 범위 | 단일 Pod 장애, 재시작 시 복구까지 Kafka 이용이 중단됩니다. Pod 재생성 시 기존 PVC를 재사용하며, EBS 재연결은 같은 AZ에서 수행합니다. 다중 Broker 복제와 AZ 장애 전환은 제공하지 않습니다. |
> > | 환경별 소비 | 환경별 bootstrap 주소를 주입하고 같은 환경의 Topic만 구독합니다. Topic 접두사와 Consumer Group ID도 환경별로 구분하며 다른 환경의 broker 연결은 허용하지 않습니다. |
> > | 구축 확인 | dev BE, AI API 접속과 송수신, 교차 환경 접속 차단, Kafka Pod 재생성 후 메시지, cluster ID, offset 유지 여부를 확인합니다. |
> >
> > | 항목 | 설계 |
> > |---|---|
> > | 작업 전달 | 공유 참여를 확정한 뒤 이벤트를 전달하고, BE 내부 Consumer가 알림을 생성합니다. |
> > | 알림 실패, 저장 | 알림 실패 시 참여는 유지하고 알림만 재처리하며, 참여, 재고, 완성된 알림은 DB에 저장합니다. |
> > | AI 요청, 결과 | BE가 `analysis.requested.v1`, `recommendation.requested.v1`에 요청을 발행하고, AI API는 처리 후 대응하는 `analysis.completed.v1`, `recommendation.completed.v1`에 결과를 발행합니다. 토픽은 환경별로 구분합니다. |
> > | AI 작업 복구 | FastAPI 내부 큐 접수와 작업 완료를 구분하고, 결과 발행 확인, 오프셋 커밋, 미완료 작업 재처리, 중복 반영 방지를 함께 구성합니다. |
> > | 실행 한도 | 알림, AI Consumer는 외부 서비스의 처리 한도에 맞춰 실행합니다. |
> > | 순서, 작업 분담 | 같은 냉장고의 이벤트는 냉장고 ID를 키로 같은 Topic, Partition에 전달하고 Consumer Group으로 분담합니다. |
> > | 누락, 중복 처리 | Producer 발행, Consumer 처리, 재시도의 순서, DB 저장과 이벤트 전달 사이의 누락, 재처리 중복은 애플리케이션과 함께 설계합니다. |
> >
> > | 남은 항목 | 결정 범위 |
> > |---|---|
> > | stage, prod 구성 | 장애 대응 범위에 따른 Broker, Controller 수, 역할 분리, Node와 AZ 배치 |
> > | stage, prod 자원, 저장 | 초기 CPU, 메모리, PVC 용량, 토픽별 보관 기간, 복제와 파티션 수 |
> > | 처리 제어 | Consumer별 동시 실행 한도, 순서, 누락, 중복, 재시도, 정상 종료, 재개 |

## 5. 자원, 배치, 확장 정책
>
> - Pod의 자원을 기준으로 배치 가능 용량을 판단하고, HPA로 Pod 수를 조절한 뒤 Karpenter로 필요한 Node를 공급합니다.
>
> ### 5.1 Pod requests, limits
> >
> > - 애플리케이션 컨테이너별 초기 자원 검토안은 다음과 같습니다.
> >
> > | 대상 | CPU request | CPU limit | 메모리 request | 메모리 limit |
> > |---|---|---|---|---|
> > | FE | `250m` | `1000m` | `512Mi` | `1Gi` |
> > | 통합 BE | `500m` | `1000m` | `1Gi` | `2Gi` |
> > | AI API | `250m` | `1000m` | `512Mi` | `1Gi` |
> > | Redis | `250m` | `500m` | `512Mi` | `1Gi` |
> > | dev Kafka | `500m` | `2` | `2Gi` | `2Gi` |
> >
> > FE, BE의 기존 값을 유지하고, AI API, Redis와 dev Kafka에는 초기 예산을 배정합니다. 실제 CPU, 메모리와 처리 지연은 구축 후 확인하여 조정합니다.
> >
> > #### 5.1.1 AI API 자원
> > >
> > > | 항목 | 설계 |
> > > |---|---|
> > > | 실행, 확장 방식 | AI API는 Deployment의 Pod로 운영하고, 활성 버전은 dev 1개, stage 2개, prod 2개를 고정 실행합니다. 필요한 Node는 Karpenter가 공급합니다. |
> > > | 배포 여유 | AI API도 Blue/Green으로 배포하며, 배포 중에는 해당 환경의 활성 버전과 같은 수의 신버전 Pod를 추가합니다. 전체 환경 동시 배포 시 AI API는 총 10개를 합산합니다. |
> > > | 내부 큐 | FastAPI 내부 큐는 유지할 수 있으나, 해당 큐만을 작업 보관 수단으로 삼지 않습니다. Pod 종료 후 미완료 작업을 재처리할 수 있도록 구성합니다. |
> > > | 적용 전 검증 | 결과 발행과 커밋 시점, 중복 처리, Pod 종료와 Consumer 재배정 후 복구를 확인합니다. |
> > > | 소비 병렬성 | AI 작업 Consumer Group의 파티션 수, 소비 동시성과 RunPod 처리 한도를 함께 검토합니다. 로컬의 파티션 1개를 운영 확장 기준으로 사용하지 않습니다. |
> > > | 자원, HPA 수치 | 초기 requests, limits는 5.1절의 검토안을 적용합니다. Kafka 연동과 작업 복구를 검증한 뒤 HPA를 도입할 때 확장 지표, 최소, 최대 Replica와 NodePool 용량을 함께 재산정합니다. |
> > >
> > #### 5.1.2 Node, BE 메모리
> > >
> > > `m7i.large`의 물리 자원은 CPU 2 vCPU, 메모리 8Gi입니다. 용량 계산에서는 Node당 CPU `500m`, 메모리 `1Gi`를 OS, Kubernetes와 Alloy 등 공통 Pod의 합산 예산으로 제외하여 앱 배치 예산을 CPU `1.5 vCPU`, 메모리 `7Gi`로 잡습니다. 실제 Node의 Allocatable과 DaemonSet requests를 확인하여 계산 예산을 검증하며, 예약 자원을 중복 차감하지 않습니다.
> > >
> > > BE의 JVM Heap은 메모리 limit 안에서 다른 JVM 메모리의 여유를 두며, Kafka 연동 후 합산 부하로 기동, 응답, OOM을 확인합니다.
> > >
> > > [초기 자원 산정 근거](v3%20인프라%20설계%20의사결정%20근거.md#51-pod-requests-limits)

> ### 5.2 시스템용, 앱 Node 배치
> >
> > | 항목 | 설계 |
> > |---|---|
> > | 실행 위치 | Karpenter, Argo CD, Sealed Secrets Controller, Strimzi Cluster Operator는 시스템용 Node에, 각 환경의 FE, BE, AI API, Redis와 dev Kafka는 앱 NodePool에 배치합니다. |
> > | Node 선택 | `nodeSelector`로 시스템용 Node 라벨을 선택하고, 시스템용 Node에는 `NoSchedule` taint를 적용하여 일반 앱 Pod의 배치를 제한합니다. |
> > | Pod별 설정 | 각 도구에는 해당 toleration을 설정하고, 컨테이너별 requests, limits와 도구별 ServiceAccount를 구성합니다. |
> > | Node 교체 | 시스템용 EC2를 수동으로 교체, 재등록할 때도 같은 라벨, taint를 적용합니다. |

> ### 5.3 FE, BE HPA와 Replica
> >
> > - stage, prod의 FE, BE에 같은 CPU 기반 HPA를 적용하고 VPA는 함께 사용하지 않습니다. dev는 FE, BE를 각각 1개로 고정합니다.
> > - Metrics Server가 CPU 지표를 공급하며 CPU request 대비 Pod 평균 사용률로 확장합니다.
> >
> > | 공통 정책 | 설정 |
> > |---|---|
> > | CPU 목표 사용률 | `averageUtilization: 80` |
> > | 축소 안정화 시간 | `behavior.scaleDown.stabilizationWindowSeconds: 300` — 5분 |
> >
> > - 확장, 축소 속도는 Kubernetes 기본값으로 시작하고 부하 시험과 운영 데이터로 조정합니다.
> > [HPA 선택 근거](v3%20인프라%20설계%20의사결정%20근거.md#53-fe-be-hpa와-replica)를 별도로 관리합니다.
> >
> > #### 5.3.1 초기 최소, 최대 Replica
> > >
> > > - prod는 평시 25~45 RPS, 피크 300 RPS를 기준으로 처리 Pod에 장애 여유 1개를 더합니다. stage에도 같은 Replica 범위와 HPA 정책을 적용하여 prod와 동일한 확장 동작을 검증합니다. 장애 여유는 Blue/Green의 신버전 실행 용량과 별개입니다.
> > > - 최소는 `ceil(45 / 100) + 1 = 2`, 최대는 `ceil(300 / 100) + 1 = 4`입니다.
> > >
> > > | 환경 | FE Replica | BE Replica | 확장 방식 |
> > > |---|---:|---:|---|
> > > | dev | 1 | 1 | 고정 |
> > > | stage | 2~4 | 2~4 | CPU 기반 HPA |
> > > | prod | 2~4 | 2~4 | CPU 기반 HPA |
> > >
> > > ##### 5.3.1.1 처리량, 확장 기준
> > > >
> > > > | 항목 | 설계 |
> > > > |---|---|
> > > > | BE 처리 목표 근거 | BE의 목표는 [ECS 시험 결과와 산정 근거](v3%20인프라%20설계%20의사결정%20근거.md#초기-최소-최대-replica)를 사용합니다. |
> > > > | FE 처리 목표 검증 | FE의 100 RPS는 API 시험으로 검증한 값이 아닌 초기 목표입니다. |
> > > > | 확장 지표 | RPS는 범위 산정에만 사용하고 실제 확장은 CPU 사용률로 제어합니다. |
> > > >
> > > ##### 5.3.1.2 운영 용량 검토
> > > >
> > > > AI API의 활성 버전은 전체 5개, Redis는 전체 3개, dev Kafka는 1개를 합산합니다. Blue/Green은 기존 버전을 유지한 채 같은 수의 FE, BE, AI API 신버전을 실행하는 기준이며 Kafka는 복제하지 않습니다. stage, prod Kafka의 자원은 해당 다중 구성 확정 후 추가 산정합니다.
> > > >
> > > > | 실행 상황 | FE | BE | AI API | Redis | CPU requests | 메모리 requests | 메모리 limits | 계산상 앱 Node |
> > > > |---|---:|---:|---:|---:|---:|---:|---:|---:|
> > > > | dev만 실행 | 1 | 1 | 1 | 1 | 1.75 vCPU | 4.5Gi | 7Gi | 2대 |
> > > > | 평시, stage, prod 최소 | 5 | 5 | 5 | 3 | 6.25 vCPU | 13.5Gi | 25Gi | 5대 |
> > > > | stage, prod 동시 피크 | 9 | 9 | 5 | 3 | 9.25 vCPU | 19.5Gi | 37Gi | 7대 |
> > > > | 동시 피크, prod FE, BE, AI API Blue/Green | 13 | 13 | 7 | 3 | 12.75 vCPU | 26.5Gi | 51Gi | 9대 |
> > > > | stage, prod FE, BE, AI API 동시 Blue/Green | 17 | 17 | 9 | 3 | 16.25 vCPU | 33.5Gi | 65Gi | 11대 |
> > > > | 전체 환경 FE, BE, AI API Blue/Green | 18 | 18 | 10 | 3 | 17.25 vCPU | 35.5Gi | 69Gi | 12대 |
> > > >
> > > > 앱 Node 수는 `max(ceil(CPU requests 합계 / 1.5), ceil(메모리 limits 합계 / 7))`와 Pod별 배치 가능 여부로 검토합니다. 계산상 최대 12대에 교체 여유 1대를 더한 앱 상한 13대의 계산 예산은 CPU 19.5 vCPU, 메모리 91Gi이며 시스템용 EC2 1대는 별도입니다.
> > > >
> > > > | 항목 | 설계 |
> > > > |---|---|
> > > > | 계산 범위 | 앱 NodePool의 FE, BE, AI API, Redis와 dev Kafka 1개를 합산합니다. 시스템용 Node의 관리 도구와 EKS 외부의 DB, 관측 EC2는 제외합니다. stage, prod Kafka의 자원과 배치 확정 시 합산값과 Node 상한을 다시 계산합니다. |
> > > > | requests, limits 기준 | 실제 스케줄링은 CPU, 메모리 requests를 기준으로 하며 용량 검토에서는 메모리 limits 합계도 추가로 확인합니다. CPU limits 합계만큼의 동시 CPU 사용을 보장하는 구성은 아니므로 피크 응답 지연과 CPU 경합은 부하 시험으로 확인합니다. |
> > > > | 실제 Node 수 | 표의 값은 계산 기준입니다. 실제 Allocatable, DaemonSet, Pod ENI, PVC와 배치 조건에 따라 필요한 Node 수가 달라지면 자원값과 상한을 재검토합니다. |
> > > > | 시스템용 Node | `m7i.large` 1대를 별도로 유지하고, 관리 도구 requests 합계가 실제 가용 자원 안에 들어오는지 확인합니다. Worker Node 전체 상한은 앱 13대와 시스템 1대를 합한 14대 기준입니다. |
> > > > | DB 연결 | stage, prod는 각각 BE 4개의 연결 풀 상한을 10개로 유지하면 해당 환경 MySQL에 대한 상한이 40개, 신, 구 BE 동시 실행 시에는 80개입니다. dev는 정상 10개, 배포 중 20개이며 다른 DB 사용자 연결도 합산합니다. PostgreSQL은 신, 구 AI API Pod의 연결 풀을 함께 합산합니다. |
> > > > | Consumer 실행량 | BE 내부 Consumer, Batch의 CPU도 HPA에 반영되므로 Pod 증감에 따른 전체 작업 실행량은 외부 서비스 한도에 맞춰 제어합니다. |
> > > >
> ### 5.4 Karpenter Node 확장, 정리
> >
> > - Karpenter는 배치할 수 없는 Pod의 자원, 조건에 맞춰 앱 Node를 공급합니다.
> > - BE 용량은 API, Batch, Consumer의 합산 부하로 검증하고, Kafka 용량은 이벤트량, 메시지 크기, 보관 기간, 복제 구성으로 별도 산정합니다.
> >
> > ```mermaid
> > flowchart TB
> >     cpuMetrics["Metrics Server, FE, BE CPU 지표"] --> hpa["HPA, CPU request 대비 목표 80%"]
> >     hpa --> replicas["stage, prod Replica 조정, FE 2~4 / BE 2~4"]
> >     replicas --> scheduler["Scheduler, Pod 배치"]
> >     scheduler --> capacity{"기존 Node에 배치 가능?"}
> >     capacity -->|"가능"| running["Pod 실행, Readiness 확인"]
> >     capacity -->|"불가"| pending["Pod Pending, 미충족 자원, 배치 조건"]
> >
> >     subgraph systemNodes["시스템용 Node, EC2 1대 상시 운영"]
> >         karpenter["Karpenter Controller, 직접 운영"]
> >     end
> >
> >     pending --> karpenter
> >     karpenter -->|"NodePool 정책, 허용 용량 확인"| nodeSupply["EC2 앱 Node 공급, 최대 13대 기준"]
> >     nodeSupply -->|"Node 등록 후 재배치"| scheduler
> > ```
> >
> > - 앱 Node 상한 13대에 시스템용 Node 1대는 포함하지 않습니다. 상한은 상시 실행 대수가 아니며 필요한 Node는 Karpenter가 공급합니다.
> > - 스토리지, 할당량, 배치 정책이 원인이면 Node를 추가해도 Pod는 Pending으로 남을 수 있습니다.
> >
> > 앱 NodePool의 정리, 교체 정책은 다음과 같습니다.
> >
> > | 항목 | 설정 | 동작 |
> > |---|---|---|
> > | 정리 대상 | `consolidationPolicy: WhenEmpty` | 일반 앱 Pod가 없는 빈 Node만 정리합니다. |
> > | 정리 대기 | `consolidateAfter: 5m` | Pod 추가, 제거 후 5분간 배치 변화가 없고 빈 상태인 Node를 정리 대상으로 검토합니다. |
> > | 동시 정리, 교체 | `budgets`의 `nodes: "1"` | 자발적인 정리와 설정 변경에 따른 교체는 한 번에 한 대씩 진행합니다. |
> >
> > - 앱 Node의 자발적인 정리, 교체에 적용합니다.
> > - 시스템용 EC2의 수동 교체와 앱 Node의 장애, 수명 만료에 의한 종료는 별도로 관리합니다.
> >
> ### 5.5 Redis 운영
> >
> > #### 5.5.1 실행과 자원
> > >
> > > | 항목 | 설계 |
> > > |---|---|
> > > | 실행 구성 | dev, stage, prod Namespace마다 `redis` StatefulSet을 Replica 1개로 운영합니다. 읽기 Replica와 HPA는 적용하지 않습니다. |
> > > | 접속 | StatefulSet의 식별자는 `redis-headless` Headless Service로 관리하고, BE는 별도의 `redis` ClusterIP Service에 TCP 6379로 접속합니다. |
> > > | AOF 정책 | v2 prod의 `appendonly yes`, `appendfsync everysec`를 유지합니다. `/data`에 전용 PVC를 마운트하고 AOF 파일을 기록합니다. |
> > > | 자원 관리 | 초기 검토안은 CPU request `250m`, limit `500m`, 메모리 request `512Mi`, limit `1Gi`입니다. 사용량을 확인하여 수동 조정하며 자동 자원 조정은 적용하지 않습니다. |
> > > | 메모리 여유 | 초기 `maxmemory`는 `512Mi`로 설정하여 메모리 limit `1Gi` 안에 AOF 처리, 클라이언트 버퍼, 내부 관리 메모리와 메모리 단편화에 대한 여유를 확보합니다. |
> > >
> > #### 5.5.2 영속 볼륨 공급과 복구
> > >
> > > | 항목 | 설계 |
> > > |---|---|
> > > | 드라이버 | AWS EBS CSI Driver를 EKS add-on으로 설치하고 전용 IAM Role로 EBS 생성, 연결 권한을 부여합니다. |
> > > | StorageClass | 공통 `redis-gp3`를 사용합니다. `provisioner: ebs.csi.aws.com`, `type: gp3`, `volumeBindingMode: WaitForFirstConsumer`, `allowVolumeExpansion: true`로 설정합니다. |
> > > | PVC 생성 | StatefulSet의 `volumeClaimTemplates`에 `data`를 정의하고, 환경별 `data-redis-0` PVC를 생성합니다. 각 PVC는 `redis-gp3`, ReadWriteOnce, 초기 요청 용량 `10Gi`를 사용합니다. |
> > > | PV와 EBS 공급 | PVC를 사용하는 Pod의 배치 조건에 맞춰 EBS CSI Driver가 같은 AZ에 gp3 EBS와 PV를 동적으로 공급하고 PVC에 바인딩합니다. 환경별 EBS 한 개씩, 초기 총 `30Gi`를 사용하며 PV를 수동으로 미리 만들지 않습니다. |
> > > | Pod 재생성 | StatefulSet은 기존 PVC를 재사용합니다. Node가 바뀌면 같은 AZ에서 기존 EBS의 연결 해제, 재연결을 거쳐 `/data`를 마운트하고 AOF 복원 후 요청을 받습니다. 특정 Node에 고정하지 않습니다. |
> > > | 데이터 보존 | StatefulSet의 PVC 보존 정책은 `whenDeleted: Retain`, `whenScaled: Retain`, StorageClass의 `reclaimPolicy`는 `Retain`으로 설정합니다. StatefulSet이나 PVC 삭제가 EBS 자동 삭제로 이어지지 않도록 하고, 환경 폐기 시 Cloud 팀이 남은 PV와 EBS를 확인해 정리합니다. |
> > > | 복구 범위 | 볼륨 재연결과 AOF 로딩 동안 해당 환경의 Redis는 중단될 수 있습니다. 볼륨 자체의 손실과 AZ 장애는 이 구성만으로 복구하지 않으며, Kafka도 Redis의 인증, 서비스 상태를 자동 복원하지 않습니다. |
> > >

> >

## 7. 운영 권한과 Secret
>
> ### 7.1 운영 책임과 접근 권한
> >
> > | 담당 | 책임 |
> > |---|---|
> > | FE 팀 | 화면, 사용자 기능과 BE API 연동, FE 배포 검증, 장애 분석을 담당합니다. |
> > | BE 팀 | API, DB 연동, 알림, Batch, Kafka Consumer와 BE 배포 검증, 장애 분석을 담당합니다. |
> > | AI 팀 | AI 분석, 추천 기능과 BE 연동, AI 기능의 검증, 장애 분석을 담당합니다. |
> > | Cloud 팀 | 클러스터, Node, 네트워크, 공통 CI/CD, 접근 권한, 관측 기반과 인프라 장애 대응을 담당합니다. |
> >
> > #### 7.1.1 직접 접근 권한
> > >
> > > FE, BE, AI, Cloud 팀의 애플리케이션 직접 접근 권한은 아래 기준에 따라 Role, RoleBinding으로 관리합니다.
> > >
> > > Grafana, Loki의 로그 조회 권한도 같은 환경 범위로 맞춥니다.
> > >
> > #### 7.1.2 공통 운영 권한
> > >
> > > 관리 도구의 `tool` Namespace와 클러스터 공통 자원은 Cloud 팀이 별도 운영 권한으로 관리합니다.
> > >
> > > Argo CD 배포 권한은 각 팀의 직접 접근 권한과 구분합니다.
> > >
> > > | 작업 | dev | stage | prod |
> > > |---|---|---|---|
> > > | 로그 조회 | 허용 | 허용 | 허용 |
> > > | Deployment 직접 수정 | 허용 | 허용하지 않음 | 허용하지 않음 |
> > > | 자기 팀의 Secret 관리 | 생성, 조회, 수정, 삭제 허용 | 생성, 조회, 수정, 삭제 허용 | 권한 부여하지 않음 |
> > >
> ### 7.2 Secret 구분과 공급
> >
> > | 항목 | 설계 |
> > |---|---|
> > | Secret 이름 | Secret 이름은 `fe-secrets`, `be-secrets`, `ai-secrets`, `cloud-secrets`로 구분합니다. |
> > | 직접 접근 권한 | RBAC의 `resourceNames`로 이름별 권한을 제한하고 생성 요청의 담당 팀, 이름은 추가 검증합니다. |
> > | Git 변경 권한 | SealedSecret, Git 변경 권한에도 같은 환경, 팀 기준을 적용합니다. [권한 적용 근거와 제약](v3%20인프라%20설계%20의사결정%20근거.md#71-환경-트랙별-접근-권한) |
> > | Git 보관 | Git에는 Sealed Secrets의 공개키로 암호화한 SealedSecret을 보관합니다. |
> > | 암호화 범위 | 이름, Namespace에 결합되는 기본 `strict` 범위를 사용하고 지속적인 변경은 Git에 반영합니다. |
> >
> > ```mermaid
> > flowchart LR
> >     author["담당자, kubeseal 공개키 암호화"] --> gitSealed["Git, 암호화된 SealedSecret"]
> >     gitSealed --> secretArgo["Argo CD, 적용"]
> >     secretArgo --> sealedResource["대상 Namespace, SealedSecret"]
> >     sealedResource --> sealedController["tool, Sealed Secrets Controller"]
> >     sealedController -->|"복호화, 생성, 갱신"| runtimeSecret["대상 Namespace, Secret"]
> >     runtimeSecret --> consumingPod["애플리케이션 Pod"]
> > ```

## 8. 관측: Prometheus, Loki, Grafana
>
> - Prometheus, Loki, Grafana는 EKS 외부의 EC2에 배치합니다.
> - AWS 데이터를 같은 Grafana에서 조회하고 관측 서버의 OS, 프로세스, 스토리지, 복구는 직접 관리합니다.
>
> | 구성요소 | 역할 |
> |---|---|
> | Prometheus | EKS의 운영 메트릭을 수집, 저장합니다. |
> | Grafana Alloy | 수집 대상 Worker Node마다 DaemonSet Pod 1개를 배치하여 해당 Node의 로그를 Loki로 전달합니다. |
> | Loki | Alloy가 전달한 로그를 관측 EC2에서 저장, 조회합니다. |
> | Grafana | 관측 EC2의 Prometheus, Loki에 연결하여 메트릭, 로그를 조회합니다. |
>
> ```mermaid
> flowchart LR
>     subgraph eksCollection["AWS EKS, 관측 대상, 로그 수집"]
>         awsTargets["EKS 관측 대상"]
>         awsAlloy["Alloy DaemonSet, Node별 로그 수집"]
>         awsTargets -->|"로그"| awsAlloy
>     end
>
>     subgraph awsObservability["별도 AWS EC2, EKS 외부의 중앙 관측 시스템"]
>         prometheus["Prometheus"]
>         loki["Loki"]
>         grafana["Grafana, 통합 대시보드"]
>         grafana -->|"메트릭 조회"| prometheus
>         grafana -->|"로그 조회"| loki
>     end
>
>     awsTargets -->|"메트릭 수집"| prometheus
>     awsAlloy -->|"로그 전송"| loki
>     operator["FE, BE, AI, Cloud 팀"] --> grafana
>
>     style eksCollection fill:#eff6ff,stroke:#1d4ed8,stroke-width:3px,color:#1e3a8a
> ```
>
> | 항목 | 설계 |
> |---|---|
> | 공통 설정, 권한 | 공통 라벨, 대시보드를 사용하고, 관측 EC2의 수집 대상 접근 권한을 구축 시 구성합니다. |
> | 재시작 시 보관 | 저장 데이터와 Alloy의 로그 읽기 위치는 재시작 후에도 유지합니다. |
> | 수집 공백 | 원본 로그가 남은 범위에서 후속 수집할 수 있지만 지표 수집 공백과 일부 로그 유실은 감수합니다. |
> | 중앙 관측 장애 | 관측 EC2, AWS 장애 시 중앙 관측도 영향을 받습니다. |
