# v3 인프라 설계 전 배경

> 기준일: 2026-10-28

서비스와 조직이 성장하면서 배포, 자원, 장애 대응을 표준화할 필요가 커졌습니다. AWS를 주 운영 환경으로 유지하고, 피크 시간대의 AWS 장애에 대비해 GCP에 핵심 서비스의 복구 환경을 마련합니다. 두 환경에 공통으로 적용할 운영 플랫폼을 설계하는 것이 v3의 목적입니다.

온프레미스 이전이라면 AWS 전용 서비스의 의존성 제거를 우선하겠지만, v3는 AWS, GCP 멀티클라우드를 통해 단일 제공업체에 집중된 운영 의존성을 분산합니다. 클라우드별 관리형 서비스의 종속성은 일부 허용하고, 공통 배포 정의와 데이터 복구 경로를 마련하여 향후 워크로드, 복구 용량과 제공업체별 사용 비중을 조정할 기반을 확보합니다.

## 1. 기존 운영 환경

[v2 설계](wiki/ktb4-cloud-wiki-v2.md)를 기반으로 다음 구성을 운영합니다.

| 영역 | 구성 |
|---|---|
| 실행, 확장 | ECS EC2 launch type, ASG, ALB |
| 배포 | GitHub Actions, GHCR, ECS Native Blue/Green |
| 데이터 | 자체 구축 MySQL Primary, Standby, Read Replica, Redis |
| 관측, 구축 | CloudWatch, CloudFormation |
| 가용성 | 앱서버 다중 AZ 배치, Orchestrator 기반 DB 장애조치 |

FE, BE, AI는 저장소가 분리되어 있으며, nginx, FE, BE는 하나의 ECS Task에 포함됩니다. BE는 API, 알림 처리, 정기 Batch를 같은 프로세스에서 실행하고, 발송 대기 작업도 업무 DB에서 관리합니다.

## 2. 서비스와 조직의 변화

### 조직과 변경 범위 확대

계정, 공유 냉장고, 재고, 알림, 추천 기능의 변경이 늘고, 여러 팀의 릴리스 일정과 검증 범위가 달라졌습니다.

| 팀 | 담당 영역 |
|---|---|
| FE | 사용자 화면, 사용자 기능, BE API 연동 |
| BE | 계정, 공유 냉장고, 재고, 알림, Batch, AI 연동 API |
| AI | AI 분석, 추천 기능, BE 연동 |
| Cloud | 인프라, 배포, 자원, 관측, 권한, 장애 대응의 공통 기반 |

FE, BE, AI 팀의 변경이 서로 연동되므로 API 호환성, 배포 일정, 검증 범위를 함께 조정해야 합니다. API, 알림, Batch가 자원을 공유하여 특정 작업의 부하가 요청 처리에 영향을 줄 수 있습니다. 기능별 MSA 전환과 정기 Batch 분리는 고도화 범위로 두고, 초기에는 FE, BE의 배포 단위를 유지합니다.

### 식사 준비 시간대의 부하 집중

사용자는 식사 준비 시간대에 냉장고 재료를 확인하고 재고를 변경하거나 추천을 조회합니다. 이 시간대에 부하와 장애가 겹치면 핵심 기능을 필요한 시점에 이용할 수 없습니다.

| 지표 | v2 | v3 |
|---|---:|---:|
| 외부 피크 RPS | 약 95 | 약 300 |
| 피크 동시 접속자 | 약 7,200명 | 약 22,000명 |

평상시와 피크 트래픽은 AWS 내부에서 확장하여 처리합니다. 알림, AI 작업은 처리 한도에 맞춰 실행할 수 있도록 보관, 분배하고, API와의 자원 경합을 관리해야 합니다.

## 3. 장애 대응 범위의 확장

v2는 AWS 내 Multi-AZ로 AZ, DB 인스턴스 장애에 대응했습니다. v3에서는 DB 이중화를 AWS, GCP 간 구성으로 변경하여 주 운영 환경에 접근하기 어려운 장애에도 복구할 데이터를 확보합니다.

| 환경 | 역할 |
|---|---|
| AWS 서울 | 평상시, 피크 요청을 처리하고 MySQL Primary를 운영합니다. |
| GCP 서울 | AWS의 DB 데이터를 복제하고, 장애 시 냉장고, 재고 등 핵심 서비스를 복구합니다. |

복구 환경의 배포, 운영 절차는 AWS 장애 중에도 사용할 수 있도록 준비합니다.

## 4. 공통 운영 플랫폼의 필요성

ECS에서도 독립 배포, 자원 제한, 자동 확장을 구성할 수 있습니다. 이번 전환에서는 AWS, GCP에 같은 운영 기준을 적용하는 것을 우선합니다.

ECS를 유지하고 GCP에 별도 플랫폼을 두면 Task Definition과 Kubernetes 배포 정의, 배포 절차와 장애 대응 기준을 각각 관리해야 합니다. Kubernetes를 공통으로 사용하면 애플리케이션 배포 정의와 Helm, GitOps 운영 방식을 재사용하고, 클라우드별 네트워크, 스토리지, 권한 연동을 구분할 수 있습니다.

## 5. 운영 요구사항

- FE, BE의 배포, 자원, 확장 기준을 표준화합니다.
- API, 알림, AI, 정기 작업이 공유하는 자원과 처리량을 관리합니다.
- 환경, 담당별 접근 권한과 민감 정보를 일관되게 관리합니다.
- AWS, GCP에서 배포, 관측 설정과 운영 절차를 재사용합니다.
- 피크 시간대의 AWS 장애에 대비해 GCP에서 핵심 서비스와 데이터를 복구합니다.

구성과 정책은 [v3 인프라 설계](v3%20인프라%20설계.md), 대안 비교와 선택 이유는 [의사결정 근거](v3%20인프라%20설계%20의사결정%20근거.md)에서 다룹니다.
