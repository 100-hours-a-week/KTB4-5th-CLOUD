#### 1. MAU
- 대한민국 2025년 가구수는 23,245,980명 (https://kosis.kr/visual/nsportalStats/detailContents.do?statJipyoId=3633&vStatJipyoId=4881&listId=A)
- 침투율 1% 가정
  - 이유: 카카오톡 99%, 유튜브 84%, 인스타그램 34% 등 국민 앱 대비, 냉장고 관리라는 니치 카테고리 서비스 특성상 훨씬 낮게 설정
- **MAU = 230,000명**으로 확정해 이후 계산에 사용 (23,245,980 × 1% ≈ 232,460명)

#### 2. Peak 동시 접속자 수 (Concurrency)
- 추정 방식: MAU → DAU(스티키니스 비율) → Peak 동시접속자(CCU) 순서로 계산
- DAU/MAU 스티키니스 = **50%** 가정
  - 이유: 다먹자는 냉장고·식사라는 매일의 생활에 밀착된 서비스라는 판단
  - 카테고리별 벤치마크 비교(2026년, vmobify "DAU/MAU Stickiness Benchmarks by Category"): 메시징/소셜 커뮤니케이션 50%+, 소셜·콘텐츠 피드 40~60%+, 게임 20~50%, 핀테크/뱅킹·B2B SaaS 10~25%, 이커머스 한 자릿수~10대 중반, 전체 앱 평균 약 20% (https://vmobify.com/blog/dau-mau-stickiness-benchmarks)
  - DAU ≈ 230,000 × 50% ≈ **115,000명**
- 3번 항목(RPS)의 시간대별 흐름표를 그대로 재사용해 아래처럼 산정함 — 3번 항목과의 일관성을 유지하기 위함.
- Little's Law: CCU = 세션 도착률(세션/시간) × 평균 세션 지속시간(시간). 3번 항목 흐름표의 시간대별 접속 수를 각 윈도우의 도착률로 환산해 적용함 — 평균 세션 지속시간은 5분으로 가정:

  | 시간대 | 윈도우 | 접속 수 | CCU |
  |---|---|---|---|
  | 아침 알림 버스트 (08:00~08:10) | 10분 | 11,500 | 5,750명 |
  | 오전 지연 반응 (08:10~10:00) | ~2시간 | 17,250 | 719명 |
  | 점심시간 (12:00~13:00) | 1시간 | 11,500 | 958명 |
  | 저녁 요리 준비 (18:00~19:00) | 1시간 | 54,625(고유 40,250 + 재접속 14,375) | 4,552명 |
  | 기타 분산 시간대 | ~19.8시간 | 34,500 | 145명 |

- **Peak CCU는 아침 알림 버스트 구간(5,750명)**. 저녁 요리 준비 구간은 접속 수가 54,625명으로 가장 많지만 윈도우가 1시간으로 넓어 순간 동시접속자는 상대적으로 적은 4,552명에 그치고, 아침 알림 버스트는 접속 수가 11,500명으로 적어도 윈도우가 10분으로 좁아 순간 동시접속자가 가장 많음. 아래 3번 항목에서 다시 계산한 Peak RPS는 저녁 요리 준비 구간이 기준으로 바뀌어 Peak CCU와 시간대가 갈라지는데, 그 이유는 3번 항목 마지막에서 이어서 설명함.
- 3번 항목과 동일한 안전마진 25% 적용 → **설계 목표 피크 CCU ≈ 7,200명**
- 실사용 데이터 없이 잡은 가정치이므로 출시 후 실제 로그 기반 재검증 필요. 시간대별 비율을 조정하면 이 값도 함께 바뀜 — 3번 항목 참고.

#### 3. RPS, Peak RPS

- **RPS·Peak RPS 산정 방식**: `RPS = 시간대별 접속 수 × 시간대별 가중평균 요청 수 ÷ 윈도우(초)` 공식을 하루 사용자 흐름을 시간대별로 나눠 적용함. 이전에는 모든 시간대에 동일한 세션당 요청 수를 적용했지만, 실제로는 시간대마다 사용자 행동 — 알림만 확인/재료검색까지 확인/재료 등록 — 의 비중이 달라 요청 수도 달라짐. 아래에서 세 가지 사용자 흐름별 요청 수와 시간대별 흐름 구성을 각각 정의한 뒤 가중평균으로 재계산함. 시간대 구간과 각 구간의 DAU 비율은 실제 푸시 알림 오픈율 벤치마크를 참고해 설정함(Airship 2021: Android 평균 4.6%, iOS 평균 3.4% — https://www.airship.com/resources/mobile-app-push-notification-benchmarks-2026/ / Business of Apps 2026 종합 — https://www.businessofapps.com/marketplace/push-notifications/research/push-notifications-statistics/).

- **세 가지 사용자 흐름과 흐름별 요청 수**: 실제 API 명세서(`스마트 냉장고 API 시트` — 재고 등록/마이페이지/추천 탭)와 팀 GitHub 위키 유저 플로우 차트(https://github.com/100-hours-a-week/KTB4-5th-wiki/wiki/유저-플로우-차트, V3 "3-2. 홈(MAIN)")를 반영해, 사용자 행동을 크게 세 가지 흐름으로 구분함 — B·C는 모두 A(홈 화면 진입)에 이어서 발생하는 누적 구조:

  | 흐름 | 포함 액션 | 요청 수 |
  |---|---|---|
  | **A. 알림 확인** | 토큰 확인/갱신 + 재고 통계 조회 + 만료 요약 조회 (홈 화면 진입까지) | **3회** |
  | **B. 재료검색** | A + 재고 상세 목록 조회 + 재료 검색 결과 조회 | **5회** |
  | **C. 재료 등록 — 수동 입력** | A + 재고 목록 조회 + 재고 일괄 등록 | **5회** |
  | **C. 재료 등록 — 영수증/사진 인식 (대표값)** | A + 사진 업로드 URL 요청 + 이미지 분석 요청 + 분석 결과 조회 + 일괄 등록 확정 | **7회** |

  - **A**는 재고 상태와 만료 요약 정보를 확인하는 홈 화면 진입까지만 도달하는, 가장 가벼운 흐름(v2는 AI 추천 기능이 없어 유저 플로우 차트 3-2의 추천 요약 영역·조회는 흐름에 포함하지 않음).
  - **C**는 API 명세서 '재고 등록' 탭 확인 결과 재고를 배열로 한 번에 등록하는 **일괄 등록** 방식이 있어, 등록하는 재료 개수와 무관하게 요청 수가 고정됨. 수동 입력(5회)과 영수증·사진 인식(7회) 두 경로 중, 인프라 용량 설계 관점에서는 더 무거운 영수증 인식 경로를 대표값(보수적 상한)으로 채택.
  - 조리 완료 처리(위 흐름에는 미포함)는 멱등성 있는 쓰기 액션으로, 매 세션이 아니라 실제로 요리를 완료했을 때만 발생해 별도 세션으로 보지 않음.
  - **알림 채널 확인**: 유저 플로우 차트 3-5에 "임박·만료 재고는 서비스 내부 알림, 추천 요리는 휴대전화 푸시 알림"으로 **두 채널이 분리**돼 있음을 확인했으나, 실제 발송 시각은 동시임을 팀에서 확인했으므로 아래 시간대별 흐름표의 "아침 알림 버스트" 하나로 계속 통합 모델링하며, 별도 버스트 구간은 두지 않음.

- **시간대별 흐름 구성(가정치)과 가중평균 요청 수**: 시간대마다 세 흐름의 비중이 다르다고 보고 아래처럼 가정함.
  - 이유: 아침 알림 버스트·오전 지연 반응은 아직 요리 시점 전이라 알림 확인 위주, 점심시간은 재료검색 비중이 늘고, 저녁 요리 준비는 재료검색이 압도적이며 재료 등록도 일부 섞임(퇴근길 장보기 후 저녁에 등록), 기타 분산 시간대는 재료 등록이 요일·시간에 매이지 않고 가장 많이 발생해 세 흐름이 고르게 섞임:

  | 시간대 | A. 알림 확인 | B. 재료검색 | C. 재료 등록 | 가중평균 요청 수 |
  |---|---|---|---|---|
  | 아침 알림 버스트 | 90% | 10% | 0% | 3.2회 |
  | 오전 지연 반응 | 80% | 20% | 0% | 3.4회 |
  | 점심시간 | 35% | 65% | 0% | 4.3회 |
  | 저녁 요리 준비 | 10% | 80% | 10% | 5.0회 |
  | 기타 분산 시간대 | 40% | 45% | 15% | 4.5회 |

  이 비중으로 계산한 주간 쓰기 세션 비율은 전체의 약 8%(읽기:쓰기 ≈ 11:1)로, 4번 항목에서 개인 경험으로 추정한 읽기:쓰기 비율(7:1~14:1) 범위 안에 들어와 흐름 구성 가정의 교차 검증이 됨. 흐름 비중 자체는 실측 데이터 없는 가정치라 실측 전까지 조정 가능함.

- **DAU(고유 사용자)와 접속 수의 관계**: DAU 115,000명은 하루 동안 접속한 **고유 사용자 수**로 중복 없이 집계됨. 반면 아래 시간대별 접속자 수는 같은 사용자가 하루에 여러 번 접속하면 그만큼 **중복 집계**됨 — 특히 아침 알림 즉시·지연 반응(DAU의 25%, 28,750명)한 사용자는 실제로 요리하는 시점인 저녁에 다시 접속해 재료를 검색할 가능성이 높음. 재접속률은 실측 데이터가 없어 **50%**로 가정해, 아침 알림 반응군의 절반인 14,375명이 저녁 세션에도 중복 집계되도록 반영함. 이 가정이 실제와 달라도 아침 알림 버스트 구간이 기준인 Peak CCU에는 영향이 없지만, 저녁 요리 준비 구간이 RPS 기준 Peak를 차지하는 지금 모델에서는 저녁 접속 수가 늘어날수록 Peak RPS도 함께 상향돼 이 가정이 곧 Peak RPS 산정에도 영향을 줌.

  | 시간대 | 윈도우 | 접속 수 | 가중평균 요청 수 | RPS |
  |---|---|---|---|---|
  | 아침 알림 버스트 (08:00~08:10) | 10분(600초) | 11,500 (DAU의 10%, 고유) | 3.2회 | 61.3 RPS |
  | 오전 지연 반응 (08:10~10:00) | ~2시간(7,200초) | 17,250 (DAU의 15%, 고유) | 3.4회 | 8.1 RPS |
  | 점심시간 (12:00~13:00) | 1시간(3,600초) | 11,500 (DAU의 10%, 고유) | 4.3회 | 13.7 RPS |
  | 저녁 요리 준비 (18:00~19:00) | 1시간(3,600초) | 54,625 (고유 40,250 + 아침 알림 반응군 재접속 14,375) | 5.0회 | 75.9 RPS |
  | 기타 분산 시간대 (나머지 하루) | ~19.8시간(71,400초) | 34,500 (DAU의 30%, 고유) | 4.5회 | 2.2 RPS |
  | 총 접속 수(중복 포함) | | 129,375 | | |
  | DAU(고유, 중복 없음, 참고) | | 115,000 | | |

  세션당 요청 수를 모든 시간대에 동일하게 6회로 적용했던 이전 모델에서는 접속 수는 적어도 윈도우가 좁은 아침 알림 버스트(10분)가 Peak였지만, 흐름별 가중평균 요청 수를 반영하면 결과가 달라짐. 아침은 알림만 확인하고 끝나는 가벼운 세션이 대부분이라 RPS가 61.3까지 낮아지고, 대신 재료검색이 몰리는 저녁 요리 준비 구간 — 접속 수도 가장 많은 54,625명, 가중평균 5.0회/세션 — 이 RPS 기준 Peak인 75.9로 바뀜.

  - 아침 알림 즉시반응 비율 10%는 벤치마크치인 4~8%보다 다소 높게 잡은 값으로, 실측 전까지는 조정 가능한 가정치임.
    - 이유: 유통기한 임박 알림은 프로모션성 푸시보다 행동 유발력이 강한 실용 정보라는 판단.

**결론 요약**

| 항목 | 값 | 비고 |
|---|---|---|
| 평균 RPS (하루 24시간 기준) | 약 7 RPS | 시간대 쏠림 미반영, 참고용 |
| 평시 RPS (ASG 최소 용량 기준) | 8~14 RPS | 오전 지연·점심시간대 수준 |
| Peak RPS (안전마진 적용 전) | 75.9 RPS | 저녁 요리 준비 구간(18~19시) 기준 |
| **설계 목표 Peak RPS (안전마진 25% 적용)** | **약 95 RPS** | 민감도 범위 약 91~99 RPS |

- **설계 목표 Peak RPS ≈ 95 RPS**
  - 이유: CCU 산정에 쓴 안전마진 25%를 RPS에도 동일하게 적용
- 민감도: 저녁 재료검색 비중 가정 80%가 ±10%p 달라지면 대략 약 91~99 RPS 범위. CCU 7,200명은 요청 수가 아니라 세션 수 기준이라 흐름별 요청 수 가정과는 별개로 산정됨.
- 전제조건: 시간대별 비율(아침 10%, 저녁 35% 등), 아침 알림 반응군의 저녁 재접속률 50%, 위 표의 시간대별 흐름 구성은 여전히 실사용 로그 없이 잡은 가정치이므로 재검증 필요. 흐름별 요청 수는 API 스펙+유저 플로우 차트 기반이라 근거가 탄탄해졌지만, 흐름 비중·시간대 비율을 다르게 잡으면 결과 RPS는 달라짐.
- **참고**: CCU도 이 흐름표를 그대로 재사용해 산정함 — 다만 RPS Peak(저녁, 약 95)와 CCU Peak(아침, 약 7,200)은 서로 다른 시간대를 가리킴.
  - 이유: CCU는 도착률 × 체류시간으로 정해지는 세션의 체류 시간에 좌우돼 짧고 좁은 아침 버스트(10분)가 순간적으로 가장 붐비고, RPS는 세션당 요청의 무게에 좌우돼 재료검색이 몰리는 저녁(1시간)이 더 무거움. 즉 ASG는 아침 버스트에는 동시 연결·세션 처리 용량을 CCU 기준으로, 저녁 구간에는 요청 처리량을 RPS 기준으로 각각 감당할 수 있어야 함 — 두 시간대 모두에 대한 Scheduled Scaling 적용을 팀 논의로 정할 필요가 있음.

#### 4. 읽기 쓰기 비율
- 읽기:쓰기 ≈ **7:1 ~ 14:1** 가정 ( 읽기 세션 7~14회/주 vs 쓰기 세션 1회/주 , 하루 1~2회)
  - 이유(개인 경험 기반): 주말에 한 번 장을 보고 그 재료로 한 주를 생활하는 패턴을 일반화 — 쓰기, 즉 재료 등록은 장보기 직후 주 1회 몰리는 버스트성 이벤트이고, 읽기, 즉 오늘 뭘 요리할지 확인하는 행동은 재료가 떨어질 때까지 매일 하루 여러 번 반복됨.
- 트레이드오프: 읽기 비중이 압도적이므로 DB Read Replica 우선순위가 높음. 캐시(Redis 등)도 반복 조회 결과에 효과적 — Read Replica는 일관성 유지가 쉽지만 비용↑, 캐시는 응답속도는 빠르지만 무효화 로직 복잡도고 상승함.

#### 5. Latency
- 목표(Good, SLO): API 응답시간(p50) **200ms 이하**
  - 이유: Google Core Web Vitals의 INP "Good" 기준 = 200ms 이하. 이상적으로는 100ms가 이론적 최적치이지만, 실사용 데이터 기준 100ms는 모바일 기기의 12%만 달성 가능한 반면 200ms는 모바일 56%/데스크톱 96%가 달성 가능해, 현실적으로 도달 가능하면서 좋은 사용감을 주는 기준으로 200ms를 채택함 (https://web.dev/articles/defining-core-web-vitals-thresholds)
- 마지노선(Hard limit): p95/p99 기준 **1000ms(1초) 이하**
  - 이유: RAIL 성능 모델상 "100~1000ms 구간은 작업의 자연스러운 흐름으로 느껴지는 범위이며, 1000ms(1초)를 넘어서면 사용자가 작업에 대한 집중력을 잃기 시작한다"(https://web.dev/articles/rail) — 1000ms 초과 요청은 SLO 위반으로 간주해 알림/모니터링 대상으로 설정
- 일단 마지노선부터 달성하고 최적화를 하면서 목표에 가까워지도록 할 계획임.
- OCR 기반 이미지 분석 API(영수증/사진 인식 경로의 "이미지 분석 요청")는 모델 추론 특성상 200ms/1000ms 기준을 적용할 수 없음 — 로딩 UI·비동기 처리(분석 진행 상태 표시, "분석 중" 상태 표시 등)로 체감 지연을 완화하는 방향으로 계획함.
- 트레이드오프: 200ms를 목표로 타이트하게 잡을수록 캐싱·CDN·서버 스펙 상향 등 비용이 늘어남.
- 위 목표·마지노선도 SLO의 일종 — 6번 에러율·7번 가용성 SLO와의 종합은 10번 참고.

#### 6. 에러율
- 에러율은 기존 운영 데이터가 쌓여야 명확하게 설정 가능한 영역이라, 지금은 간단하게 설계함
- 지표(SLI): HTTP 5xx 비율, 성공 요청 비율, 헬스체크 성공률
- 목표(SLO): 30일 기준 요청 성공률 99.9% 이상(에러율 0.1% 이하)

#### 7. 가용성 (MTBF, MTTR)
- 가용성도 기존 운영 데이터가 쌓여야 명확하게 설정 가능한 영역이라, 지금은 간단하게 설계함
- 목표 가용성 예시: 99.9%(월 다운타임 약 43분 이내)
- MTTR 단축: v1에서 설계한 Health Check + Rollback 자동화(3단계 CD 문서 참고)를 확장해 장애 감지~복구 시간 최소화
- MTBF 향상: v1의 단일 EC2(SPOF) 구조에서 벗어나 Multi-AZ + Auto Scaling Group으로 이중화 필요
- 목표 가용성도 SLO의 일종 — 5번 Latency·6번 에러율 SLO와의 종합은 10번 참고.

#### 8. 확장성
- v1(Docker Compose 단일 EC2) 구조에서 오토스케일링이 가능한 구조로 전환 필요
- 후보 방향(트레이드오프 비교, 최종 선택은 팀 논의 필요):
  - **EC2 + Auto Scaling Group + ALB**: 기존 Docker 기반 구조를 크게 바꾸지 않고 확장 가능. 다만 인스턴스 관리·배포 자동화를 직접 운영해야 하는 부담
  - **ECS(Fargate 또는 EC2 launch type)**: 컨테이너 오케스트레이션을 AWS가 관리해 운영 부담↓, 다만 AWS 종속성↑ 및 학습 비용 발생
  - **EKS(Kubernetes)**: 가장 유연하고 생태계가 넓지만 러닝커브·운영 복잡도가 가장 높아 소규모 팀에는 과잉일 수 있음
- DB 확장성: v1은 EC2에 직접 MySQL을 구동 중이며, 확장 방향으로 아래 두 후보를 고민 중 — 트레이드오프 비교, 최종 선택은 팀 논의 필요:
  - **RDS 전환**: Multi-AZ·Read Replica·백업 등을 AWS가 관리형으로 대신 운영해 운영 부담↓, 다만 자체 구축 대비 비용이 더 들 수 있고 세부 튜닝 자유도는 낮음
  - **직접 DB 구축**: v1처럼 EC2에서 직접 운영하며 Multi-AZ(자체 Standby)·Read Replica까지 직접 구성. 비용 절감 여지는 크지만 복제·장애조치·백업 등을 직접 운영해야 하는 부담

#### 9. 서비스의 트래픽 특성 (앞선 항목의 정리)
- 2·3번 항목의 시간대별 흐름 기준으로 RPS Peak와 CCU Peak가 서로 다른 시간대에서 나타남:
  - 순간 RPS 기준 Peak: 저녁 요리 준비 시간대(18~19시, DAU의 35%)로, 접속 수가 가장 많음. 윈도우는 1시간으로 넓지만 재료검색 비중이 압도적이라 세션당 요청 수가 가장 무거움 — 3번 항목의 Peak RPS 산정 근거.
  - 순간 CCU 기준 Peak: 유통기한 임박 알림(Push) 발송 직후 아침 버스트(08:00~08:10, DAU의 10%) — 윈도우가 10분으로 좁아 순간 동시접속자가 가장 많음, 다만 세션 대부분이 알림 확인에서 끝나 요청 수는 가벼움. 2번 항목의 Peak CCU 산정 근거.
- 주간 패턴: 쓰기(재료 등록)는 주말 장보기 직후 주 1회 몰리는 버스트, 읽기(냉장고 확인·재료검색)는 매일 반복 — 4번 읽기 쓰기 비율 항목 참고.
- 종합: 다먹자의 트래픽은 예측 가능한 특정 시각(알림 발송 시각, 저녁 시간대, 주말)에 집중되는 스파이크형 패턴을 가짐
- 트레이드오프: 예측 가능한 피크 — 저녁 시간대, 알림 발송 시각 — 는 스케줄 기반 사전 스케일링(Scheduled Scaling)으로 대응 가능함. 구현이 단순하고 리소스를 미리 준비해 반응 지연이 없지만, 예측이 어긋나면 과잉·과소 프로비저닝 위험이 있음. 그 외 돌발 스파이크는 지표 기반 동적 스케일링(Dynamic Scaling, 예: Target Tracking)으로 대응해야 함. 예측 없이도 실측 지표로 유연하게 대응할 수 있지만, 지표 감지·반응까지 지연이 존재함. 두 전략을 함께 쓰는 것을 검토 — 3번 항목의 결론과 연결.

#### 10. SLI·SLO 종합 (5·6·7번의 정리)
- SLI/SLO는 에러율 같은 특정 지표 하나에 국한된 개념이 아니라, 여러 지표에 공통으로 적용하는 신뢰성 목표 프레임워크임: **SLI**는 측정하는 지표 자체, **SLO**는 그 지표의 내부 목표치를 뜻하며 SLI → SLO 순서로 이어짐. 5·6·7번에서 각각 정의한 latency·에러율·가용성 목표를 이 틀로 모아 정리함:

  | 지표 | SLI(측정 대상) | SLO(목표치) | 출처 |
  |---|---|---|---|
  | Latency | API 응답시간(p50, p95/p99) | p50 200ms 이하(목표) / p95·p99 1000ms 이하(마지노선) | 5번 |
  | 에러율 | HTTP 5xx 비율, 요청 성공률 | 30일 기준 요청 성공률 99.9% 이상(에러율 0.1% 이하) | 6번 |
  | 가용성 | 가동률(Uptime) | 99.9% 이상(월 다운타임 약 43분 이내) | 7번 |

- SLA는 대외 계약까지 요구되는 수준이라 지금 단계에서 설정하기엔 이르다고 판단해 이번 설계 범위에서는 제외함 — 추후 B2B 제휴나 외부 API 제공 등이 필요해지면 그때 별도로 검토.
- 트레이드오프: 세 SLO를 한꺼번에 타이트하게 잡을수록 — 가용성↑, latency↓, 에러율↓ — 캐싱·이중화·모니터링 등 비용·운영 복잡도가 함께 늘어남. 반대로 느슨하게 잡으면 비용은 아끼지만 사용자 경험·신뢰도 저하 위험이 있음. 초기에는 마지노선(1000ms, 99.9% 등) 달성을 우선하고, 운영 데이터가 쌓이면 점진적으로 목표(Good) 수준까지 좁혀가는 방향으로 계획 — 5·6·7번 결론과 연결.
- 실사용 데이터 없이 잡은 가정치이므로 출시 후 실제 운영 로그 기반 재검증 필요.
