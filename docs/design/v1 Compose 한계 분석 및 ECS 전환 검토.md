# v1 Compose 운영 한계 분석 및 ECS 전환 검토

> 기준: v1 운영 중(2026-10-06) 작성한 분석. v1은 이 분석을 바탕으로 v2(ECS)로 전환한 뒤(dev 2026-10-09~11, prod 2026-10-19) 종료했다.

작성일: 2026-10-06  
대상: v1 EC2 + Docker Compose 운영 구조  
목적: v1 운영 중 겪은 컨테이너 관리의 불편함과 향후 서버·서비스 확장 시 증가하는 운영 부담을 정리한다.

## 1. v1 운영 구조

- dev·prod 모두 앱 EC2 한 대에서 nginx·FE·BE를 Compose로 실행하고, MySQL은 별도 DB EC2에 둔다. 상세 구성은 [1단계 위키](wiki/ktb4-cloud-wiki-v1.md)를 따른다.
- dev·prod의 Compose 파일을 GitHub에서 각각 관리하고 EC2 배포 디렉터리에 반영한다.
- FE·BE 배포는 GitHub Actions가 SSH로 서버의 배포 스크립트를 실행하는 방식이다.
- 배포 스크립트에는 이미지·서비스 환경 설정 갱신, 헬스체크, 실패 시 이전 이미지·환경 설정으로 복구하는 기능이 있다.
- Compose·nginx 설정과 인증서, 로그 폴더 권한, CloudWatch Agent 등은 서버에 적용된 상태를 함께 관리한다.

## 2. 한계 분석

### 2.1 설정 원본과 서버 적용 상태를 별도로 관리

- GitHub에서 Compose·nginx 설정을 변경한 뒤 EC2에도 반영해야 한다. 파일 수정뿐 아니라 해당 서버에 어떤 설정이 적용됐는지까지 확인해야 하는 번거로움이 있다.
- 확인한 FE·BE 배포 경로는 서버에 존재하는 Compose 파일을 사용한다. 앱 이미지 배포와 인프라 설정 반영이 분리되어 있어, 앱 배포 성공만으로 최신 설정 적용 여부를 알 수 없다.
- 서버에서 별도로 수정하거나 반영을 누락하면 원본과 실행 환경이 달라질 수 있다. 실제 불일치 발생은 확인하지 않았지만, 두 상태를 대조하는 관리 부담이 있다.

### 2.2 dev·prod의 유사한 설정을 중복 관리

- 서비스 이미지, 헬스체크, 로그 마운트 등 공통 설정을 환경별 파일에서 각각 관리한다. 공통 항목을 변경할 때 두 파일을 수정하고 차이를 확인해야 한다.
- 도메인·인증서·환경 변수·재시작 정책처럼 필요한 환경 차이와, 누락으로 생긴 차이를 구분해야 한다.
- 서비스와 설정 항목이 늘어나면 환경별 수정·검토 범위도 함께 증가한다.

### 2.3 설정 변경 이후 컨테이너 반영을 별도로 수행

- Compose 파일을 수정해도 실행 중인 컨테이너에 자동으로 반영되지 않는다. 환경 변수·볼륨·포트 변경은 컨테이너 갱신이 필요하며, 단순 `restart`로는 변경된 Compose 설정이 적용되지 않는다.
- nginx 설정 변경도 실행 중인 프로세스에 반영하는 별도 절차가 필요하다. 운영자는 파일 변경과 함께 적용 대상·순서·정상 동작을 확인해야 한다.
- 앱 이미지와 서비스 환경 설정 배포는 자동화되어 있지만, 인프라 설정 변경까지 모두 같은 경로에서 처리하는 구성은 확인되지 않았다. 이 부분은 여전히 직접 반영하고 확인하는 부담으로 남아 있다.

### 2.4 서버 단위 관리로 인한 확장 부담

- v1은 각 EC2에서 Compose를 실행하는 구조이므로, 서비스 전체 상태를 파악하려면 서버별 실행 상태와 설정을 확인해야 한다.
- 서버가 늘어나면 컨테이너 배치, 설정 일치 여부, 배포 순서, 트래픽 분산을 여러 서버에 걸쳐 관리해야 한다. v1 Compose 구성에는 이를 통합 관리하는 스케줄러가 없다.
- 트래픽 변화에 따른 컨테이너 수 조정과 배치도 별도 관리 대상이다. 단일 서버의 컨테이너 관리에서 여러 서버의 서비스 관리로 확대될수록 운영 부담이 커진다.
- 이는 향후 확장을 고려한 구조적 한계다. 기존 7RPS·5분 테스트만으로 v1 서버의 처리량 부족이나 즉각적인 확장 필요성이 입증된 것은 아니다.

### 2.5 배포·장애 대응의 자체 관리 범위 증가

- v1 배포 스크립트가 설정 검증, 배포 잠금, 헬스체크와 롤백을 처리한다. 서비스와 서버가 늘어나면 이러한 절차의 적용 범위와 예외 처리도 늘어난다.
- 단일 서비스 컨테이너를 교체하는 동안 요청 처리 공백이 발생할 수 있다. 2026-10-04 부하테스트에서 BE 교체 시각과 겹쳐 CSRF 502가 1건 발생했고, 배포 직후 로그인 응답시간 847.38ms가 관측됐다. 배포 영향 가능성은 높지만 개별 지연 원인은 확인하지 못했다.
- prod의 `restart: unless-stopped`는 프로세스 종료 등에 대한 재시작을 지원하지만, 실행 중인 컨테이너가 `unhealthy`가 됐을 때 자동 교체하거나 다른 서버에 재배치하지 않는다.
- EC2 중단·교체 시에는 인증서·로그 경로·권한·모니터링 설정 등 서버 준비 작업도 필요하다. 서비스 배치와 복구를 서버 단위로 관리하는 부담이 남는다.

## 3. 한계의 정의

- v1의 한계는 설정 파일을 수정한다는 사실 자체보다, 설정 변경 이후 서버 반영·컨테이너 갱신·상태 확인을 서버별로 관리해야 하는 데 있다.
- 설정 중복과 수동 반영은 Compose에서도 개선 가능하다. 다만 자동화 범위를 넓힐수록 자체 스크립트와 운영 절차의 유지보수 책임도 증가한다.
- ECS 전환을 검토하는 주된 이유는 v1의 컨테이너 관리 부담을 줄이고, 향후 여러 서버에 걸친 배치·수량·상태 관리를 서비스 단위로 확장하기 위해서다. Blue-Green 배포는 별도로 선택할 배포 방식이다.
