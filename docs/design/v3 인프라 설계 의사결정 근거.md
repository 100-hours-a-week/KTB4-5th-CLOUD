## 1. 설계 방향과 요구사항

### 1.1 Kubernetes 도입

**결정 요약**: AWS, GCP에서 애플리케이션 배포 정의와 운영 절차를 재사용하기 위해 Kubernetes를 공통 플랫폼으로 선택하고, AWS에서는 ECS를 EKS로 전환하기로 했습니다.

**이유**

- **배포 정의, 운영 절차 재사용** — AWS에서 ECS를 유지하고 GCP에 별도 운영 플랫폼을 두면 배포 정의와 운영 절차를 각각 관리해야 하므로, Kubernetes와 Helm, GitOps를 공통 기준으로 사용하기로 했습니다.
- **관리형 서비스 활용** — AWS 서비스의 종속성을 모두 제거하기보다 서비스별 연동 변경을 감수하고 공통 운영 기준을 확보하기로 했습니다.

**근거**

- **기존 대안과 비교** — 독립 배포, 자원 제한, 자동 확장은 ECS에서도 구성할 수 있는 것으로 검토했습니다. AWS만 운영한다면 ECS 유지가 가능한 선택이지만, 배경에서 정한 두 클라우드의 공통 운영을 선택 기준으로 삼았습니다.
- **도구의 역할 구분** — 공통 배포, 권한, 운영 기준은 Kubernetes, Helm, Argo CD로 관리하고, Karpenter와 AWS 네트워크, 스토리지 연동은 AWS 환경에 맞춘 구성으로 구분했습니다.

**트레이드오프**

- **전환, 유지관리 부담** — 기존 배포 정의를 Kubernetes 자원으로 옮기고 클러스터, Controller, 구성요소의 호환성을 관리하는 부담을 감수했습니다.
- **효과 검증** — 배포 정의, 운영 절차의 재사용과 장애 대응 효과는 구축 후 검증하기로 했습니다.

## 2. 전체 인프라 아키텍처

### 2.1 AWS 배치 범위

**결정 요약**: AWS 서울 리전을 사용하고 앱, 시스템 Node와 MySQL Primary는 단일 AZ에 배치하기로 했습니다.

**이유**

- **기존 운영 기반 활용** — 국내 사용자 접근과 기존 AWS 인프라의 위치를 고려해 서울 리전을 선택했습니다.

**트레이드오프**

- **AZ 장애 수용** — 해당 AZ에 장애가 발생하면 앱, DB가 중단될 수 있는 위험을 감수했습니다.

### 2.2 기존 인프라 유지, 변경

**결정 요약**: 기존 prod VPC, Subnet, NAT Gateway, Node 사양(`m7i.large`), OS 계열(AL2023)과 운영 경험을 활용했습니다. MySQL, PostgreSQL 데이터는 유지하되 stage, prod는 v3 IaC로 만든 새 DB EC2로 옮겼고, dev는 기존 dev DB EC2를 그대로 사용합니다.

**이유**

- **전환 범위 제한** — Kubernetes 전환과 직접 관련된 변경에 집중하고 기존 인프라를 활용하기로 했습니다.
- **v2 스택과 수명 분리** — v2 stage DB는 v2 `dameokja-stage` 스택에 묶여 있어 v2를 정리하면 함께 사라지므로, v3 IaC로 DB EC2를 따로 만들고 데이터를 한 번 옮기기로 했습니다(#256). prod DB도 같은 구성으로 만들어 v2 prod DB의 데이터를 `migrate-db.sh`로 옮겼습니다(#302, #305).

**트레이드오프**

- **기존 제약 유지** — 재사용하는 자원의 주소 용량과 자원 여유가 EKS 운영에 충분한지는 별도로 확인하기로 했습니다.
- **데이터 이전 작업** — stage, prod 전환 때 덤프, 복원과 표별 행 수 대조를 별도로 수행하는 부담을 감수했습니다.

### 2.3 Kubernetes 전환 범위

**결정 요약**: 실행 환경, AMI, 클러스터 등록, 권한, 확장 연동은 EKS에 맞춰 변경했습니다. 기존 v2 ALB는 인계하지 않고 AWS Load Balancer Controller가 새 internal ALB `dameokja-v3-gateway`를 만들도록 했습니다.

**이유**

- **실행 환경 변경 반영** — OS를 유지하더라도 ECS용 AMI와 등록, 배포 설정은 EKS용 AL2023 EKS 최적화 AMI와 nodeadm 초기화로 변경했습니다.
- **v2 자원과 권한 분리** — Controller의 리스너, 규칙, Target 변경 권한을 v3 ALB와 `dameokja-v3-*` Target Group으로 좁혀, 같은 계정의 v2 stage, prod ALB에 닿지 않도록 했습니다(#232).

**트레이드오프**

- **전환 기간의 이중 진입점** — 전환 동안 v2 ALB와 v3 ALB를 함께 두고 Route 53 가중치 레코드로 트래픽을 옮기는 절차를 감수했습니다. v2 ALB는 전환 뒤 삭제했습니다(#321).

### 2.4 VPC와 Pod 네트워크

**결정 요약**: 기존 prod VPC `10.20.0.0/16`, Subnet, NAT Gateway를 재사용하고 Amazon VPC CNI를 사용하기로 했습니다.

**이유**

- **기존 네트워크 활용** — VPC, Subnet, NAT Gateway를 재사용하여 네트워크 전환 범위를 줄이기로 했습니다.
- **외부 통신 유지** — Private Node의 GHCR 이미지 다운로드와 RunPod 등 외부 서비스 호출은 기존 NAT Gateway를 경유하도록 정했습니다.
- **초기 운영 부담 축소** — AWS 기본 연동을 활용하고 별도 CNI의 설치, 운영 범위를 추가하지 않기로 했습니다.

**근거**

- **EKS 생성 요건** — 앱, DB의 배치 AZ 수와 별개로 클러스터 생성 시 서로 다른 2개 AZ의 Subnet이 필요하여 유지하기로 했습니다.
- **ALB 구성 요건** — Internal ALB에도 서로 다른 2개 AZ의 Subnet이 필요하므로, DB의 AWS Multi-AZ 대기 구성 여부와 별개로 해당 Subnet을 유지하기로 했습니다.

**트레이드오프**

- **Pod IP 용량 검증** — 확장, 배포 중 필요한 Pod IP 수요와 Subnet의 주소 여유를 함께 검증하기로 했습니다.

**출처**

- [EKS VPC, Subnet 요구사항](https://docs.aws.amazon.com/eks/latest/userguide/network-reqs.html)
- [ALB Subnet 요구사항](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/application-load-balancers.html#subnets-load-balancer)

#### NetworkPolicy와 Pod별 보안그룹

**결정 요약**: 환경 간 Pod 통신은 NetworkPolicy로 제한하고, Security Groups for Pods를 도입해 환경, 서비스별 SG를 연결하기로 했습니다. 서비스별 통신 허용표는 설계서 2.4절에서 관리하기로 했습니다.

**이유**

- **공유 Node의 접근 권한 구분** — BE와 AI API가 같은 Node에 배치되더라도, DB SG에서 같은 환경의 BE Pod SG는 MySQL에, AI API Pod SG는 PostgreSQL에만 접근하도록 허용하기로 했습니다.
- **환경 간 접근 제한** — 같은 Namespace 내부에서도 필요한 서비스 연결만 허용하고, 다른 환경의 앱, DB, Kafka 접근은 차단하기로 했습니다. DNS, 상태 점검, 관측과 관리 통신은 운영에 필요한 예외로 구분했습니다.
- **변경 관리 범위 구분** — AWS SG는 환경별 `<환경>-pod-sg` CloudFormation 스택으로 관리합니다. 환경별 NetworkPolicy와 SecurityGroupPolicy는 `platform` Helm 차트에서 `environments`(dev, stage, prod) 값으로 렌더링하고, 관리자 PC에서 Helm으로 적용합니다.

**근거**

- **Pod별 SG 연결** — SecurityGroupPolicy의 Pod 선택자로 환경, 서비스별 SG를 지정했습니다. Pod가 이동하거나 Replica가 증가해도 같은 서비스 권한을 적용할 수 있어, 환경 안에서는 NodePool을 서비스별로 나누지 않았습니다.
- **NetworkPolicy 병행** — VPC CNI의 standard 모드에서 Pod별 SG와 NetworkPolicy를 함께 적용했습니다. VPC 외부 송신은 기본 SNAT 구성에서 Node SG가 적용되므로, RunPod 등 외부 HTTPS 허용은 Pod의 Egress 정책과 함께 관리합니다. VPC 안 DB로 가는 연결은 SNAT 예외로 Pod IP를 유지하여 DB SG가 Pod SG를 구분하도록 했습니다(#220, #226).
- **Kubernetes API 송신 예외** — Strimzi Kafka 브로커와 Entity Operator는 시작할 때 API에서 Secret을 읽습니다. NetworkPolicy는 바뀌기 전의 kubernetes Service 주소로 판단하므로, Kafka 송신 정책에 API Subnet 443과 Service 주소 `192.168.0.1/32`의 443을 함께 열었습니다(#222, #224, #276). 브로커가 3개인 stage, prod는 브로커 사이 9090, 9091도 허용합니다.

**트레이드오프**

- **추가 네트워크 관리** — Pod ENI 활성화, IAM 권한, 지원 인스턴스, branch ENI와 IP 수용량을 관리하고 Pod 생성 지연, SG와 NetworkPolicy 규칙의 불일치를 검증하는 부담을 감수했습니다.
- **AWS 연동 유지** — 표준 NetworkPolicy는 공통 통신 규칙으로 유지하되, Pod별 SG와 DB의 SG 참조 규칙은 다른 환경으로 이전할 때 재구성이 필요함을 수용했습니다.
- **외부 송신 제어 범위** — 외부 TCP 443 허용은 도메인별 접근 제한을 보장하지 않으므로, 특정 외부 도메인만 허용하는 정책과 구분했습니다.

#### Service Mesh 미도입

**결정 요약**: 초기 구성에는 Service Mesh를 도입하지 않기로 했습니다.

**이유**

- **현재 통신 제어 요구 충족** — 환경 간 통신 격리와 서비스별 연결 제한은 NetworkPolicy와 보안그룹으로 구성하기로 했습니다.
- **도입 판단 기준** — MSA 여부만으로 Service Mesh 도입을 결정하지 않고, 서비스 간 통신 관계의 복잡성과 인증서, 접근 정책, 요청 제어를 공통으로 관리할 필요성을 기준으로 삼았습니다.
- **추가 기능의 필요성 부족** — 서비스 간 mTLS, 신원 기반 접근 제어, 세밀한 요청 라우팅을 공통 계층에서 관리할 필요가 아직 크지 않아, 프록시와 관리 프로그램의 자원, 버전, 정책을 추가로 운영할 부담을 정당화하기 어렵다고 판단했습니다.

**트레이드오프**

- **통신 기능의 공통 관리 범위 제한** — NetworkPolicy와 보안그룹은 Service Mesh의 mTLS나 HTTP 요청 제어를 대신하지 않으므로, 해당 기능을 공통으로 제공하는 계층은 두지 않기로 했습니다.
- **mTLS와 도입 여부 구분** — mTLS는 Service Mesh 없이도 구성할 수 있으므로, 서비스 수와 별개로 통신 상대 인증과 암호화가 필요한 구간이 생기면 적용 방식을 별도로 검토하기로 했습니다.

**출처**

- [Istio 구성 요소와 운영 구조](https://istio.io/latest/docs/ops/deployment/architecture/)
- [Istio 통신 보안 기능](https://istio.io/latest/docs/concepts/security/)

### 2.5 데이터 배치

#### MySQL 배치 비교

**결정 요약**: MySQL은 환경별로 Kubernetes 외부 EC2에서 운영하고 DB 계정, 데이터를 분리했습니다. stage, prod는 EKS VPC Private Subnet 2b에 새 DB EC2(`stage-db`, `prod-db`, t3.medium, MySQL 8.4 GTID)를 두고, dev는 기본 VPC의 기존 dev DB EC2를 VPC Peering으로 연결해 사용합니다.

**이유**

- **기존 운영 경험 활용** — 자체 구축 MySQL의 운영 경험을 활용하고 DB를 Kubernetes 수명주기와 분리하기로 했습니다.
- **환경별 데이터 분리** — dev, stage의 개발, 검증 요청이 prod 업무 데이터에 영향을 주지 않도록 환경별 DB를 유지하기로 했습니다.
- **v3 IaC로 수명 관리** — v2 stage DB는 v2 스택과 함께 지워지므로 stage DB를 v3 스택으로 새로 만들었고(#256, #257), prod DB도 같은 구성과 v2 prod DB와 같은 크기로 만들었습니다(#302). 두 서버 모두 종료 보호와 스택 삭제, 교체 시 보존(Retain)을 적용했습니다.
- **DB 접근 제한** — DB SG는 같은 환경의 BE Pod SG에 3306을, AI Pod SG에 5432를 허용합니다.

**근거**

- **대안 비교** — Kubernetes 내부 운영에는 Operator, PVC, 스토리지 복구 구성이 추가되어 초기 운영 범위가 커진다고 판단했습니다.

**트레이드오프**

- **별도 서버 운영** — DB 서버의 운영, 복구는 Kubernetes 워크로드 관리와 별도로 담당하기로 했습니다.
- **AWS 내부 장애 전환 제외** — prod는 Primary 1대이며 AWS 내부의 별도 Multi-AZ Standby는 두지 않아, 인스턴스, AZ 장애 시 AWS 내부의 자동 DB 장애 전환을 제공하지 않는 것으로 정리했습니다.

#### PostgreSQL 배치 근거

**결정 요약**: AI용 PostgreSQL은 각 환경의 MySQL과 같은 DB용 EC2에서 별도 엔진으로 실행합니다. stage, prod는 PostgreSQL 16, dev는 기존 dev DB EC2에 새로 설치한 Ubuntu 기본 PostgreSQL 18입니다.

**이유**

- **DB 서버 운영 통합** — PostgreSQL 전용 EC2를 추가하지 않고 환경별 DB 서버에서 함께 관리하기로 했습니다.
- **Pod 접근 경로 확보** — v2 dev의 PostgreSQL은 AI EC2의 127.0.0.1에서만 받아 Pod가 닿을 수 없었으므로, dev DB EC2에 PostgreSQL을 설치하고 데이터를 옮겼습니다(#225, #226).
- **기존 데이터 역할 유지** — BE의 MySQL과 AI의 PostgreSQL을 유지하고 엔진별 계정, 데이터 경로와 연결 설정을 구분하기로 했습니다.

**트레이드오프**

- **자원, 장애 영향 공유** — MySQL과 PostgreSQL이 CPU, 메모리, 디스크를 공유하고 같은 EC2 장애에 영향을 받는 부담을 감수했습니다. 두 엔진의 합산 부하를 기준으로 서버 용량을 검증하기로 했습니다.

#### Redis 배치 근거

**결정 요약**: Redis는 dev, stage, prod Namespace에 각각 단일 Replica StatefulSet과 전용 PVC로 배치하고, v2 prod의 AOF 정책을 유지하기로 했습니다.

**이유**

- **Pod 운영 정책과 통합** — Redis의 재시작과 자원 관리를 Kubernetes에서 함께 관리하고, 재생성된 Pod가 같은 PVC의 AOF를 읽도록 구성하기로 했습니다.
- **환경별 상태 분리** — v2의 환경별 Redis 사용 구조를 유지하기로 했습니다.
- **서비스 상태 유지** — Redis는 단순 조회 캐시 외에 Refresh Token과 회전, 폐기 상태, AI 작업 상태를 저장하므로, 매번 빈 상태로 기동해 로그인 갱신과 작업 조회에 영향을 주는 구성을 피하기로 했습니다.

**근거**

- **v2 구성 확인** — prod Redis의 실제 설정에서 `appendonly yes`, `appendfsync everysec`와 호스트 디렉터리의 `/data` 연결을 확인했습니다. v3에서는 이를 PVC와 EBS 연결로 옮기기로 했습니다.
- **저장 데이터 확인** — 보관된 BE `origin/main` 코드에서 RedisRefreshSessionStore의 로그인 세션, 토큰 회전과 폐기 상태 저장, AnalysisJobStore의 분석 작업 저장과 AnalysisPendingNotificationStore의 알림 재확인 대상 저장을 확인했습니다. 유효기간이 있는 데이터도 그 기간 안의 재시작에서는 유지할 필요가 있다고 판단했습니다.
- **데이터 역할 구분** — DB의 업무 데이터, Kafka의 작업 이벤트와 Redis의 서비스 상태는 구분했습니다. Kafka 도입만으로 Redis의 인증 상태나 작업 조회 상태가 자동 복원되지는 않는 것으로 정리했습니다.
- **단일 구성의 범위** — 단일 Pod는 전체 환경이 공유하는 1개가 아닌 환경별 1개로 정했습니다.
- **동적 볼륨 공급** — StatefulSet의 volumeClaimTemplates로 환경별 PVC를 요청하고, EBS CSI Driver가 gp3 EBS와 PV를 공급하도록 정했습니다. WaitForFirstConsumer로 Pod 배치 AZ와 디스크 AZ를 맞추고, 초기 용량은 환경별 10Gi로 시작해 사용량에 따라 확장하기로 했습니다.
- **저장소 보존** — StatefulSet의 PVC 보존 정책과 PV 반환 정책을 Retain으로 지정하여 재배포, Pod 재생성과 볼륨 삭제의 수명을 구분하기로 했습니다. 공급한 EBS를 CloudFormation에서 중복 관리하지 않기로 했습니다.

**트레이드오프**

- **저장소 관리 부담** — EBS CSI, PVC, 같은 AZ의 볼륨 재연결과 AOF 파일 용량을 관리하는 부담을 감수했습니다.
- **보존 자원 정리** — Retain 정책으로 남은 PV와 EBS는 자동으로 삭제되지 않아 비용이 계속 발생하므로, 환경 폐기 시 Cloud 팀이 수동 정리하는 부담을 감수했습니다.
- **복구 보장 범위** — AOF는 단일 Redis의 복원 수단이며 고가용성과 완전한 무손실을 보장하지 않습니다. everysec 동기화의 장애 직전 쓰기 유실 가능성과 볼륨 손실, 복원 중 서비스 중단은 남는 것으로 정리했습니다. Redis Pub/Sub 메시지는 AOF의 재전송 대상이 아닌 것으로 구분했습니다.

**이유**

- **관리 대상 제한** — 환경별 클러스터를 따로 운영하는 대신 하나의 클러스터에서 환경별 Namespace를 관리하기로 했습니다.

#### AWS: EKS 선택

**결정 요약**: Control Plane은 kubeadm으로 직접 구축하지 않고 EKS에 맡기기로 했습니다.

**이유**

- **Cloud 팀의 운영 범위 조절** — 전환 일정 안에서 Node, 워크로드, 배포 운영에 집중하기로 했습니다.

**근거**

- **kubeadm과 비교** — 직접 구축 시 Control Plane, etcd의 구축, 업그레이드, 백업, 장애 복구까지 담당해야 하는 점을 비교했습니다.

**트레이드오프**

- **서비스 의존성 수용** — Control Plane 운영을 EKS에 맡기는 대신 해당 관리형 서비스에 대한 의존성을 감수했습니다.

### 3.2 Worker Node 운영 구조

**결정 요약**: 앱 Node는 Karpenter로 공급하고 EKS Auto Mode 대신 Karpenter를 직접 운영하기로 했습니다.

**이유**

- **Node 공급 정책 구성** — ASG, Cluster Autoscaler 방식과 비교해 Pod의 자원, 배치 조건에 맞춰 Node를 공급하는 구성을 선택했습니다.
- **구축, 운영 학습** — Node 공급, 교체와 AMI, 구성요소 업데이트, 장애 분석을 직접 경험하는 범위를 확보하기로 했습니다.
- **추가 관리 요금 절감** — Auto Mode의 추가 관리 요금을 줄이기로 했습니다.

**트레이드오프**

- **직접 운영 비용** — Controller의 실행 자원과 유지관리, 장애 대응에 필요한 인력 비용은 부담하기로 했습니다.

#### Karpenter 실행 기반

**결정 요약**: Karpenter, Argo CD, Sealed Secrets Controller, Strimzi Cluster Operator와 Load Balancer Controller, CoreDNS, Metrics Server, kube-state-metrics, Strimzi Topic Operator는 시스템용 Self-managed EC2(`m7i.large`, AL2023) 한 대에서 실행하고, ASG 없이 상시 운영합니다.

**이유**

- **실행 기반 확보** — Karpenter Controller가 자신이 앞으로 생성할 앱 Node에 의존하지 않도록 시스템용 Node를 별도로 두기로 했습니다.
- **초기 구성 단순화** — 시스템용 EC2 한 대를 유지하는 현재 범위에서는 ASG의 대수 유지, 교체 자동화를 추가하지 않기로 했습니다.
- **관리 범위 구분** — 시스템용 EC2는 Cloud 팀이 직접 운영하고 앱 Node는 Karpenter가 ASG 없이 공급하도록 정했습니다.
- **운영 절차 통제** — Self-managed Node의 초기화, 업데이트, 교체 절차를 직접 구성하기로 했습니다.

**트레이드오프**

- **Node 유지관리 책임** — AMI, 보안 패치, 클러스터 등록, Node 장애 복구는 직접 관리하기로 했습니다.
- **수동 복구와 단일 장애점** — 시스템용 EC2 장애 시 Cloud 팀이 복구, 교체와 클러스터 재등록을 수행하기로 했습니다. 복구 전에는 신규 앱 Node 공급, GitOps 배포, SealedSecret 공급과 Strimzi의 Kafka 구성 조정이 중단되는 부담을 감수했습니다. CoreDNS도 이 Node에 1개만 있어 클러스터 DNS 조회가 함께 멈출 수 있습니다. 기존 앱 Pod와 Secret이 함께 삭제되는 것은 아닌 것으로 구분했습니다.
- **클라우드 연동 유지** — EC2, IAM과 Node 초기화 설정은 다른 환경으로 이전할 때 변경할 대상으로 남겼습니다.

### 3.3 애플리케이션용 NodePool

**결정 요약**: 앱 NodePool을 환경별 `dev-app`, `stage-app`, `prod-app`으로 나누고, 환경 안에서는 FE, 통합 BE, AI API, Redis, Kafka가 같은 NodePool을 공유합니다. 세 NodePool 모두 `m7i.large`, AZ 2b, On-Demand이며, `stage-app`, `prod-app`은 환경 라벨 `dameokja.com/environment`와 NoSchedule taint로 해당 환경 Pod만 받습니다. 상한은 `dev-app` CPU 26, 메모리 104Gi, `stage-app`, `prod-app` 각각 CPU 16, 메모리 64Gi입니다.

**이유**

- **환경별 켜기, 끄기** — stage를 끌 때 stage Node만 0대로 줄도록 dev와 Node를 나눴습니다(#258, #259).
- **prod 배치 격리** — prod는 stage와 같은 사양, 상한의 `prod-app`을 두고 taint로 dev, stage Pod가 prod Node에 올라가지 않게 했습니다(#304).
- **환경 안의 운영 대상 축소** — 워크로드별 NodePool을 별도로 관리하는 대신 환경 안에서는 공통 NodePool을 사용하기로 했습니다.
- **GPU 실행 분리** — EKS에는 AI API 서버를 배치하고 GPU 모델 실행은 외부 RunPod에 맡기기로 했습니다.

**근거**

- **상한의 범위** — 상한은 상시 유지 대수가 아닌 공급 상한입니다. `dev-app`의 CPU 26은 초기 검토안의 앱 Node 상한 13대(`m7i.large` 2 vCPU 기준)를 유지한 값이고, `stage-app`, `prod-app`의 CPU 16은 평시 FE, BE 각 2, AI API 1, Redis 1, Kafka 3(Node마다 1)에 HTTP Blue/Green 여유를 더한 값입니다. 시스템용 Node 1대는 상한과 별도입니다.
- **실제 대수** — dev는 CPU 요청을 줄이고 저활용 Node를 합쳐 1대로 운영합니다(#279, #280). stage, prod는 Kafka 브로커가 Node마다 1개씩 놓여 각각 3대 이상입니다.

**트레이드오프**

- **자원 경합 수용** — 같은 NodePool을 사용하는 환경 안 워크로드의 합산 자원과 배치 가능 용량을 함께 검증하기로 했습니다.
- **환경별 최소 Node** — 환경마다 Node를 따로 쓰므로 환경 간에 남는 자원을 나눠 쓰지 못하고, stage, prod는 Kafka 배치 때문에 최소 3대를 유지하는 비용을 감수했습니다.

## 4. Namespace와 워크로드

### 4.1 Namespace 구성

**결정 요약**: dev, stage, prod로 애플리케이션 환경을 구분하고 관리 도구는 `tool` Namespace에 통합하기로 했습니다.

**이유**

- **클러스터 관리 대상 축소** — 환경별 클러스터를 추가하지 않고 Namespace로 운영 단위를 구분하기로 했습니다.
- **공통 관리 도구 통합** — Karpenter, Argo CD, Sealed Secrets Controller, Strimzi Cluster Operator, Load Balancer Controller, 공용 Gateway와 관측 수집기(Alloy, kube-state-metrics)를 tool에서 관리하고 도구별 자원, ServiceAccount는 구분했습니다.

**트레이드오프**

- **공통 장애 영향** — 각 환경이 같은 클러스터의 장애, 변경 영향을 공유하는 부담을 감수했습니다.

### 4.2 애플리케이션 배포 단위

**결정 요약**: 환경별 FE, BE, AI API는 별도 Deployment로 배포하고 API, 정기 Batch, 알림 Consumer, AI 결과 Consumer는 같은 BE 프로세스에 유지했습니다. AI 작업 Consumer는 AI API Pod에서 실행하도록 Kafka 연결 설정(`KAFKA_ENABLED`)과 토픽을 넣어 두었으나, 현재 AI 이미지는 이 설정을 읽지 않아 AI 결과는 BE의 HTTP 콜백(AI→BE 8080)으로 전달됩니다.

**이유**

- **BE 전환 범위 제한** — API, Consumer, Batch를 별도 서버로 분리하지 않고 기존 BE 실행 단위를 유지하기로 했습니다.
- **AI 역할 구분** — AI API는 Kafka 작업 소비와 결과 발행을, RunPod는 모델 서빙을 담당하도록 정했습니다. AI 팀의 Kafka 코드가 병합되면 바로 연결되도록 설정을 미리 두고, 그 코드가 시작할 때 요구하는 토픽도 먼저 만들었습니다.
- **환경별 작업 상태 분리** — dev, stage 요청이 prod AI API의 작업 상태에 섞이지 않도록 환경별 AI API 서버, 내부 Service, 호출 설정을 구분했습니다.

**트레이드오프**

- **BE 실행 단위의 결합** — API, Consumer, Batch가 자원, 배포, 확장을 공유하는 부담을 감수했습니다.
- **AI 작업의 HTTP 의존** — AI의 Kafka 소비가 시작되기 전까지 AI 작업 전달은 HTTP 호출과 콜백에 의존합니다.

### 4.3 Pod 구성

**결정 요약**: FE, BE, AI API를 별도 Pod로 실행하고 앱 Pod에 nginx, 로그 수집 Sidecar를 추가하지 않았습니다. AI API는 모든 환경에서 1개로 실행하고, Kafka 연동과 작업 복구 방식을 갖춘 뒤 수평 확장을 적용하기로 했습니다.

**이유**

- **공통 기능의 중복 축소** — 외부 라우팅은 ALB가 담당하고 로그는 Node별 Alloy로 수집하기로 했습니다.
- **AI 운영 방식 통일** — 별도 EC2 배포 체계를 추가하는 대신 기존 Helm, Argo CD, 관측 구성과 Karpenter의 Node 공급을 활용하기로 했습니다.
- **작업 상태 의존성 완화** — AI 요청과 결과를 Kafka로 교환하고, FastAPI 내부 큐의 미완료 작업을 Pod 종료 후 재처리할 수 있도록 구성한 뒤 수평 확장하기로 했습니다. 내부 큐 제거는 필수 조건으로 두지 않았습니다.
- **분석 결과의 메모리 보관** — 현재 AI는 분석 결과를 프로세스 메모리에 두므로 여러 개를 띄우면 요청마다 상태가 갈립니다. v2처럼 1개로 시작했습니다(#267).

**트레이드오프**

- **공통 구성의 영향 공유** — 라우팅, 수집 기능을 앱별로 두는 대신 공통 로드밸런서와 Node 수집기에 의존하기로 했습니다.
- **AI 작업 복구 구현** — Kafka 도입만으로 기존 인메모리 작업이 복구되지는 않으므로 결과 발행, 커밋, 재처리, 중복 방지와 종료 처리를 애플리케이션에서 함께 구현하는 부담을 감수했습니다.

#### Probe 기본 정책

**결정 요약**: FE, BE, AI API, Redis에 Startup, Readiness, Liveness를 구분해 적용했습니다. 기동 예산은 FE 2분, BE 5분, AI API 3분, Redis 10분이며 dev, stage, prod에 같은 정책을 적용했습니다. AI API는 Readiness에도 `/health/live`를 사용합니다.

**이유**

- **느린 기동 보호** — JVM 초기화와 Redis AOF 복원 도중 Liveness가 컨테이너를 반복 재시작하지 않도록 Startup이 성공하기 전까지 Readiness, Liveness를 실행하지 않도록 했습니다. Redis는 AOF 로딩을 고려해 10분의 초기 예산을 두었습니다.
- **일시 장애와 컨테이너 장애 구분** — DB, Kafka, 외부 모델 서버 장애는 BE, AI API의 Liveness 실패로 연결하지 않기로 했습니다. 운영 중에는 10초 간격으로 6회 연속 실패했을 때 컨테이너를 재시작하도록 하여 일시 지연의 영향을 줄였습니다.
- **요청 수신 제어** — Readiness는 5초 간격으로 검사하고 3회 연속 실패하면 Service의 요청 전달 대상에서 제외하도록 정했습니다. Kafka Consumer의 작업 수신은 별도 애플리케이션 제어 대상으로 구분했습니다.

**근거**

| 대상 | 확인 내용과 적용 판단 |
|---|---|
| FE | 전용 헬스 경로가 없어 Pod Probe는 3000 포트의 TCP 연결을 확인합니다. ALB Target 헬스 체크는 `/`가 로그인하지 않은 요청을 `/login`으로 307 redirect해 unhealthy가 되므로 `/manifest.webmanifest`를 사용합니다(#233). |
| BE | Actuator의 Readiness, Liveness 전용 그룹(`/actuator/health/readiness`, `/actuator/health/liveness`)을 주 서비스 포트에서 사용합니다. |
| AI API | Startup, Readiness, Liveness 모두 `/health/live`를 사용합니다. `/health/ready`는 RunPod Worker가 꺼져 있으면 503을 돌려주고 AI는 Worker를 켜지 않으므로, Readiness에 쓰면 Worker가 꺼진 동안 AI가 Service에서 계속 빠지기 때문입니다(#230). |
| Redis | TCP 접속만으로 기동 완료를 판단하지 않고 `redis-cli ping`의 `PONG` 응답을 확인합니다. |

**트레이드오프**

- **기동 실패 판정 지연** — 기동 예산을 늘리면 실제 기동 실패를 판정하는 시간도 길어지는 부담을 감수했습니다. 값은 실제 기동, 복구 시간으로 조정하기로 했습니다.
- **FE 검사 범위 제한** — TCP 검사는 포트 접근을 확인하지만 화면 렌더링이나 애플리케이션 내부의 모든 비정상 상태를 검증하지 못하는 한계를 명시했습니다.
- **AI 준비 상태 미반영** — AI Readiness가 프로세스 생존만 보므로 RunPod Worker가 준비되지 않은 동안에도 요청을 받는 점을 감수했습니다.

### 4.4 Service와 외부 라우팅

**결정 요약**: Gateway API, AWS Load Balancer Controller를 사용하고 dev, stage, prod가 CloudFront 배포 1개와 internal ALB 1개(`dameokja-v3-gateway`)를 공유합니다. CloudFront 캐시는 끄고, 이미지용 S3 오리진은 두지 않습니다. 인증서는 dev 인증서에서 dev, stage 공용, dev, stage, prod 공용 인증서를 차례로 추가해 사용합니다. Grafana는 서비스와 별도의 CloudFront 배포로 엽니다(8절).

**이유**

- **라우팅 정의 관리** — Cloud 팀이 `tool` Namespace의 공용 Gateway를 관리하고, 앱별 HTTPRoute와 TargetGroupConfiguration은 공통 앱 차트가 환경별 values의 `route` 값으로 만듭니다. Gateway는 `dameokja.com/gateway-access` 라벨이 있는 Namespace의 Route만 받습니다.
- **프록시 운영 부담 축소** — Envoy Gateway, NGINX Gateway Fabric 방식과 비교해 현재 라우팅, 분산 요구는 ALB로 충족하기로 했습니다.
- **공용 진입점 관리** — 공통 VPC, EKS에서 진입점 분리만으로 보안 격리가 완성되지 않는다고 판단하여 자원 수와 관리 부담을 줄이는 공유 구성을 선택했습니다.
- **인증서 관리 범위 제한** — 사용자 HTTPS는 CloudFront에서 종료하고 internal ALB는 VPC Origin으로 HTTP 80에 연결했습니다.
- **이미지 직접 전송** — 이미지는 BE가 발급한 S3 presigned URL로 브라우저가 S3에 직접 올리고 받으므로 CloudFront에 S3 오리진을 두지 않았습니다(#233).
- **인증서 추가 방식** — 기존 인증서를 교체하며 지우면 같은 DNS 검증 CNAME이 함께 지워질 위험이 있어, 도메인을 넓힌 새 인증서를 추가하고 옛 인증서는 남겼습니다(#270, #303).

**근거**

- **권한, 라우팅 경계** — 공용 Gateway에 환경별 HTTPRoute를 연결하고 도메인, 권한, Secret, 데이터 접근 기준으로 환경을 구분했습니다. FE는 `/`, BE는 `/api`, `/swagger-ui`, `/v3/api-docs`이며 AI는 외부에 노출하지 않습니다.
- **내부 통신 기준** — 비공개 경로와 보안 그룹을 신뢰 경계로 삼아 CloudFront 이후 앱 구간은 HTTP로 연결하고 ALB 인증서는 생략했습니다. ALB SG는 CloudFront origin-facing prefix list의 80만 받아 VPC 밖에서 ALB로 직접 들어올 수 없습니다. ALB SG는 CloudFormation이 소유하고 Controller에는 SG 생성, 규칙 변경 권한을 주지 않았습니다(#232).
- **캐시 끔** — 캐시 정책은 Managed-CachingDisabled, 오리진 요청 정책은 Managed-AllViewer로 두어 Host, 쿠키, Authorization, 쿼리를 모두 넘깁니다. API를 캐시하지 않는 기준(#231)을 배포 전체에 적용했습니다.
- **트래픽 전환** — 각 도메인은 Route 53 레코드로 v3 CloudFront를 가리키며, dev, prod는 가중치 레코드로 v2에서 v3로 옮겼습니다(#315).

**트레이드오프**

- **사용량에 따른 비용** — ALB 기본 요금, LCU 요금과 CloudFront 요청, 전송 비용을 감수했습니다.
- **공통 변경 영향** — 공용 설정의 실수나 변경이 prod를 포함한 모든 환경에 영향을 줄 수 있는 부담을 감수했습니다.
- **캐시 효과 없음** — 정적 자원도 모두 오리진까지 가므로 CloudFront 캐시로 얻는 응답 시간, 오리진 부하 감소는 얻지 않습니다.
- **클라우드별 연동 설정** — GatewayClass, IAM, 전용 설정은 클라우드별로 달라지는 점을 감수했습니다.
- **운영 정책 관리** — 남겨 둔 옛 인증서와 오리진 정책을 별도로 관리합니다.

### 4.5 Kafka 연동

**결정 요약**: 작업 보관, 분배를 외부 MQ로 분리하기 위해 Kafka를 도입했습니다. 알림과 AI 결과 Consumer는 BE 내부에 유지하고, AI 작업 Consumer는 AI API에서 실행하기로 했습니다(AI 이미지가 Kafka 설정을 읽게 되면 시작).

Kafka는 MSK 대신 Strimzi로 직접 운영합니다. dev는 Broker, Controller 겸용 Pod 1개, stage, prod는 겸용 Pod 3개를 Node마다 1개씩(AZ 2b) 두고 복제 수 3, `min.insync.replicas` 2로 구성했습니다. 환경별 Kafka 클러스터(`<환경>-kafka`), bootstrap 주소, Topic(`<환경>.dameokja.*`), Consumer Group과 저장 데이터를 분리했습니다. BE의 Kafka Consumer는 세 환경 모두 켜져 있고, AI의 Kafka 소비는 AI 이미지가 설정을 읽게 되면 시작됩니다.

#### 현재 구조와 외부 MQ의 필요성

**이유**

- **업무 DB의 역할 분리** — API 업무 데이터와 발송 대기 작업을 같은 DB에서 관리하는 부담을 줄이기로 했습니다.
- **참여와 알림 실패 분리** — 공유 참여를 먼저 확정하고 BE 내부 Consumer가 이벤트를 받아 알림을 생성하도록 정했습니다.
- **외부 처리량 제어** — 알림, AI 작업은 외부 서비스 처리 한도에 맞춰 실행하기로 했습니다.
- **AI 요청, 결과 분리** — 이미지 분석, 추천의 요청과 완료 토픽을 구분해 BE와 AI API가 비동기로 작업을 교환하도록 정했습니다.
- **Kubernetes 운영 통합** — Kafka 설정을 Strimzi의 선언형 리소스로 관리하고, Pod 재생성과 영속 볼륨 연결을 기존 EKS 운영 체계에 통합하기로 했습니다.
- **dev 우선 구축** — 개발 연동에는 Broker, Controller 겸용 Pod 1개를 사용하고, stage, prod의 장애 대응 구성은 dev 구축의 선행 조건으로 두지 않았습니다.
- **stage, prod 다중 구성** — stage는 prod와 같은 검증 환경이므로 stage, prod 모두 겸용 Pod 3개를 필수 podAntiAffinity로 서로 다른 Node에 두었습니다. 복제 수 3, `min.insync.replicas` 2로 브로커 1개가 내려가도 `acks=all` 쓰기가 계속되도록 했습니다(#260, #261, #304).
- **환경별 작업 구분** — 접속 주소, cluster ID, 저장 데이터와 Topic, Consumer Group을 환경별로 구분하고, 같은 환경의 BE, AI API Pod만 클라이언트 접속을 허용하기로 했습니다. 공유 Node, AZ와 네트워크의 공통 장애 가능성은 남는 것으로 정리했습니다.

#### 대안 비교와 선택 이유

**근거**

- **순차 처리와 분담** — 냉장고 ID 기반 Partition과 Consumer Group으로 같은 냉장고의 작업 순서와 서버 간 분담, 재배정을 구성하기로 했습니다.
- **선택 기준** — 현재의 작업 전달, 분담 요구와 Kafka Streams의 집계, 이벤트 결합 활용 가능성을 함께 고려했습니다.
- **순서 보장의 범위** — Partition 내 순서와 별개로 Producer 발행, 재시도까지 포함한 업무 순서는 애플리케이션에서 보장하기로 했습니다.
- **AI 소비 병렬성** — dev 토픽은 파티션 1개로 기능을 검증하고, stage, prod 토픽은 파티션 3개로 만들었습니다. AI Pod 증가가 소비 병렬성으로 이어지도록 소비 동시성, RunPod 처리 한도를 함께 검토하기로 했습니다.

| 대안 | 판단 |
|---|---|
| DB 큐 유지 | 기존 구성을 활용하지만 업무 데이터와 대기 작업 관리가 같은 DB에 남아 채택하지 않았습니다. |
| RabbitMQ Super Streams, Single Active Consumer | 순차 처리와 작업 분담을 충족할 수 있는 대안으로 검토했습니다. |
| Kafka | 냉장고 ID 기반 Partition, Consumer Group과 Streams 집계, 이벤트 결합 활용 가능성을 고려해 선택했습니다. |

#### Kafka 운영 방식

Kafka 기반 운영은 직접 담당하되, 클러스터와 토픽 설정은 Strimzi 리소스로 선언하고 환경별 데이터 차트(`dev-data`, `stage-data`, `prod-data`)를 관리자 PC에서 Helm으로 적용합니다. Kafka Pod는 각 환경의 앱 NodePool을, Strimzi Cluster Operator는 시스템용 Node의 `tool` Namespace를 사용합니다. 토픽 자동 생성은 브로커와 클라이언트 모두 꺼 두고, BE가 쓰는 토픽(DLT, `cooking.applied`, 만료 확인 토픽 등)은 차트에 추가해 만듭니다(#241, #320).

| 대안 | 판단 |
|---|---|
| EC2, Docker Compose | 단일 서버의 설정과 디스크를 직접 관리하기 쉽지만, Kubernetes 밖의 Kafka 배포와 복구 절차를 별도로 유지해야 하므로 채택하지 않았습니다. |
| EKS Pod, Strimzi | Kafka 클러스터, 토픽과 저장소를 선언형 리소스로 관리하고 기존 EKS, Helm 운영에 통합하기 위해 선택했습니다. |
| Amazon MSK | 기반 운영 부담은 줄지만 다중 Broker의 상시 비용과 관리형 서비스 요금이 발생합니다. Kafka 4.2 계열의 지원 구성과 비용을 확인한 뒤 현재 예산에서는 채택하지 않았습니다. |

#### Kafka 자원과 보관 정책

**결정 요약**: Kafka Pod는 CPU limit 2, 메모리 request, limit 2Gi, gp3 PVC 10Gi와 업무 메시지 보관 기간 30일로 구성했습니다. CPU request는 dev 250m, stage, prod 500m입니다.

**이유**

- **초기 규모의 참고값** — MSK에서 소형 개발용으로 제공하는 `t3.small`의 2 vCPU, 메모리 2GiB를 참고하여 Pod의 자원 상한을 정했습니다. 사용량을 확인하여 조정하기로 했습니다.
- **Node 배치 가능성 확보** — 2 vCPU Node에 다른 Pod와 함께 놓이도록 CPU 2개를 전부 request로 예약하지 않고 limit만 2로 두었습니다. 별도 `t3.small` EC2를 생성하는 선택과 구분했습니다.
- **dev 요청 축소** — dev는 CPU 요청 합계(2.26코어)가 `m7i.large` 한 대의 Allocatable(1.93코어)을 넘어 Node가 2대였으나 실사용은 낮았습니다. dev Kafka, BE의 CPU request를 500m에서 250m으로 낮춰 1대로 합쳤습니다(#279, #280).
- **저장과 재확인 기간 확보** — PVC는 10Gi로 시작하고 업무 토픽의 `retention.ms`를 2592000000으로 설정하여 30일 보관 정책을 적용했습니다. PVC는 Pod 재생성 후 재사용하고, 삭제 시 자동 폐기하지 않습니다(`deleteClaim: false`).

**트레이드오프**

- **메모리 사용 범위** — JVM Heap 외의 메모리와 캐시도 Pod의 2Gi 안에서 사용하므로 기동과 소비 중 메모리 사용량을 확인하기로 했습니다.
- **저장 용량 제한** — 10Gi는 업무 메시지와 내부 메타데이터가 함께 사용하는 용량이며 30일치 수용량을 보장하지 않습니다. 디스크 사용량에 따라 용량을 확장하기로 했습니다.
- **관리 도구의 별도 예산** — Kafka Pod의 자원값에 Strimzi Operator 등 관리 Pod는 포함하지 않고 시스템용 Node에서 별도로 검토하기로 했습니다.

- [MSK의 T3 개발용 사용 기준](https://docs.aws.amazon.com/msk/latest/developerguide/broker-instance-sizes.html)

#### Kafka 접속 보안

**결정 요약**: dev, stage, prod의 클라이언트는 사설 경로의 TCP 9092에서 PLAINTEXT를 사용하고, 클라이언트 접속에 TLS와 SASL 인증을 추가하지 않기로 했습니다. Strimzi 내부 연결은 지원 기본 설정으로 관리하기로 했습니다.

**이유**

- **현재 내부 통신 기준 유지** — 내부 앱 구간에 추가 암호화를 적용하지 않는 현재 범위에 맞춰 Kafka도 같은 기준으로 구성하기로 했습니다.
- **초기 구성 범위 제한** — 클라이언트 인증서 발급, 갱신과 Kafka 인증 계정 관리를 추가하지 않고, 환경별 클러스터 분리와 SG, NetworkPolicy로 접근 대상을 제한하기로 했습니다. Strimzi가 내부 운영에 사용하는 인증서는 Operator의 관리 범위로 구분했습니다.

**트레이드오프**

- **네트워크 접근 제한에 의존** — 사설망과 SG는 Kafka 통신을 암호화하거나 Kafka 클라이언트의 신원을 인증하지 않으므로, 메시지 암호화와 Kafka 자체 접속 인증을 제공하지 않는 구성을 수용했습니다.

#### 감수할 부담과 남은 검증

**트레이드오프**

- **Broker, 스토리지 운영** — Kafka 클러스터와 이벤트 발행, 소비 구현의 부담을 감수했습니다.
- **누락, 중복 처리** — DB 저장과 이벤트 전달 사이의 누락 및 재처리 중복을 별도로 해결하기로 했습니다.
- **순차 재시도 지연** — 순서 유지를 위한 재시도가 다른 작업까지 지연시킬 수 있는 부담을 감수했습니다.
- **BE 확장과의 연동** — Pod 증감에 따른 Consumer 실행량, Partition 재배정, DB 접근, API 지연을 함께 검증하기로 했습니다.

- **stage, prod의 단일 AZ** — 브로커 3개가 모두 AZ 2b에 있어 Node 장애에는 대비하지만 AZ 장애에는 대비하지 않습니다.
- **직접 운영 책임** — Strimzi, Kafka 버전, PVC와 EBS, Node 자원, 디스크 용량과 장애 복구는 Cloud 팀이 관리하는 부담을 감수했습니다.
- **Node 최소 대수** — 필수 podAntiAffinity로 stage, prod는 각각 앱 Node가 최소 3대 필요합니다.

## 5. 자원, 배치, 확장 정책

### 5.1 Pod requests, limits

**결정 요약**: FE는 CPU request 250m, limit 1, 메모리 request 512Mi, limit 1Gi, BE는 CPU request 500m(dev 250m), limit 1, 메모리 request 1Gi, limit 2Gi로 구성했습니다. AI API는 CPU request 250m, limit 1, 메모리 request 512Mi, limit 1536Mi, Redis는 CPU request 250m, limit 500m, 메모리 request 512Mi, limit 1Gi입니다.

**이유**

- **합산 실행 부하 반영** — BE가 여러 역할을 같은 프로세스에서 실행하는 구성을 자원 배정에 반영하기로 했습니다.
- **AI 메모리 상한** — AI API 메모리 limit은 v2 stage, prod AI 태스크의 메모리 값(1536Mi)을 따랐습니다.
- **dev 요청 축소** — dev BE는 실사용이 낮아 CPU request를 250m으로 낮추고 limit은 그대로 두었습니다(#279, #280).

**근거**

- **측정 자료의 범위** — ECS 시험은 앱 Task 2개의 합산 결과이므로 FE, BE별 자원 크기로 직접 환산하지 않았습니다.
- **AI, Redis 예산** — AI 모델은 RunPod에서 실행하므로 AI API에는 요청, 결과와 큐 처리를 위한 예산을 두었습니다. Redis는 maxmemory 512mb와 limit 1Gi를 구분하여 AOF 처리, 클라이언트 버퍼, 내부 관리 메모리와 메모리 단편화에 대한 여유를 두었습니다.
- **Node 계산 예산** — `m7i.large`의 CPU 2 vCPU, 메모리 8Gi에서 OS, Kubernetes, 공통 Pod 합산 예산 500m, 1Gi를 제외하여 앱 계산 예산을 Node당 1.5 vCPU, 7Gi로 잡았습니다. 실제 Allocatable과 DaemonSet requests로 확인하고 예약 자원을 중복 차감하지 않도록 구분했습니다.

**트레이드오프**

- **초기값 검증 필요** — 개별 사용량, 응답 지연, JVM 메모리, OOM, CPU 제한, DB 연결 수와 배포 여유를 측정해 조정하기로 했습니다.

**출처**

- [초기 requests, limits](v3%20인프라%20설계.md#51-pod-requests-limits)

### 5.2 시스템용, 앱 Node 배치

**결정 요약**: 관리 도구와 앱의 실행 Node를 나누고 역할 라벨, `taint`, `toleration`으로 배치를 제어합니다. 시스템용 Node는 라벨 `dameokja.com/node-role=system`과 taint `dameokja.com/system=true:NoSchedule`, 앱 Node는 라벨 `dameokja.com/node-role=app`을 쓰고, stage, prod 앱 Node에는 환경 라벨과 taint를 더했습니다.

**이유**

- **자원 경합 완화** — 관리 도구와 앱이 같은 실행 자원을 두고 경합하는 범위를 줄이기로 했습니다.
- **Node 교체 대응** — 특정 인스턴스를 고정하는 대신 역할별 배치 정책으로 교체 후에도 같은 역할의 Node에서 실행하도록 정했습니다.
- **환경별 Node 구분** — stage, prod Pod는 환경 라벨의 nodeSelector와 taint의 toleration을 함께 두어 자기 환경 Node에만 놓입니다(3.3절).

**트레이드오프**

- **배치 정책 관리** — Node 교체, 초기화 시에도 역할 라벨과 taint를 유지하고 Pod의 배치 설정을 함께 관리하기로 했습니다.

### 5.3 FE, BE HPA와 Replica

**결정 요약**: FE, BE는 현재 HPA 없이 고정 Replica로 운영합니다(dev 각 1개, stage, prod 각 2개). 확장 방식으로는 CPU 사용률 기반 HPA를 택하고 VPA는 함께 적용하지 않기로 했으며, HPA 도입은 [고도화 계획 2절](v3%20인프라%20고도화%20계획.md#2-자원-확장-정책-개선)에서 다룹니다. Metrics Server는 설치되어 있습니다.

**이유**

- **독립 요청 분산** — Pod를 추가해 요청을 분산하는 방식이 FE, BE의 실행 구조에 맞는다고 판단했습니다.
- **초기 지표 선택** — Metrics Server로 공급할 수 있고 BE 내부 작업의 연산 부하도 반영하는 CPU를 선택했습니다.
- **Replica 범위** — 공통 앱 차트는 색상별 Replica를 0~4로 제한합니다.

**근거**

| 기준 | HPA | VPA |
|---|---|---|
| 확장 단위 | Pod를 추가하여 요청을 분산합니다. | 단일 Pod의 자원을 조정합니다. |
| 운영 중 영향 | 기존 Pod를 유지하지만 새 Pod, Node의 기동을 기다려야 합니다. | 적용 모드와 Node 여유 자원에 따라 변경이 보류되거나 재생성이 필요합니다. |
| 부담 | Pod별 런타임, 연결 풀과 여유 용량이 추가됩니다. | 단일 Node 수용 용량과 프로세스의 처리 한계에 제약을 받습니다. |

**트레이드오프**

- **고정 Replica의 한계** — HPA를 적용하기 전에는 부하가 늘어도 Pod가 자동으로 늘지 않으므로 Replica 값을 직접 바꿔야 합니다.
- **확장 지연과 추가 자원** — HPA 적용 시 새 Pod, Node의 기동을 기다리고 Pod별 런타임, 연결 풀, 여유 용량을 추가하는 부담이 생깁니다.
- **CPU 지표의 한계** — DB, 외부 API 대기는 CPU만으로 판단하기 어려우므로 합산 부하를 검증하기로 했습니다.
- **Consumer, DB 연결 증가** — BE Pod가 늘면 작업 실행량과 DB 연결도 늘어나는 점을 함께 검증하기로 했습니다.

#### 초기 최소, 최대 Replica

**결정 요약**: BE 처리 목표는 100 RPS/Pod로 유지합니다. FE, BE는 stage, prod 각각 2개, dev 각각 1개, AI API는 모든 환경 1개, Redis는 환경별 1개로 운영합니다. stage, prod NodePool 상한에는 평시 구성과 HTTP Blue/Green 여유를 반영했습니다(3.3절).

**이유**

- **처리 목표의 여유 확보** — ECS 시험의 Task당 평균 처리량보다 낮은 목표를 사용하기로 했습니다.
- **Pod 1개 여유 반영** — prod의 평시 처리량을 Pod당 목표로 나눈 뒤 장애 여유 Pod 1개를 더해 FE, BE 2개로 정했습니다.
- **AI 단일 실행** — AI가 분석 결과를 메모리에 두므로 v2 stage, prod처럼 1개로 시작했습니다(#267, #305).
- **운영 환경과 같은 검증 구성** — stage의 워크로드, requests, limits, Replica, NodePool 사양과 배포 방식을 prod와 같게 구성하여 운영과 같은 조건에서 검증합니다. 도메인, 데이터와 Secret은 환경별로 구분했습니다.
- **환경별 부하 구분** — 사용자 피크 300 RPS는 prod의 산정 기준이며 stage에서도 같은 처리 목표를 검증할 수 있도록 같은 용량을 두었습니다. dev만 개발 목적의 단일 FE, BE로 운영합니다.

**근거**

- **측정 조건** — ECS Task 2개에 조회 80%, 재고 등록 20%의 API 부하를 전달한 결과를 사용했습니다.
- **응답 지연 검토** — 로그인 집중 구간의 DB 연결 대기와 최대 약 22초 지연도 관측하여 최고 처리 구간만으로 전체 응답 성능을 판단하지 않았습니다.

| 항목 | 측정값, 계산 |
|---|---|
| 목표 280 RPS 구간 | 합계 278 RPS, p95 42ms, p99 121ms, HTTP 실패 0건 |
| Task당 평균 | 균등 분산 기준 `278 / 2 = 139 RPS` |
| BE 초기 목표 | 평균보다 약 28% 낮춘 100 RPS/Pod |

**트레이드오프**

- **단일 Pod 최대치 검증 필요** — ECS, Kubernetes 자원 제한 차이와 Kafka 연동 부하를 추가 검증하기로 했습니다.
- **FE 처리량 검증 필요** — BE API 시험으로 FE의 처리량을 검증한 것으로 보지 않고 별도 검증 대상으로 남겼습니다.
- **단일 구성의 중단** — dev의 FE, BE와 모든 환경의 AI API는 각각 한 개이므로 Pod 장애나 배포 시 해당 기능이 대체 Pod의 기동까지 중단될 수 있는 부담을 감수했습니다.
- **공급, 배포 여유 비용** — 실제 Node 공급은 NodePool 상한 안에서 Karpenter의 배치 판단에 따릅니다. stage, prod는 Kafka 브로커 배치 때문에 평시에도 각각 3대 이상을 사용합니다.
- **확장, 장애 조건 검증** — 로그인, 토큰 갱신과 Node, AZ 장애 수용 범위를 별도로 검증하기로 했습니다.

### 5.4 Karpenter Node 확장, 정리

**결정 요약**: stage, prod는 빈 Node만 5분 후 정리(`WhenEmpty`)하고, dev는 빈 Node와 덜 찬 Node를 함께 합칩니다(`WhenEmptyOrUnderutilized`, 5분). 자발적인 정리, 교체는 모든 NodePool에서 한 대씩 진행하고, 수명 만료에 의한 자동 교체는 끕니다(`expireAfter: Never`).

**이유**

- **실행 중 Pod 이동 최소화** — stage, prod는 사용 중인 Node의 통합보다 빈 Node 정리를 우선하기로 했습니다.
- **dev 비용 절감** — dev는 실사용이 낮은데 CPU 요청 합계 때문에 Node가 2대였으므로, 요청을 줄이고 덜 찬 Node를 합쳐 1대로 운영합니다. 앱 Node 한 대(월 약 $90)를 줄였습니다(#279, #280).
- **동시 교체 범위 제한** — 자발적인 교체가 한 번에 여러 Node에 영향을 주는 범위를 줄이기로 했습니다.

**트레이드오프**

- **dev의 이동 중단** — dev 전체가 Node 1대에 모이고, 합치는 동안 옮겨지는 dev Pod가 잠깐 멈추는 것을 감수했습니다.
- **용량 검증 필요** — 병렬 공급, 교체 중 일시적인 Node 수 초과와 실제 배치 가능 용량을 검증하기로 했습니다.
- **수명 만료 교체 없음** — 수명 만료 교체를 끄므로 AMI, 구성 변경에 따른 Node 교체는 drift로 일어나며 장애에 의한 종료는 별도로 검증하기로 했습니다.

### 5.5 Redis 운영

**결정 요약**: Redis는 환경별 단일 Pod로 운영하고 CPU, 메모리 requests, limits를 고정값으로 관리하기로 했습니다. 자원 부족 시 사용량을 확인하여 수동 조정하기로 했습니다.

**이유**

- **초기 운영 범위 제한** — 자동 자원 조정과 다른 Pod의 자원 회수 자동화를 추가하지 않고, 단일 Redis의 AOF 복원과 기본 운영을 먼저 구성하기로 했습니다.
- **메모리 여유 확보** — Redis `maxmemory`를 컨테이너 메모리 limit보다 낮게 설정하여 AOF 처리, 클라이언트 버퍼, 내부 관리 메모리와 메모리 단편화에 대한 여유를 두기로 했습니다.

**트레이드오프**

- **수동 자원 조정** — 부하 증가 시 자동으로 증설되지 않으므로 사용량 확인과 자원 변경을 직접 수행하는 부담을 감수했습니다.
- **변경 영향 확인** — 자원 변경의 반영 방식과 재시작 영향을 확인한 뒤 적용하기로 했습니다.

**출처**

- [Redis 메모리 상한](https://redis.io/docs/latest/develop/reference/eviction/)

### 6.1 IaC: AWS CloudFormation

**결정 요약**: AWS IaC는 기존 CloudFormation을 유지했습니다. v3 스택은 `infra/v3/cloudformation/`에 두고, PR에서는 cfn-lint만 실행하며, `infra-v3-cfn.yml`을 main에서 수동 실행해 plan(change set 생성) 후 apply(change set 실행)합니다. 인증서와 Grafana 배포 스택(`edge-cert`, `grafana-edge`)만 us-east-1에서 실행합니다.

- **동시 전환 범위 제한** — Kubernetes, GitOps 구축과 Terraform 학습, 기존 자원 이관을 동시에 진행하는 부담을 줄이기로 했습니다.

- **적용 승인 절차 없음** — apply는 main에서 Workflow를 실행할 수 있는 사람이면 진행할 수 있고, GitHub Environment 승인은 두지 않았습니다.
- **Kubernetes 자원 적용 경로** — 관리 도구와 `platform`, 데이터 차트는 CloudFormation이 아닌 관리자 PC의 Helm으로 적용하므로 적용 이력이 Workflow에 남지 않습니다.

### 6.3 CD: Helm, Argo CD와 Blue/Green

**결정 요약**: 앱(FE, BE, AI API)과 SealedSecret은 Helm 차트와 Argo CD로 GitOps 배포하고, Argo CD는 시스템용 Node의 `tool` Namespace에서 운영합니다. 관리 UI는 외부 도메인 없이 관리자 PC의 port-forward로만 접속하며, Argo CD 로컬 계정으로 로그인합니다. 이미지 갱신은 Workflow가 환경별 values의 활성 색상 이미지 digest를 main에 커밋하는 방식입니다.

| 환경 | 이미지 갱신 | Argo CD 동기화 |
|---|---|---|
| dev | 앱 CI → `v3-dev-image.yml`(병합 즉시) | 앱 자동(prune), Secret 수동 |
| stage | 앱 main CI → `v3-stage-image.yml` | 모두 수동. stage를 켤 때 앱을 sync |
| prod | `prod-approval.yml`(같은 이미지의 stage 성공 확인, Environment "prod" 승인) → `v3-prod-image.yml` | 앱 자동(prune, selfHeal 끔), Secret 수동 |

**이유**

- **공통 설정 재사용** — 공통 앱 차트(`v3/charts/application`)와 환경별 values를 사용하여 배포 정의를 관리합니다.
- **Git 기준 운영** — 배포 Git과 클러스터 실행 상태를 동기화하기 위해 Argo CD를 선택했습니다.
- **사설 API 접근** — EKS API는 private endpoint만 열려 있어 GitHub 러너가 클러스터에 직접 배포할 수 없으므로, Workflow는 이미지 값만 커밋하고 Argo CD가 그 커밋을 가져가 배포합니다(#239, #306).
- **환경별 동기화 정책** — dev는 병합 즉시 반영하고(#238), stage는 수동 sync로 두고(#267), 켤 때 꺼진 동안 바뀐 이미지를 sync합니다(#278). prod는 승인 뒤 바로 배포되도록 자동 동기화하되 prune, selfHeal은 끄고, Secret은 수동으로 둡니다(#305).
- **기본 로그인 활용** — Dex, SSO 연동 없이 Argo CD 로컬 계정을 사용해 초기 인증 연동의 관리 범위를 줄였습니다. 익명 접근은 비활성화하고 로그인 후 기본 권한은 `role:readonly`입니다.

**트레이드오프**

- **정책 유지관리** — Chart, 권한, 동기화 정책과 Argo CD의 운영을 담당하기로 했습니다.
- **실행 기반의 영향 공유** — 시스템용 Node, EKS 장애가 배포 도구에도 영향을 주는 점을 감수했습니다.
- **배포 도구와 앱 실행 구분** — Argo CD 중단 자체로 실행 중인 앱이 중지되는 것은 아니지만 배포, 동기화는 영향을 받을 수 있는 것으로 구분했습니다.
- **계정 직접 관리** — Cloud 팀이 로컬 계정, 비밀번호와 Argo CD 권한을 관리하는 부담을 감수했습니다.
- **관리 UI 접근 제한** — 관리 도메인이 없어 UI와 동기화 상태 확인은 SSM, port-forward 권한이 있는 관리자만 할 수 있습니다.
- **관리 도구의 수동 적용** — Argo CD는 앱과 Secret만 관리하고, 관리 도구, `platform`, 데이터 차트는 관리자 PC에서 Helm으로 적용합니다.

#### FE, BE, AI API Blue/Green 배포

**결정 요약**: 공통 앱 차트에 색상(blue, green)별 Deployment와 `activeColor`를 가리키는 Service를 두어 Blue/Green 전환 구조를 갖췄습니다. 실제 배포는 활성 색상(blue)의 이미지 digest를 바꾸는 방식이며, Deployment 전략은 `Recreate`입니다. BE, AI API는 두 색상을 동시에 실행하지 못하게 막았습니다(`allowConcurrentConsumers: false`).

**이유**

- **Consumer 중복 방지** — BE, AI API는 Kafka Consumer와 메모리 작업 큐가 있어, 두 색상이나 신, 구 Pod가 함께 뜨면 같은 Consumer가 두 벌 떠서 작업을 중복 처리할 수 있습니다. 색상 안에서 이미지를 바꿀 때도 `Recreate`로 기존 Pod를 먼저 내리고, 두 색상 동시 실행은 중복 처리 검증 뒤에 열기로 했습니다.
- **전환 구조 유지** — v2의 Blue/Green 경험을 활용할 수 있도록 색상별 Deployment, `-blue`, `-green` Service와 `activeColor` 전환 구조는 차트에 남겼습니다. 색상 전환 배포는 Kafka Consumer의 Blue/Green 전환 절차를 정한 뒤 적용합니다([고도화 계획 5.2](v3%20인프라%20고도화%20계획.md#52-kafka-consumer의-bluegreen-전환)).
- **구현 부담 대비 효과** — Canary는 일부 사용자에게 새 버전을 제공하며 반응, 오류율, 지연을 확인할 수 있지만, 현재 서비스에서는 이러한 단계별 검증의 추가 이점이 구현, 운영 부담에 비해 크지 않다고 판단했습니다.
- **추가 Controller 운영 제한** — Deployment, Service와 기존 Helm, Argo CD로 배포를 구성하고, 별도 Rollouts Controller를 추가하지 않았습니다.
- **검증된 이미지만 배포** — 이미지는 해당 앱의 GHCR digest 형식만 받고, prod는 같은 이미지가 stage에 반영된 뒤 승인을 거쳐야 배포됩니다.

**트레이드오프**

- **배포 중 중단** — `Recreate`는 기존 Pod를 내린 뒤 새 Pod를 띄우므로, 새 Pod가 Ready가 될 때까지 해당 앱의 요청이 중단됩니다.
- **이전 버전 복귀** — 이전 색상이 떠 있지 않으므로 복귀는 이전 이미지 digest를 다시 커밋해 재배포하는 방식입니다.
- **HTTP 전환 범위** — 색상 전환을 적용하더라도 Service selector가 전환하는 대상은 HTTP 요청이며, 이미 발행된 Kafka 작업을 되돌리거나 Consumer의 실행 대상을 전환하지는 않습니다. BE의 정기 Batch는 기존 ShedLock으로 중복 실행을 제어합니다.
- **복구 범위 구분** — 앱 복귀와 DB 변경 복구를 별도로 관리하는 부담을 감수했습니다.

## 7. 운영 권한과 Secret

### 7.1 환경, 트랙별 접근 권한

**결정 요약**: 팀(FE, BE, AI)에는 Kubernetes 직접 접근 권한을 주지 않고, IAM 그룹 `dameokja-iam`의 SSM 경로 정책으로 dev, stage 설정값의 조회, 생성, 수정, 삭제 권한을 부여합니다(#286, #307). prod 설정값의 관리 권한은 부여하지 않습니다. 클러스터 안의 Role은 stage 켜기, 끄기(`stage-power`)와 Argo stage 앱 sync용만 두었습니다. Grafana는 GitHub 아이디 허용 목록으로 GrafanaAdmin, Editor 역할을 부여합니다(8절).

**이유**

- **개발 설정의 직접 관리** — dev, stage에서는 각 팀이 설정값을 직접 만들고 바꿀 수 있어야 하므로, v2 스택에 있던 팀용 SSM 정책을 v3 스택(`dev-app-iam`, `stage-app-iam`)으로 옮겼습니다. v2 스택을 지우며 stage 정책이 함께 사라져 팀원이 stage 설정값을 바꿀 수 없게 된 것을 복구했습니다(#307).
- **운영 변경 통제** — prod 설정값과 클러스터 변경은 Cloud 팀이 관리하고, 앱 배포는 Git 커밋과 Argo CD를 거치도록 했습니다.
- **자동화 권한 최소화** — stage 켜기, 끄기의 kubectl 역할은 EKS 접근 정책 없이 stage Namespace의 `stage-power` Role만 쓰고, 앱, Redis의 scale, Kafka annotation 등 필요한 동작으로 제한했습니다(#272, #276). Argo sync용 Role은 `tool`의 stage Application 4개만 get, patch할 수 있습니다(#278).

**트레이드오프**

- **팀의 클러스터 조회 제한** — 팀이 Pod 상태, 이벤트를 kubectl로 직접 볼 수 없으므로 로그, 메트릭 조회는 Grafana에 의존하고, 그 밖의 확인은 Cloud 팀을 거칩니다.
- **환경별 조회 권한 없음** — Grafana 역할은 환경을 구분하지 않아 허용된 팀원은 prod를 포함한 모든 환경의 로그, 메트릭을 봅니다.
- **봉인 작업 집중** — 팀이 SSM 값을 바꿔도 클러스터 Secret에 반영하려면 관리자가 봉인, 커밋해야 합니다(7.2절).

**출처**

- [RBAC 이름별 리소스 제한](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#referring-to-resources)
- [워크로드 권한과 Secret 접근](https://kubernetes.io/docs/concepts/security/rbac-good-practices/#workload-creation)

### 7.2 Secret 공급: Sealed Secrets

**결정 요약**: Kubernetes Secret의 암호화, Git 보관, 클러스터 공급에 Sealed Secrets를 사용합니다. 원본 값은 환경별 SSM Parameter Store(일부 Secrets Manager)에 두고, 관리자가 PC에서 환경별 `seal-secrets.sh`로 값을 읽어 SealedSecret을 만들고 암호문만 커밋합니다. 환경마다 `be-secrets`, `ai-secrets`, `fe-secrets`, `cloud-secrets`, `ghcr-pull` 5개입니다.

**이유**

- **필요한 관리 범위에 집중** — 일반 설정 파일까지 암호화하는 범위보다 Kubernetes Secret의 Git 보관, 공급에 집중하기로 했습니다.
- **Argo CD 연동 부담 축소** — Argo CD에 별도 복호화 플러그인을 추가하지 않고 대상 클러스터에서 Secret을 생성하도록 정했습니다.
- **별도 저장 서버 운영 제한** — Vault의 저장 서버, 인증, 공급 구성을 초기 운영 범위에 추가하지 않기로 했습니다.

**근거**

- **암호화 범위** — 기본 `strict` 범위로 이름, Namespace 변경에 의한 재사용을 제한했습니다.
- **원본 값의 위치** — 팀이 SSM 값을 관리하고(7.1절), Sealed Secrets 공개 인증서는 저장소(`v3/platform/sealed-secrets-cert.pem`)에 두어 봉인에 클러스터 접속이 필요 없게 했습니다. 평문은 실행 중 임시 폴더에만 두고 남기지 않습니다(#228, #229).
- **Argo 동기화** — Secret Application은 모든 환경에서 수동 sync입니다.

**트레이드오프**

- **Controller 운영** — 복호화 Controller와 키의 백업, 복구를 관리하는 부담을 감수했습니다.
- **수동 봉인** — SSM 값이 바뀌면 관리자가 스크립트를 다시 실행하고 커밋, sync해야 반영됩니다.
- **키 유실 대응** — 기존 암호문을 복호화할 수 없게 되는 위험에 대비해 Git 외부 백업과 클러스터 재구축 시 복원을 준비하기로 했습니다.

**출처**

- [Sealed Secrets, 암호화 범위, 키 백업](https://github.com/bitnami/sealed-secrets)
- [Argo CD의 Secret 관리 권고](https://argo-cd.readthedocs.io/en/stable/operator-manual/secret-management/)
- [SOPS](https://getsops.io/docs/)

## 8. 관측: Prometheus, Loki, Grafana

**결정 요약**: Prometheus, Loki, Grafana는 EKS 외부 관측 EC2(t3.medium, AL2023, 시스템 Node와 같은 사설 Subnet) 한 대에 docker compose로 배치하고, dev, stage, prod를 함께 관측합니다. 로그와 메트릭 수집은 모두 `tool` Namespace의 Node별 Alloy DaemonSet이 맡아 로그는 Loki로, 메트릭은 Prometheus remote-write로 보냅니다. Grafana는 전용 CloudFront 배포(`grafana.dameokja.com`)와 GitHub OAuth 로그인으로 엽니다.

**이유**

- **대시보드 대기 시간 개선** — CloudWatch를 사용하며 경험한 긴 대기 시간을 개선하기 위해 PLG를 선택했습니다.
- **저장소 연동 부담 축소** — EKS 내부 PLG와 비교해 PVC, CSI, Pod 재배치 시 저장소 연결을 관리하는 범위를 줄이기로 했습니다.
- **실행 기반 분리** — 관측 시스템의 실행 기반을 EKS와 분리하기로 했습니다.
- **수집 설정 중복 축소** — 앱별 전용 수집 요구가 없어 Sidecar 대신 Node별 Alloy를 선택했습니다.
- **클러스터 자격 증명 불필요** — Alloy가 클러스터 안에서 긁어 remote-write로 보내므로 관측 EC2에 클러스터 자격 증명이 필요 없고, Node SG에 kubelet 10250, kube-state-metrics 8080 수신을 열지 않아도 됩니다(#246).
- **팀의 조회 편의** — SSM 포트 포워딩 없이 팀이 Grafana를 보도록 도메인을 열고, 접근은 GitHub 로그인으로 제한했습니다(#288, #289).

**근거**

- **수집 구성** — Alloy는 자기 Node의 Pod 로그(`/var/log/pods`), kubelet, cAdvisor와 같은 Node의 kube-state-metrics, BE `/actuator/prometheus`, Karpenter 메트릭을 수집하고(kubelet, cAdvisor, kube-state-metrics, BE는 15초 간격) 모든 대상을 자기 Node로 나눠 중복 수집을 피합니다(#247, #297). Kubernetes 이벤트는 단일 Alloy Deployment가 수집합니다(#297).
- **보존과 저장** — 메트릭 15일(크기 상한 15GB), 로그 7일이며 데이터는 별도 EBS(gp3 30GiB, Retain)의 `/data`에 둡니다. 설정과 대시보드는 CloudFormation의 State Manager Association이 파일로 넣습니다(#246, #249).
- **Grafana 접근** — 관측 SG는 CloudFront origin-facing prefix list만 3000으로 받습니다. GitHub 아이디 허용 목록에 있는 사람만 첫 로그인 때 자동 가입되고 역할(GrafanaAdmin, Editor)은 로그인마다 목록대로 맞춰지며, 비밀번호 로그인과 API Basic 인증은 껐습니다(#296). 서비스용 CloudFront와 배포를 나눠 Grafana 변경이 서비스 경로에 영향을 주지 않게 했습니다.
- **개선 효과 검증** — PLG의 조회 성능은 기존 CloudWatch와 비교해 검증하기로 했습니다.

| 대안 | 판단 |
|---|---|
| CloudWatch 유지 | 기존 구성을 활용할 수 있지만 대시보드 대기 시간의 개선 검토가 필요했습니다. |
| EKS 내부 PLG | 자동 복구를 활용할 수 있지만 PVC, CSI와 Pod 재배치 시 저장소 연결을 함께 관리해야 했습니다. |
| 별도 EC2 중앙 PLG | Kubernetes 저장소 연동을 줄이고 실행 기반을 EKS와 분리하기 위해 선택했습니다. |

**트레이드오프**

- **EC2 직접 관리** — 관측 서버의 OS, 도구, 프로세스, 스토리지, 복구는 직접 관리하기로 했습니다.
- **Node별 수집 장애 영향** — Alloy 장애 시 해당 Node의 여러 Pod 수집이 함께 영향을 받는 한계를 감수했습니다.
- **중앙 관측의 장애 영향** — 관측 EC2, AWS 장애에 따른 중앙 관측 중단과 일부 수집 공백, 로그 유실을 감수했습니다. 짧은 중단은 Alloy WAL과 재시도로 이어서 보냅니다.
- **수신 포트 인증 없음** — remote-write, Loki 수신 포트는 인증이 없어 SG(Node SG에서 3100, 9090)로만 제한합니다. Prometheus 화면의 targets에는 클러스터 대상이 보이지 않아 수집 상태는 Alloy 쪽에서 확인합니다(#246).
- **공개 도메인의 위험** — Grafana가 인터넷에 열려 있어 접근 통제가 GitHub 로그인과 허용 목록에 의존하고, 팀원 추가, 삭제는 목록을 고쳐 apply해야 합니다.

- [Prometheus](https://prometheus.io/docs/introduction/overview/)

## 10. 비용과 운영 복잡성

**결정 요약**: 처리 용량과 복구 요구를 먼저 설계하고 구현 예산은 별도로 검토합니다. 운영 시간은 환경별로 구분하여, dev, prod와 공통 자원(시스템 Node, 관측 EC2, ALB, CloudFront)은 상시 운영하고 stage는 필요할 때만 켭니다.

**이유**

- **설계 기준 유지** — 필요한 처리 용량, 복구 요구와 실제 구축 비용을 구분하여 검토하기로 했습니다.
- **stage 사용 시간 제한** — stage는 쓸 때만 켜도록 GitHub Actions 켜기, 끄기 Workflow를 두었습니다(#272, #273). 끄면 앱 0, Kafka 조정 일시정지와 PodSet 삭제, Redis 0, DB EC2 중지 순서로 내리고, 빈 stage Node는 Karpenter가 5분 뒤 정리합니다. PVC는 남깁니다.
- **dev 상시 비용 축소** — dev 앱 Node를 1대로 합쳐 월 약 $90을 줄였습니다(#279, #280).

**근거**

- **산정 시간 기준** — 상시 자원은 월 730시간, stage는 실제 켠 시간으로 산정합니다.
- **비용 합산 범위** — 클러스터, Node, DB, 스토리지, 전송, 관측 비용을 함께 합산하기로 했습니다. stage를 꺼도 PVC, EBS와 중지된 DB EC2의 디스크 비용은 남습니다.
- **켜기 경로** — GitHub 러너는 사설 EKS API에 닿지 않으므로 SSM으로 시스템 Node에서 `power.sh`를 실행하고, 그 kubectl 권한은 stage Namespace 안으로 제한했습니다(#272).

**트레이드오프**

- **stage 기동 대기** — stage를 쓰기 전 DB, Redis, Kafka, 앱을 차례로 띄우는 시간을 기다려야 하고, 꺼진 동안 반영된 이미지는 켤 때 sync됩니다.
- **별도 예산 검토** — 일부 자원만으로 전체 운영 비용을 판단하지 않고 운영 항목별 비용을 추가 확인하기로 했습니다.
